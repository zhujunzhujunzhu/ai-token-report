# 数据库重设计：接口与真实验收

日期：2026-09-26。配套主设计：[服务端数据库重设计（Portal v4）](数据库重设计.md)。

本文记录 Portal v4 的接口方案与验收标准。数据库身份、账号、会话、管理接口及显式迁移已实现，已执行项目的范围与证据以 [2026-09-26 真实端到端报告](真实端到端验收-2026-09-26.md) 和 [数据库验证记录](database-v4/验证记录.md) 为准。真实浏览器交互尚在验收，原有真实业务库未自动迁移；建表检查、HTTP 对账与客户端上报均不能替代浏览器验收，也不表示所有阶段已经完成。

## 2. 统一身份与授权结果

数据库表名、字段约束和种子权限以主设计及 `database-v4/` DDL 为准。服务端内部使用类似下面的结构，禁止由请求体直接构造可信身份：

```ts
interface Principal {
  memberId: string
  name: string
  departmentId: string | null
  roleCodes: string[]
  permissions: string[]
  auth: { kind: 'session'; sessionId: string; accountId: string }
      | { kind: 'token'; tokenId: string }
}
```

内部类型使用 camelCase，新 HTTP/DB 字段使用 snake_case，转换在边界完成。Principal 不包含明文 Token、Cookie 或密码哈希。这里的权限必须来自当前数据库：Cookie 使用角色权限，Bearer 使用角色权限与 `report_token_scopes` 的交集。

既有身份校验响应继续保留 `ok/name/dept/role/registered/reason`，可增加 `member_id`，使旧 CLI/插件继续工作。`role` 保留兼容投影；新的后台以 `permissions` 判断操作入口，不能把缺少字段默认解释成管理员。

登录和 Session 响应增加稳定身份和数据库权限，例如：

```json
{
  "ok": true,
  "viewer": {
    "member_id": "11111111-1111-4111-8111-111111111111",
    "name": "张三",
    "username": "zhangsan",
    "department_id": "22222222-2222-4222-8222-222222222222",
    "department_name": "研发部",
    "role": "member",
    "roles": [{ "role_id": "33333333-3333-4333-8333-333333333333", "code": "member", "name": "普通成员" }],
    "permissions": ["identity:read", "usage:write", "stats:read", "departments:read"]
  }
}
```

后台默认通过 Cookie 登录。保留旧管理 Bearer 的兼容入口；新上报 Token 默认仅有 `identity:read` 和 `usage:write`，即使其所属人员是管理员，也不能拿它管理人员或读取统计。迁移旧 Token 时固定导入其原有范围，之后角色升权不会给该 Token 自动增加 scope。

凭证和角色授予遵循一个原则：**操作者不能通过签发另一种凭证或分配角色，授予超出自己本次有效权限的能力。** 不能只验证 `tokens:manage`、`accounts:manage` 或 `roles:assign` 这个动作权限：

- Token 签发、扩 scope 和轮换：`grantableScopes = actor.permissions ∩ target 当前角色权限`；请求的新范围必须是这个集合的子集。默认上报范围也须完整可授予，不能静默删减。
- 轮换未提供 scope 时保留原范围；只有原范围完全可授予才执行。否则 403，要求具足够权限的管理员明确签发新凭证，不能借轮换扩权，也不能静默缩减。
- 角色分配：请求的角色组合所包含的权限必须全部在 actor 本次有效权限内；仅有 `roles:assign` 的窄 Token 不能给自己升为管理员。
- 开通、重置或恢复登录账号会使目标获得完整角色的 Cookie 身份，因此还须 actor 本次有效权限覆盖目标当前角色的全部权限。仅有 `accounts:manage` 的窄 Token 不能通过重置自己的密码换取完整管理员 Cookie。单纯停用账号仍使用动作权限和最后管理员护栏。

上述条件全部在写事务中使用当前数据库状态重新验证，不用人员角色权限替代 actor 经过 Token scope 限制后的本次有效权限。

## 3. 人员、部门、角色与凭证接口

为缩小迁移面，目标接口沿用现有 `/api/v1/admin` 和 POST 操作风格。新增动作和新请求字段必须在 shared 中定义，并在同一版服务器和后台页面中接入；表内接口是目标契约，不表示已存在。

| 方法与路径 | 请求要点 | 必需权限与结果 |
|---|---|---|
| `GET /api/v1/admin/members` | 可按状态/部门筛选 | `members:read`；返回人员 ID、姓名、部门、角色、账号摘要和版本，不返回秘密 |
| `POST /api/v1/admin/members` | `name, department_id?, role_ids` | `members:manage`；分配角色另需 `roles:assign`；创建人员，不隐式签发 Token |
| `POST /api/v1/admin/members/update` | `member_id, expected_version, name?, department_id?` | `members:manage`；不允许混入密码或角色字段 |
| `POST /api/v1/admin/members/roles` | `member_id, expected_version, role_ids` | `roles:assign`；事务内替换角色关系并重验最后管理入口 |
| `POST /api/v1/admin/members/status` | `member_id, expected_version, status` | `members:manage`；停用/恢复人员，历史不删除 |
| `POST /api/v1/admin/members/login` | `member_id, expected_version, username, password` | `accounts:manage`；开通/重置后台账号，不需要上报 Token |
| `POST /api/v1/admin/members/login/status` | `member_id, expected_version, enabled` | `accounts:manage`；停用账号与会话，独立于上报凭证 |
| `GET /api/v1/admin/members/tokens?member_id=…` | 人员 ID | `tokens:manage`；只返回 Token 元数据及 scopes |
| `POST /api/v1/admin/members/tokens` | `member_id, label, scopes?, expires_at_ms?` | `tokens:manage`；返回新凭证摘要及一次性 `token_secret` |
| `POST /api/v1/admin/members/tokens/rotate` | `member_id, token_id, expected_version` | `tokens:manage` 且可授予完整原范围；原子吊销旧 Token、签发同范围新 Token |
| `POST /api/v1/admin/members/tokens/revoke` | `member_id, token_id, expected_version` | `tokens:manage`；只吊销目标 Token |
| `POST /api/v1/admin/members/tokens/scopes` | `member_id, token_id, expected_version, scopes` | `tokens:manage`；范围必须由服务端允许，不能超过操作者可授予及目标当前角色权限 |
| `GET /api/v1/admin/roles` | 无 | `roles:read`；数据库角色目录和权限摘要，首期仅两个内置角色 |
| `GET /api/v1/departments` | 可按启用状态筛选 | `departments:read`；数据库部门目录，供普通成员与管理员使用 |
| `POST /api/v1/admin/departments` | `name` | `departments:manage`；创建部门 |
| `POST /api/v1/admin/departments/update` | `department_id, expected_version, name` | `departments:manage`；重命名不改变 ID 或历史快照 |
| `POST /api/v1/admin/departments/status` | `department_id, expected_version, status` | `departments:manage`；停用后不能新分配，已有引用保留 |
| `GET /api/v1/admin/audit` | 时间、动作、对象筛选及分页 | `audit:read`；返回脱敏操作记录 |
| `GET /api/v1/admin/storage` | 无 | `members:read`；只返回数据库类型、schema 版本、可用状态，不返回连接密码或凭证文件路径 |

角色、权限、部门候选都从 API 读取；页面不能把两个角色的中文名称、部门选项和可操作权限作为另一份权威数据。首期不增加自定义权限编辑器。

`member_id` 不是秘密，但也不是授权依据。Token 操作必须验证 `token_id` 确实属于所传 `member_id`。角色分配和 scope 变更不能依赖前端选项限制。

`expected_version` 对应被操作对象：人员资料、角色和账号管理使用 `members.version`，这些变更都递增该版本；凭证操作使用 `report_tokens.version`，部门操作使用 `departments.version`。账号另有密码版本用于 Session 失效，两种版本不能混为一谈。

姓名和部门校验继续复用现有规则：姓名最多 32 个 UTF-16 code unit，部门最多 64 个 UTF-16 code unit（即 JavaScript `String.length`），保留 trim 与换行/制表符规则。不要因数据库 VARCHAR/CHAR_LENGTH 按字符计数就扩大 API 接受范围；回归须覆盖 emoji 边界。规范化用户名仍唯一，显示名允许同名。

人员列表目标形状：

```json
{
  "members": [{
    "member_id": "11111111-1111-4111-8111-111111111111",
    "name": "张三",
    "status": "active",
    "department_id": "22222222-2222-4222-8222-222222222222",
    "department_name": "研发部",
    "roles": [{ "role_id": "33333333-3333-4333-8333-333333333333", "code": "member", "name": "普通成员" }],
    "account": { "username": "zhangsan", "enabled": true },
    "active_token_count": 2,
    "version": 4,
    "created_at_ms": 1790370000000,
    "updated_at_ms": 1790370300000
  }]
}
```

修改示例：

```json
{
  "member_id": "11111111-1111-4111-8111-111111111111",
  "expected_version": 4,
  "name": "张三（研发）"
}
```

业务失败继续使用现有 `{ "ok": false, "reason": "…" }` 形状。鉴权失败保持非 2xx：401 无有效身份、403 缺少所需权限、503 身份存储不可用或尚未完成初始化。请求形状错误 400；新增 `expected_version` 冲突返回 409 并让页面刷新对象，不能盲目重试覆盖别人修改。管理成功返回提交后的对象和新版本。

旧 `/members/update|login|rotate|revoke` 的 Token 定位载荷不能被悄悄当成新人员 ID。后台同版切换后，旧载荷明确拒绝并提示更新页面；如部署需要兼容旧管理调用，应做显式、有期限的适配层。上报与身份校验契约则保留兼容，不要求员工同步更新客户端。

## 4. 一次性 Token 展示与人员生命周期

列表只显示 `token_id`、用途标签、不可认证的提示、scopes、签发/到期/吊销时间和版本。签发或轮换的成功响应另外包含 `token_secret`；任何 GET、普通修改响应、审计和日志都不能出现原值。

页面只在本次成功弹窗中保留 `token_secret`，关闭、退出账号或离开页面后清空，不写 localStorage、路由或全局持久 store。复制失败时仍可人工选择本次值。用户未保存或响应在网络中丢失时，页面允许再次明确轮换，不声称能从数据库找回原值，也不自动重复签发。

| 操作 | 账号/会话 | 上报 Token | 历史与身份 |
|---|---|---|---|
| 改名、转部门 | 会话继续，下次读取新资料 | 继续有效 | `member_id` 不变，旧事件快照不变 |
| 修改角色 | 会话可继续，下一请求获得当前权限 | 仍受自身 scope 与当前角色交集约束 | 不重写事件 |
| 改用户名/密码 | 账号版本递增，全部旧会话失效 | 不变 | 不变 |
| 轮换或吊销一枚 Token | 后台 Cookie 不受影响 | 仅旧/目标 Token 失效 | 新旧事件属同一 `member_id` |
| 停用登录账号 | 该账号全部会话失效 | 不变 | 人员保留 |
| 停用人员 | 不可登录，旧会话失效 | 全部失效并记录吊销 | 人员和事件保留 |
| 恢复人员 | 明确开通/恢复登录后重新登录 | 被吊销的 Token 不复活 | 不接管其他同名人员历史 |

“自己”比较 `viewer.member_id`；同名人员不影响判断。创建时间分别属于人员、账号和每枚 Token，轮换不能改人员入职/创建时间。

## 5. 统计查询兼容与历史归属

不能把已有 `?user=张三` 的含义默默替换成“传 UUID”，也不能在找不到 UUID 时猜它是姓名。统计接口通过显式 `identity_view=member` 选择新归属视图；缺省或 `identity_view=legacy` 保持旧版查询与响应键语义。未知视图返回 400。新版页面的概览、排行、候选人员、趋势、分布、明细和个人详情请求全部携带 `identity_view=member`，不能只改排行接口。

目标查询新增独立参数：

| 参数 | 明确语义 |
|---|---|
| `member_id=<UUID>`，可重复 | 仅用于 member 视图，按新的稳定人员 ID 精确筛选 |
| `legacy_user=<opaque-key>`，可重复 | 仅用于 member 视图，按旧归属键精确筛选旧事件；不等于筛当前同名人员 |
| `unattributed=true` | 仅用于 member 视图，只筛 `member_id IS NULL AND user_id IS NULL` 的真实未归属历史 |
| 旧 `user=张三,李四` | 仅用于 legacy 视图，维持既有 `user_id` 精确匹配及 `unknown` 规则，不改成 ID 查询 |

同一请求不得混用旧 `user` 与新的三种选择器，混用返回 400。选择器与 identity_view 不匹配也返回 400，不能靠参数出现与否隐式切换视图。新选择器之间按并集选择人员，随后与时间/provider/model 条件取交集。重复参数消重；空值、非法 UUID、损坏的历史 key 必须报 400，不能悄悄变成无筛选的全量查询。

legacy 视图只能返回可无损表示的旧身份数据。如果所查范围含同名但不同 member、同一 member 改名后对应多个旧键，或待确认历史与当前人员无法用旧字段准确区分，返回 409 和 `code: "identity_view_required"`，提示升级页面使用 member 视图。不能为了兼容旧页面静默合并、拆分或猜归属；其他无歧义的旧请求仍按原响应键返回。旧 CLI/插件只调用上报/身份校验，不需要增加该参数。

历史 key 由服务端生成，例如 `legacy:` 加旧 `user_id` UTF-8 字节的 base64url 编码；浏览器只把它视为不透明值，用 URLSearchParams 编码，不自行猜姓名。`legacy_user` 永久表示该旧键对应的历史子集：即使映射后来得到确认，也不把收藏的旧筛选条件静默扩大为该成员全部新旧事件。

member 视图的人员排行返回分组键和标签两个字段。目标用户分组行增加：

```json
{
  "key": "11111111-1111-4111-8111-111111111111",
  "label": "张三",
  "member_id": "11111111-1111-4111-8111-111111111111",
  "department_name": "研发部",
  "attribution_status": "member",
  "totalTokens": 1200,
  "inputTokens": 100,
  "outputTokens": 100,
  "cacheReadTokens": 1000,
  "calls": 1,
  "cacheHitRate": 0.9090909090909091
}
```

这里保留已有统计指标字段名与服务端计算方式，不借身份迁移重命名全部指标 DTO。新身份字段单独定义并在前端边界转换。`key` 的三种空间互不相撞：UUID、`legacy:…`、`unknown`。待确认历史行显示“历史人员：姓名（待确认）”，不能显示为匿名或混入当前同名人员。

明细保留旧 `userId` 的兼容含义，并新增 `member_id`、`user_name_snapshot`、`department_id`、`dept_snapshot`、`attribution_status`。新版页面使用显式标签与快照，不能直接把 UUID 展示为人名。部门快照来自接收时确定的部门，不能冒称事件发生时部门。

候选人员用不含人员筛选的同窗口查询取得。当前人员、待确认历史和真实未归属都须能单独选择；同名人员显示部门或短 ID 辅助区分。映射确认前后，概览、排行、筛选、人数、趋势和明细必须使用同一归属规则，确认后合并的是显式指定的历史键，不能自动合并同名人员。

## 6. 会话、并发和事务的验收边界

`auth_sessions` 存 Cookie 随机值的摘要、账号 ID、签发时认证版本、到期/吊销信息；每次解析读取账号和人员状态、当前角色权限。现有 `password_version` 作为账号认证版本：密码、用户名和登录启用状态变化均须递增，并失效旧会话，不能只递增普通 CAS `version`。服务重启不清空有效会话，实例 A 登录后可由实例 B 处理。Session 不保存上报 Token 或复制密码哈希。首期保留现有 8 小时会话期限与 120 秒验证码期限。

验证码写入 `auth_challenges`，答案使用共享部署密钥生成 HMAC，绑定浏览器并有过期时间；消费必须是数据库条件更新，同一挑战的并发请求最多成功消费一次。`auth_rate_limit_buckets` 的扣减和窗口滚动原子完成；换服务实例或重启不能清零重试次数。哈希并发数量等纯进程资源保护仍可留在内存。

所有管理变更按以下顺序执行：

1. 初步鉴权和参数校验；密码 KDF 在事务外计算，避免长期占锁。
2. 开事务并锁 `portal_identity_state` 单例行；读取当前操作者认证记录、人员、权限和目标对象。
3. 重新验证会话/Token 仍有效、操作者仍有相应权限、目标版本未变；不能复用 KDF 前的授权结果。
4. 判断最后可用管理入口，执行变更、会话/凭证失效和成功审计。
5. 提交成功后才返回成功和一次性秘密；失败则整个业务事务回滚。

最后管理入口按不同人员去重计算，不能用 Token 数或角色关系行数代替。它必须是启用人员，具有足够管理权限，并拥有启用且可登录的管理员账号，或拥有**无过期时间**、有效且具有足够管理 scope 的兼容 Token。短效管理 Token 可以在有效期内使用，但不计为唯一永久恢复入口。只有角色标记的空壳管理员不计数。账号停用、人员停用、角色移除、Token 吊销/轮换/缩 scope 都参与同一护栏；初始化优先建立可登录管理员账号。

两管理员并发互相降级，第二个事务重新验证操作者后可能以 403 拒绝；也可能因最后管理员护栏拒绝，但绝不能两个都成功。SQLite 需进程内队列与数据库写锁共同保护，MySQL 需固定事务连接及行锁，内存锁不能代替跨进程锁。

上报也要定义撤权生效边界：一次请求的鉴权、人员/Token 状态确认和事件写入须组成可说明的事务顺序。撤权提交前已经合法提交的事件保留；撤权先提交后开始写入的请求必须拒绝，不能拿旧 Principal 写新事件。去重重放不能更新首次归属、`report_token_id` 或 `received_at_ms`。

新增外键后要重新审查 `insertAttributedRecords()` 的重复计数：只有 `event_id` 主键冲突才能算 duplicates。现有按 INSERT IGNORE 的受影响行数差额计算重复数的做法，不能把外键、CHECK、字段截断等错误当作重复并返回成功 ACK；此类错误应回滚并返回非 2xx，保留客户端待投递数据。

## 7. 迁移接口与验收证据

迁移是显式维护操作，不由普通请求顺手触发。目标流程应提供 inspect/plan/apply/resume 等明确模式；具体命令待实现时定义，不在本文伪造已经存在的 CLI。

预检直接读取原始凭证文件，至少检查重复 Token、文件/env 冲突、重复规范化用户名、非法角色、无效密码哈希和历史归属歧义。缺省角色按旧 member 规则处理，显式非法角色必须进入报告，不能在导入中无声变成另一个权限结果。旧 Token 求摘要后保持原值仍可用；合法密码哈希直接复制。

导入过程保留源文件校验和、迁移版本、执行步骤、去敏数量清单和映射确认依据。数据库一旦初始化，环境变量不能复活已被停用的管理员。旧的内存 Session 没有可导入的持久真值，切换时允许一次明确重新登录；迁移后新 Session 必须跨重启存活。

事件验收必须逐项比较：`event_id` 集合、全部原始字段校验和、四项 token 各自 SUM、`reasoning_tokens`、调用数及未归属/待确认/已确认数量。新增外键和快照不能改事件原值。旧记录缺少接收时间和凭证 ID 时留 NULL，不能使用迁移时间或任意 Token 编造历史。

MySQL 和 SQLite 各验证空库创建、现有 v3 副本升级、断点恢复及重复执行。MySQL DDL 的步骤恢复与身份导入业务事务分开验收。未知版本、损坏迁移记录或校验和不匹配时拒绝写入，不能 drop/rebuild；本地 `usage.sqlite` 的版本与内容不得被 portal 升级影响。
