# 数据库部署与迁移

部门服务端以 MySQL 为正式部署主库，SQLite 保留给本地部署及验证。人员、分组、角色、权限、登录账号、上报 Token、会话、验证码、限流、审计、历史身份映射、**供应商归一化规则**和**模型单价**均进入同一个 **v7** 部门数据库（**v4 是冻结基线**：v3 库先迁到 v4，再依次走 v4→v5、v5→v6、v6→v7）。本机 `usage.sqlite` 仍是可重建的日志索引，与部门库严格分离。

## 新部署

使用数据库管理员预先创建独立 MySQL 数据库和专用账号，编码为 `utf8mb4`，业务表使用 InnoDB。给专用账号授予这个库所需的建表、索引、查询和写入权限，不给其他业务库的权限。连接串通过部署系统的秘密配置注入 `ATR_MYSQL_URL`，密码中的保留字符需 URL 编码，不能把真实连接串写进仓库或日志。

首次启动配置：

| 变量 | 用途 |
| --- | --- |
| `ATR_MYSQL_URL` | 部门数据库连接串；不配置时使用 SQLite |
| `ATR_ADMIN_USERNAME`、`ATR_ADMIN_PASSWORD` | 空库初始化管理员登录账号；密码 12～128 个字符 |
| `ATR_ADMIN_NAME` | 管理员显示姓名，可选 |
| `ATR_ADMIN_TOKEN` | 可选的初始化管理 API Token；只需要网页登录时可以省略 |
| `ATR_CAPTCHA_HMAC_KEY` | 至少 32 个字符的随机秘密，所有实例使用同一值 |
| `ATR_PORTAL_ORIGIN` | HTTPS 反向代理对外地址，例如 `https://tokens.example.com` |

初始化值只对空库生效，后续数据库为唯一真值。停用的账号不会因环境变量还在而复活。初始化成功后可移除管理员初始化秘密；保留数据库和验证码密钥配置。

```bash
bun install
bun run build:portal
bun run --filter @ai-token-report/server build:node
node packages/server/dist/main.mjs --port 8787 --static packages/web-portal/dist
```

Node 入口与 Bun 共用相同路由及数据库实现，MySQL 走已安装的 `mysql2` 依赖。当前 Windows Bun 1.4.2 实测存在 MySQL `caching_sha2_password` 长密码认证问题，正式联调使用 Node 22.21.1；不要缩短密码或降低数据库认证强度。详情及官方问题链接见 [MySQL 上报库](./mysql上报库.md)。

SQLite 可直接 `bun run server -- --db <独立的portal.sqlite路径>`，同样需要初始化账号及验证码密钥。默认仅监听 `127.0.0.1`；配置好数据库身份后，再按部署需要设置监听地址及反向代理。

登录后台后先维护**分组**和人员，再为人员设置角色、**所属分组（可多选，一个人可同属多个分组）**与登录账号。人员与凭证分离，同一个人可以有多把独立凭证。默认上报 Token 仅有 `identity:read` 和 `usage:write`，不能读取全员看板。**给员工发插件 / CLI 用的凭证走「appKey 管理」页**：范围由服务端固定为 `usage:write` + `stats:read`（上报用量 + 获取统计信息），列表每行一把 key 并按人员关系标明**发给了谁**，可搜索、可轮换 / 吊销、可设置与修改**有效期**（留空 = 长期有效；过期只是时间比较，所以过期的 key 可以续期而不必轮换），**交付信息**（上报 / 统计的完整地址 + 使用人 + 凭证提示）点开弹框查看。服务端只存摘要，明文只在签发 / 轮换成功那一次出现：页面不把完整值放进 DOM（最多显示 `atr-ab12…ef34` 这种中间省略号遮罩），完整值只在剪贴板里，关掉就找不回来，只能轮换；人员管理页不再承担凭证功能。

### 供应商归一化（v6，`/providers`）

上报里同一个供应商可能以多个名字出现（实测 `dashscope` 与 `bailian` 是同一家），
于是「按供应商看用量」会散成好几行。**供应商归一化**把指定的原始名折叠成一个展示名，
配置入口是看板侧边栏的「供应商归一化」页（需 `providers:read` 才看得到，改规则另需 `providers:manage`）。

四条需要知道的语义：

1. **配在查询期，不改历史数据。** `usage_event.provider` 永远是上报当时的原值，
   规则只决定「分组与筛选时按哪个名字算」。所以改一条规则**立刻**生效、
   历史数据不需要回填，删掉规则就恢复原状 —— 迁移期间不需要任何额外步骤。
2. **没配规则的供应商保持原始名。** 这不是「统一改名」，是「折叠少数几个」。
   原始名与归一化名都参与大小写不敏感的**子串**筛选，但筛选作用在归一化后的名字上：
   一个已经被折叠掉的原始名再也搜不到它（去「调用明细」页那一列看原值）。
3. **作用范围分全局与按人。** 全局规则对所有人生效；人员规则只对那个人生效，
   **逐条覆盖、未命中回落全局**。同一个库，两个人看到的供应商分布可以不同 ——
   归一化按**查看者身份**解析，绝不从查询参数取「以谁的身份归一化」。
4. **原始名是大小写敏感的精确匹配**，写错大小写、结尾多一个空格都会静默不命中；
   原始名限 ASCII 标识符形状，归一化名允许中文（但不能含 `/`，它是 `provider/model` 的分隔符）。
   明细页始终同时显示原值，就是用来核对「规则到底配没配对」的。

### 模型单价（v7，`/pricing`）

用量金额按 `(provider, model)` **精确匹配**一张单价表算出。维护入口是看板侧边栏的
「模型单价」页（`/pricing`），**读也归 `pricing:manage`** —— 单价是配置，不是「看一眼的数字」，
能看金额的人不必能看 / 改计价表。首次部署可用内置种子价一键写入
（`POST /api/v1/admin/pricing/seed`，**库里已有单价时拒绝**，避免覆盖人工维护的结果），
之后按真实生效日维护。完整口径见 [费用统计方案](./费用统计方案.md)。
**看数据时的只读快照**另走 `GET /api/v1/stats/pricing`（门是 `cost:read`）——
它只读 `model_price`、回答「这个金额是按哪个价算的」，**不含任何用量**；
管理面的 `/api/v1/admin/pricing*` 才是配置面。

要知道的五条：

1. **金额绝不落库。** 四个 `*_micro_per_ktok` 列与 `usage_event` 的四类 token 一一对应，
   金额一律在**查询期**用「事件发生时刻」选中的那条价现算 —— 所以改价、补历史价即时生效，
   `usage_event` 一个字节都不用动，**没有也不需要任何回填步骤**（页面也没有回填按钮）。
   概览金额必须**先按 `(provider, model)` 分组算完再求和**，不能用「总量 × 均价」。
2. **金额是整数「微元 / 千 token」**（1 微 = 1e-6 货币单位，上限 1e7 微/Ktok，
   由应用层常量统一收口），不会出现小数累加的分位误差。
   ⚠️ 页面与录入按「**货币单位 / 百万 token**」呈现（与官方价目表同单位），
   两者差 1000：`2 元/百万 = 2000 微元/千`；换算是整数倍，只在
   `packages/web-portal/src/utils/unitPrice.ts` 一处。
   **多币种各自累加，绝不换算、绝不相加**（`currency` 是 ISO 4217 三位大写）——
   汇率是第二个口径，合并币种只能靠录入时的人工决策。
3. **未匹配到单价的用量显式计入 `unpricedRate`**，**绝不当成 0 元**，
   失配即失配、绝不回退到模糊匹配 —— 与「鉴权失败不能渲染成 0 值空看板」是同一条理由。
4. **自建计价 ≠ 财务账单。** 折扣、预付、赠送额度都不在单价里；
   账单数字只出现在单独的对账报告里，**不进入任何页面或接口**。
5. **生效区间两端都是含的。** `[1,100]` 与 `[100,200]` 算**重叠**（共用一个端点），
   所以相邻两段的起点必须**严格大于**上一段的终点；真正重叠的区间由应用层
   `findPriceConflicts()` 拦下并回 **409** —— 数据库的唯一索引只挡「起点完全相同」那一类。

单价匹配用的是**上报原值**，供应商归一化（上一节）只改分组与筛选时的展示名、**不参与计价** ——
否则改一条展示规则就会悄悄改动历史金额。

> ⚠️ **现状**：v7 落地了**单价表与计价配置**（`model_price` 表、`/pricing` 页、
> `pricing:manage` / `cost:read` 两个权限码），并且金额的查询期计算与 `cost:read` 展示门禁
> **已经接进 `/api/v1/stats/*`**（S5 已完成）—— 有 `cost:read` 时看板会显示金额
>（概览卡片 / 排行与分布费用列 / 明细逐条金额 / 趋势费用指标），**无 `cost:read` 时整个
> `cost` 字段不下发**（不是返回 0）。看金额时的**只读单价快照**走 `GET /api/v1/stats/pricing`
>（`cost:read`），与配置面 `/api/v1/admin/pricing*`（`pricing:manage`）是**两条接口两道门**。
> 本地页面与 CLI 的金额仍待 S6。分期见 [费用统计方案](./费用统计方案.md)。

## 从旧版本迁移

**先备份并停止所有旧服务实例，再执行显式迁移。** 新服务看到 v3 / v4 / v5 / v6 旧库会拒绝启动；不会删库、重建或悄悄迁移。不要把员工机器上的 `usage.sqlite` 作为部门迁移目标。

版本路线（由 `packages/core/src/db/portal-migrations.ts` 决定）：

| 起点 | 路径 |
|---|---|
| 空库 | 直接建 **v7** |
| v3 老库 | 先走 **v3→v4**（只增表 / 增可空列；`portal-schema-v4.ts` 是冻结基线），再走 **v4→v5**、**v5→v6**，最后 **v6→v7** |
| v4 库 | 走 **v4→v5**、**v5→v6**，再走 **v6→v7** |
| v5 库 | 走 **v5→v6**，再走 **v6→v7** |
| v6 库 | 只走 **v6→v7** |

**v5 → v6 只增表**：新建 `provider_alias`（供应商归一化规则）与两个权限码
`providers:read` / `providers:manage`，并把它们授予内置管理员角色。
它不改任何既有列、不重建事实表、不触碰事件行 —— 所以这一步不需要备份证明那套编排，
`migrate` 会自动接着 v5 之后执行（v4 升上来的库在同一次 `migrate` 里连做两步）。

**v6 → v7 同样只增表**：新建 `model_price`（模型单价）与两个权限码
`cost:read` / `pricing:manage`，并把它们授予内置管理员角色。
与 v5→v6 完全同构 —— 不改既有列、不重建事实表、不触碰事件行，因此同样不需要备份证明，
`migrate` 会一路接着做下去（v4 或 v5 升上来的库在同一次 `migrate` 里连做多步）。
**事实表一个字节都不动，所以这一步不需要再比对一次事件指纹**；
真正的回退位就是「删掉这张表」。

⚠️ 唯一要留意的是 `model_price` 带一个**唯一**索引 `idx_model_price_span`，
而唯一索引在迁移路径里的建法踩过一个坑 —— 见下面 MySQL 小节的第 4 条。

**v4 → v5 会改结构**：`departments` → `member_groups`、`department_id` → `group_id`、
`members.department_id` 的归属搬进新关联表 `member_group_assignments`（多对多）、
`usage_event.dept` → `group_name` 并去掉 `usage_event.department_id`、
权限码 `departments:read|manage` → `groups:read|manage`（只改 `permissions.code`，权限 ID 与角色关联不变）。
**SQLite 分支必须重建事实表**（SQLite 不允许 DROP 掉被外键引用的列），
所以升级期间会关掉 `foreign_keys`、并用事务内的 `PRAGMA foreign_key_check` 兜住 —— **必须先按下面的备份流程执行**；
MySQL 分支不必重建事实表，但要绕开三条**只有活体 MySQL 才会报**的方言限制（见下一小节的前三条）。
两个分支都在迁移前后逐位核对事件指纹，不删事件行、不改写任何事件原值。

### MySQL 分支为什么看起来比 SQLite 麻烦

下面四条在 SQLite 上**一条都不会出现**（它会连带改写 CHECK、不在意列类型漂移，
**也从不比对索引**），所以「在 SQLite 上迁移跑通了」在这里**不构成证据**：

1. **`DROP COLUMN` / `RENAME COLUMN` 会被引用该列的 CHECK 约束挡住**
   （errno 3959 `Check constraint 'x' uses column 'y', hence column cannot be dropped or renamed`）。
   迁移会先把这些 CHECK 从 `information_schema.check_constraints` 里读出来、摘掉，
   改完再装回去；列被彻底删掉的就**不**再装回。
2. **`RENAME COLUMN` 只改名字、不改类型**。v3 的 `dept` 是 `TEXT`、v5 的 `group_name` 是
   `VARCHAR(255)`，改名之后列定义与受控 DDL 对不上，`verifyCurrent` 会在**最后一步**拒绝标记完成
   （表现为「迁移明明做完了却不算成功」）。所以迁移末尾会按受控定义逐列 `MODIFY COLUMN` 对齐。
3. **`CHECK_CLAUSE` 里的字符串定界符是反斜线转义的**，拼回 DDL 之前必须还原，否则语法错误。
4. **受控 DDL 里的 `CREATE UNIQUE INDEX` 必须真的被执行。** 迁移器早先只认
   `CREATE INDEX`（受控索引的过滤与 `ensureIndex()` 的正则都把它跳过了），于是
   `provider_alias` 的 `idx_provider_alias_member`、`model_price` 的 `idx_model_price_span`
   在**任何迁移路径里都没被建出来过** —— 只有全新库的建库路径会把整段 DDL 一次执行。
   后果是「迁移出来的库」与「新建的库」在同一个版本号下**索引集不同**：
   SQLite 侧完全看不出来（本地只比对 `sqlite_master.sql` 全文，索引不在其中），
   而 MySQL 侧会在最后一步报「表 `provider_alias` 的唯一约束与主键不一致」——
   表现为「迁移明明做完了却不算成功」，且 `resume` 也救不回来。
   现在统一走 `isCreateIndex()` + `ensureControlledIndexes()`：它会扫**全部受控语句**
   （含 v6 / v7 的追加）补齐缺失索引并逐列核对。

另有一条**状态判定**的坑，会让库看起来「怎么 `resume` 都不行」：
v5 结构已经就位、但 v5 账本行被标成 `started` / `failed` 的库（迁移中途崩过就是这副样子），
**版本号已经是 5**。若按版本号判断「v4 基线还没做」，就会重跑 v3→v4，而那时 `dept` 早已改名
`group_name`，于是抛 `Unknown column 'dept'`，此后每一次 `resume` 都失败。
现版本改为认「v5 账本行是否存在」，遇到这种库直接 `resume` 即可 ——
**不要手工删表或改账本状态**。（`inspect` 回显的 `migration` 行还会依次回落到
v6 / v5 / v4 账本，好让你看到崩在哪一步；**判定「基线是否就绪」的依据仍然只是
「v5 账本行在不在」**，与版本号无关。）

一个已经迁到 v6 的库同样会被识别成**可迁移起点**（`legacy`），判据是
「v6 账本行完整**且**校验和等于冻结的 v6 摘要」，而不是「版本号等于 6」。
少了校验和这一步，一个被手工改过结构的 v6 库会冒充成「结构完好、只差一次纯追加迁移」，
一路升到 v7 且**没有任何一步会报错**，手工改动就被留在库里了。

先检查目标。MySQL 使用环境变量 `ATR_MYSQL_URL`，SQLite 则使用 `--db`（`inspect` 是默认命令，不触碰本地 `usage.sqlite`）：

```bash
node packages/server/dist/migrate-db.mjs inspect --db <portal.sqlite路径>
node packages/server/dist/migrate-db.mjs migrate --db <portal.sqlite路径> --confirm-offline
```

SQLite 会先生成一致性备份（`VACUUM INTO`）及 SHA256 清单；可通过 `--backup <新备份路径>` 指定位置。MySQL 必须提供已完成的真实备份文件、其 SHA256 和 `inspect` 输出的准确目标标签：

> ★ **唯一的例外：库里一条历史事件都没有时（`historyCount = 0`）不要求备份证明。**
> 典型是全新部署，或 v4 刚由空库建出来还没开始上报。备份的意义是「不丢唯一副本里的历史」，
> 对一份没有保护对象的库索要备份，只会把「空库初始化」这条最常见的路径卡死 ——
> 它恰恰是除 `--confirm-offline` 之外**不需要任何人工准备**的那条路。
> 只要 `usage_event` 里有一条事件，就必须按上面的要求提供证明。

```bash
node packages/server/dist/migrate-db.mjs inspect
node packages/server/dist/migrate-db.mjs migrate --confirm-offline --backup <备份文件> --backup-sha256 <SHA256> --backup-target <准确目标标签>
```

中途失败保留迁移账本，排除故障后使用相同参数运行 `resume`；不要手动删除表或伪造迁移完成状态。DDL 迁移与身份文件导入是两个步骤，结构完成后再导入原凭证：

```bash
node packages/server/dist/import-credentials.mjs --db <portal.sqlite路径> --credentials <旧credentials.json路径> --confirm-offline
# MySQL 去掉 --db，继续使用 ATR_MYSQL_URL。
```

只有显式添加 `--include-env-admin` 才会导入原环境管理员配置。导入先验证文件，再以事务写入；相同来源重复执行不会复制人员或 Token。原文件保留作备份，正常请求从此不读取它。

旧用量按原始姓名键保留为待确认历史归属，不按同名自动合并。管理员在“历史归属确认”中指定稳定人员 ID 并填写原因，审计记录与历史回填在同一事务完成。新上报直接记录服务端确认的人员 ID、凭证 ID、接收时间及当时的姓名/**分组文本快照**（`usage_event.group_name`）；之后改名或改分组归属都不会改变原始快照。注意分组归属的**权威**是关联表 `member_group_assignments`，快照不参与归属 —— 一条事件按人员当前所属的**每个**分组展开，所以各分组之和可能大于总量。

## 备份和验证

备份范围是整个部门数据库，包括身份表及用量表，不能只备份 `usage_event`。多人并发编辑使用版本号阻止覆盖，最后一个有效管理员入口受保护，数据库故障返回明确错误并由客户端保留待发记录。

可复跑的分阶段验证入口、数据库结构与尚未完成的人工验收记录见 [接口与验收](./数据库重设计-接口与验收.md)、[数据库设计](./数据库重设计.md) 和 [验证记录](./database-v4/验证记录.md)。发布仅走根目录 release 入口；本轮验收不会发布包。
