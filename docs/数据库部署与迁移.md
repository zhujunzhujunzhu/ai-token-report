# 数据库部署与迁移

部门服务端以 MySQL 为正式部署主库，SQLite 保留给本地部署及验证。人员、部门、角色、权限、登录账号、上报 Token、会话、验证码、限流、审计和历史身份映射均进入同一个 v4 部门数据库。本机 `usage.sqlite` 仍是可重建的日志索引，与部门库严格分离。

## 新部署

使用数据库管理员预先创建独立 MySQL 数据库和专用账号，编码为 `utf8mb4`，业务表使用 InnoDB。给专用账号授予这个库所需的建表、索引、查询和写入权限，不给其他业务库的权限。连接串通过部署系统的秘密配置注入 `ATR_MYSQL_URL`，密码中的保留字符需 URL 编码，不能把真实连接串写进仓库或日志。

首次启动配置：

| 变量 | 用途 |
| --- | --- |
| `ATR_MYSQL_URL` | 部门数据库连接串；不配置时使用 SQLite |
| `ATR_ADMIN_USERNAME`、`ATR_ADMIN_PASSWORD` | 空库初始化管理员登录账号；密码 12～128 个字符 |
| `ATR_ADMIN_NAME` | 管理员显示姓名，可选 |
| `ATR_ADMIN_TOKEN` | 可选的初始化管理 API Token；只需要网页登录时可以省略 |
| `ATR_CAPTCHA_HMAC_KEY` | 至少 32 个字符的随机秘密，所有实例使用同一值 |
| `ATR_PORTAL_ORIGIN` | HTTPS 反向代理对外地址，例如 `https://tokens.example.com` |

初始化值只对空库生效，后续数据库为唯一真值。停用的账号不会因环境变量还在而复活。初始化成功后可移除管理员初始化秘密；保留数据库和验证码密钥配置。

```bash
bun install
bun run build:portal
bun run --filter @ai-token-report/server build:node
node packages/server/dist/main.mjs --port 8787 --static packages/web-portal/dist
```

Node 入口与 Bun 共用相同路由及数据库实现，MySQL 走已安装的 `mysql2` 依赖。当前 Windows Bun 1.4.2 实测存在 MySQL `caching_sha2_password` 长密码认证问题，正式联调使用 Node 22.21.1；不要缩短密码或降低数据库认证强度。详情及官方问题链接见 [MySQL 上报库](./mysql上报库.md)。

SQLite 可直接 `bun run server -- --db <独立的portal.sqlite路径>`，同样需要初始化账号及验证码密钥。默认仅监听 `127.0.0.1`；配置好数据库身份后，再按部署需要设置监听地址及反向代理。

登录后台后先维护部门和人员，再为人员设置角色、登录账号或签发上报 Token。人员与 Token 分离，同一个人可以有多个独立凭证。默认上报 Token 仅有 `identity:read` 和 `usage:write`，不能读取全员看板。Token 明文只在签发或轮换成功时显示一次，库内只存摘要。

## 从旧版本迁移

**先备份并停止所有旧服务实例，再执行显式迁移。** 新服务看到 v3 库会拒绝启动；不会删库、重建或悄悄迁移。不要把员工机器上的 `usage.sqlite` 作为部门迁移目标。

先检查目标。MySQL 使用环境变量 `ATR_MYSQL_URL`，SQLite 则使用 `--db`：

```bash
node packages/server/dist/migrate-db.mjs inspect --db <portal.sqlite路径>
node packages/server/dist/migrate-db.mjs migrate --db <portal.sqlite路径> --confirm-offline
```

SQLite 会先生成一致性备份及校验清单；可通过 `--backup <新备份路径>` 指定位置。MySQL 必须提供已完成的真实备份文件、其 SHA256 和 `inspect` 输出的准确目标标签：

```bash
node packages/server/dist/migrate-db.mjs inspect
node packages/server/dist/migrate-db.mjs migrate --confirm-offline --backup <备份文件> --backup-sha256 <SHA256> --backup-target <准确目标标签>
```

中途失败保留迁移账本，排除故障后使用相同参数运行 `resume`；不要手动删除表或伪造迁移完成状态。DDL 迁移与身份文件导入是两个步骤，结构完成后再导入原凭证：

```bash
node packages/server/dist/import-credentials.mjs --db <portal.sqlite路径> --credentials <旧credentials.json路径> --confirm-offline
# MySQL 去掉 --db，继续使用 ATR_MYSQL_URL。
```

只有显式添加 `--include-env-admin` 才会导入原环境管理员配置。导入先验证文件，再以事务写入；相同来源重复执行不会复制人员或 Token。原文件保留作备份，正常请求从此不读取它。

旧用量按原始姓名键保留为待确认历史归属，不按同名自动合并。管理员在“历史归属确认”中指定稳定人员 ID 并填写原因，审计记录与历史回填在同一事务完成。新上报直接记录服务端确认的人员 ID、凭证 ID、接收时间及当时的姓名/部门快照；之后改名不会改变原始快照。

## 备份和验证

备份范围是整个部门数据库，包括身份表及用量表，不能只备份 `usage_event`。多人并发编辑使用版本号阻止覆盖，最后一个有效管理员入口受保护，数据库故障返回明确错误并由客户端保留待发记录。

可复跑的分阶段验证入口、数据库结构与尚未完成的人工验收记录见 [接口与验收](./数据库重设计-接口与验收.md)、[数据库设计](./数据库重设计.md) 和 [验证记录](./database-v4/验证记录.md)。发布仅走根目录 release 入口；本轮验收不会发布包。
