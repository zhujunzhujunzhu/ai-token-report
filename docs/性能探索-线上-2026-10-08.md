# 线上性能分析：为什么「全年」特别慢（2026-10-08）

> §1–11 是一次性**只读**实测；§12 起记录后续代码优化与部署，不能把整篇视为零写入。
> 原始探查数字来自线上 `117.72.173.21`（服务端产物 = 2026-10-08 18:06 那一版，
> pm2 `ai-token-server` 于 18:06 起、MySQL 8.0.40 于 17:38 起）。
> 探针脚本落在本机 `.artifacts/perf-2026-10-08/`，服务器侧只在 `/tmp` 放了两个只读脚本；
> **没有改任何配置、没有写任何数据**（SQL 全部是 `SELECT` / `SHOW` / `EXPLAIN ANALYZE`）。
>
> 为什么还要再写一篇：`docs/性能探索-线上-2026-10-04.md` 的结论是「默认视图亚秒级、剩下的是
> 30 天/全年的结构性成本」。今天复测确认**那半句结论仍然成立，而且数字又翻了 2.5 倍**
> （10-07 实测 `overview year` 2.6s → 今天 **6.7s**），原因不是又回归了，而是**表在 4 天里从
> 19.7 万行涨到 41.9 万行**，并且**金额那条逐事件查询**始终占住全年请求的绝大部分。

## 0. 结论速览

| # | 发现 | 实测证据 | 影响 |
|---|---|---|---|
| **1** | 🚨 **「全年」窗口 = 整张表**，而表今天又涨了一倍 | 41.9 万行 / 353MB（10-04 是 19.5 万行 / 103MB）；今天凌晨起 Codex 历史补录 **+22.1 万行** | 全年 = 40.4 万行；所有宽窗口成本随时长**线性**变差 |
| **2** | 🚨 **金额（估算）是全年请求的主要成本**：逐事件两次 `model_price` 索引查找 + 把巨型 `CASE`（高峰/闲时）放进 `GROUP BY` | `EXPLAIN ANALYZE`（全年 40.4 万行）：**总 6,055ms** = 扫描 381ms + 专属价查找 **1,060ms** + 基础价查找 **1,682ms** + 临时表聚合 **2,932ms**；无金额的同窗口聚合同口径只有 **1.0–1.9s** | 全年 `overview` 实测 **6.19s**、`by=user` **5.92s**；**去掉金额约 1.3s** |
| **3** | 🚨 **汇总表全程缺席**：`usage_rollup_*` 明明活着（日格 1,769 行、覆盖 03-18→10-08），却一条也接不住这部分流量 | 全年请求里 **74% 带 `source=dsh`**（`#rollupUsable()` 对来源筛选直接返回 false）；`member_id` / `provider` 等维度筛选被 `isTimeWindowOnly()` 拒；`overview` 与**所有** `breakdown` **根本没有汇总分支**；`series` 的条件是 `!withCost`，而查看者**有** `cost:read` | 三条路各自独立地禁用快路径，快路径一次都没被走到 |
| **4** | ⚠️ **一个客户端把「全年」当默认视图在轮询**：每轮 5 个请求、3 个是全窗口 `by=user`/`overview` 级聚合 | 3.6 天里 `period=year&source=dsh&member_id=2194c238…`（朱俊）**5 条 URL 各 2,812 次** = 1.4 万次；占全部全年请求 **74%**；当前仍在跑（最近 2,000 条 stats 请求里 **760 条是全年**） | 每轮约 **23 秒**服务端工作量；15 分钟负载均值 **2.28 / 2 核** |
| **5** | ⚠️ **一台 2 vCPU 机器 + 5 秒轮询 = 谁都被拖慢** | 单发 6.6s 的请求，16 路并发时 **26–30s**；最近 500 条 stats 请求 **平均 4,408ms、65.6% ≥1s、31.4% ≥5s**；`last7d` 单发 0.4–0.5s，但被抢时也到 1s | 「整体差」的观感 = 宽窗口 × 并发争抢，不是某一条 SQL 坏了 |
| **6** | ⚠️ **固定开销与目录都已经修好了**（10-07 那轮的成果，本轮复测确认） | `groups`/`members`/`providers`/`sources` **51ms**、401 闸门 **48ms**；`last7d` 四个请求一屏 **1.28s** | 日志里那四个目录 0.81–0.84s 的均值是**修之前**的历史段，别再当现状 |
| **7** | ⚠️ **buffer pool 快装不下了**：表+索引 353MB / 池 512MB，按 0.85KB/行 | `Innodb_buffer_pool_reads` 增量 0（现在还够）；约 **60 万行**（≈ 再涨 18 万行）就越界 | 越界后上面那些「内存里的索引查找」会变成磁盘读，6s 会再跳一个量级 |
| **8** | ⚠️ 可观测性仍脏：`slow_query_log=ON` 但 `log_queries_not_using_indexes=ON` | 今日 6.5 万条慢查询里 **76.6% 是闸门那几条 `information_schema`**（单条 3–17ms） | 真正的慢查询会被淹掉；建议关掉这个开关，只留 `long_query_time` |

**一句话**：慢的不是机器（CPU 空载时 1–3%、池命中率 ~100%），而是**「全年」请求本身要扫整张表、
并且为每一条事件算一次金额**；再叠加**一个客户端每 ~20 秒轮询一屏 5 个全年请求**，
在 2 核上把固定开销已经优化干净的那部分收益全吃掉了。

## 2. SQL 层归因：全年那 6 秒花在哪

`EXPLAIN ANALYZE` 直接跑**线上慢查询日志里那句真实的全年金额聚合**
（`WHERE ts >= 1767196800000`，即 2026-01-01 起，命中 403,866 行）：

| 节点 | 实测 |
|---|---|
| `Table scan on usage_event` + `ts` 过滤 | 381ms（40.4 万行） |
| `Index lookup on model_price using idx_model_price_span`（专属价，`provider=e.provider AND model=e.model`） | **1,060ms**（×403,866 次） |
| 同上（基础价 `provider='*'`） | **1,682ms**（×403,866 次） |
| `Aggregate using temporary table`（`GROUP BY grp_key, price_id, currency, price_slot`） | **2,932ms** |
| **合计** | **6,055ms** |

对照（同样全年、同样几十万行，但**不带金额**）：

| 查询 | 行数 | 实测 |
|---|---|---|
| `SELECT COUNT(*), SUM(4 列) … GROUP BY grp_key`（totals） | 374,581 | **1,026ms** |
| `SELECT CONCAT(provider,'/',model) … GROUP BY`（无金额分布） | 374,576 | **1,944ms**（其中 `Sort` 1.6s + `Group aggregate` 1.9s） |

⇒ **金额那套东西给全年窗口加了大约 4 秒**（两次逐事件索引查找 2.7s + 被 `CASE` 撑大的
临时表聚合），占 6.0s 的 ~2/3；而 `overview?year` 端到端 6.19s ≈ 就是这一条查询的墙上时间
（服务端已经把子查询并发发了，所以墙上 = max，不是 sum）。

> 那句 `CASE` 是 `slotExpressionSql()` 生成的高峰/闲时判定（`DIV 86400000` / `% 1440` 那一串整数算术），
> **它是 `GROUP BY` 键的一部分**，所以每行都要算一次、还要进临时表的键。

## 4. 「谁在轮询全年」—— 一条固定形态的 5 请求轮次

统计页 `StatsLayout.vue` 每 **5 秒** `dashboard.load(true)`（`document.hidden` 或上一轮
没回来时跳过）。`overview` 区块且**选了人员**时，一轮发出 **5 个请求**：

```
overview?identity_view=member&period=year&source=dsh&member_id=<ID>
series?identity_view=member&period=year&source=dsh&member_id=<ID>&bucket=day
breakdown?identity_view=member&period=year&source=dsh&member_id=<ID>&by=user
breakdown?identity_view=member&period=year&source=dsh&member_id=<ID>&by=group
breakdown?identity_view=member&period=year&source=dsh&by=user          ← 不带人员的「候选」
```

这五条在日志里**各出现 2,812 次**（完全同步），`member_id` 全部是
`2194c238-f1be-4d8a-996d-73b83cefd457` = **朱俊**（全库 17.7 万条事件、占 42% 的那个人）。
全年请求里 **74% 带 `source=dsh`、63% 带这个 `member_id`**。

折算：3.6 天 2,812 轮 ≈ 平均 **110 秒一轮**，最近约 **20 秒一轮**（一轮墙上十几秒 +
`pending` 互斥）。按今天单发的实测值算，**一轮 ≈ 6.2 + 1.5 + 5.9 + 2.0 + 5.9 ≈ 21.5 秒**
服务端工作量 —— 在 2 核机器上，**这就已经是「一台核被一个人的一个页面长期占满」**。

⚠️ 其中 `breakdown?…&by=user`（不带人员）**只为候选**而取：按 `AGENTS.md`，人员候选的
主来源本该是 **`/api/v1/stats/members`（51ms 的名册）**，用量聚合只是名册取不到时的回落。
现在这条**全窗口金额聚合**在一轮里被算了两遍（一遍当候选、一遍当排行），
而候选那份的数字在「已选人员」的分支里根本不用。

## 5. 为什么汇总表救不了它

三张汇总表活着且在推进（`usage_rollup_day` 1,769 行 / `usage_rollup_hour` 2,197 /
`usage_rollup_hod` 1,909，日格覆盖 2026-03-18 → 2026-10-08），但：

1. **来源**：`usage_rollup_*` 的键里没有 `source` 列，`#rollupUsable()` 见到
   `filter.sources` 就 `return false`（显式判掉，不靠异常）。而全年请求 **74% 带 `source=dsh`**。
2. **维度**：`isTimeWindowOnly()` 要求筛选里**只有时间窗**；`member_id` / `group_id` /
   `provider` / `model` 任一个都会让它退原始表。上面那条轮询**同时**带了 `source` 与 `member_id`。
3. **金额**：`series` 的汇总快路径要求 `!withCost`；查看者有 `cost:read` ⇒ 又一条禁用。
4. **根本没有分支**：`overview`（totals / sessions / 未归属）与**所有** `breakdown`
   都没有汇总分支 —— 它们从来只走原始表。

⇒ 也就是说：**「按来源看全年」这种最主流的组合，恰好是汇总表唯一接不住的组合。**

## 8. 结论：按影响排序的五个原因

1. **窗口粒度 = 全表扫描，且表在暴涨**（41.9 万行、还在被历史补录推高）。
   全年 = 100% 的行，上月 = 47% 的行。任何「优化」都必须先把这部分行数降下来。
2. **金额逐事件算**：两次 `model_price` 索引查找 + 每行算高峰/闲时 `CASE` 并把它放进
   `GROUP BY` 键 ⇒ 全年查询 6.0s 里约 4s 是它。**这条是可优化的**（见 §9-C）。
3. **为此建的汇总表结构上接不住**：缺 `source` 维、维度筛选不退、带金额不退、
   `overview`/`breakdown` 没分支。四条里**任何一条**都足以让快路径失效，现在是四条同时成立。
4. **前端把宽窗口当默认视图每 5 秒轮询**，一轮 5 个请求、其中两个是同一个全窗口金额聚合；
   实测**一个客户端 = 全部全年请求的 74%**。在 2 核上，它直接决定别人的 `last7d` 是 0.5s 还是 1s。
5. **只有 2 vCPU**：并发争抢系数 ~4×（6.6s → 26–30s），所以「一个人用全年」会表现为
   「全公司都慢」。

## 9. 建议（按「投入 / 收益」排序）

| 档 | 动作 | 预期 |
|---|---|---|

### 13.1 实现与正确性边界

- `overviewCountsQuery()` 把概览的四项 token、调用数、去重会话数、未归属调用数合成一次
  事实表扫描，金额仍独立按价格桶计算。未归属条件继续区分成员视图与旧视图。
