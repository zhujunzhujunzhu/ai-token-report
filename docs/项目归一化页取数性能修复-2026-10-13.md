> 起因：线上 `/ai-token/#/projects`（部门看板「项目归一化」）使用者反馈**非常卡顿**。
> 本篇是只读实测 + 两处改动的记录。原始输出：`.artifacts/projects-page-perf-2026-10-13/`
> （探针 `online-projects-bench.mjs`，走 `packages/server/verify/perf/runtime-ab/ssh-exec.mjs`
> 上传到服务器 `/tmp` 后在**服务端本地**打请求，只读 GET + SELECT）。

## 0. 结论

卡的不是渲染，也不是规则列表，而是**首帧并发里那份「下拉候选」**：

| 请求（首帧三个一起发） | 线上实测（服务端本地） | 响应体 |
|---|---|---|
| `/api/v1/stats/projects` —— 表单里那个「仓库名 / 目录前缀」的候选项 | **692ms**（min 655 / max 697） | **51.7KB**（997 个目录） |
| `/api/v1/admin/project-aliases` —— **列表本身**（105 条规则） | 37ms | 25.0KB |
| `/api/v1/stats/members` —— 人员名册（只服务表单的「成员」下拉） | 35ms | 4.2KB |
| 对照：`/stats/groups` / `/stats/providers` | 37 / 35ms | 0.6 / 0.3KB |
| **首帧三个请求并发墙上时间** | **709 / 726 / 793ms** | — |

三者由 `Promise.all` 一起等，于是**首帧、以及每次「刷新 / 保存 / 删规则」后的重取**
都被一份「填起来方不方便」的候选值拖住半秒以上（线上 2 核被并发争抢时更长，
见 [线上性能分析 2026-10-08](性能探索-线上-2026-10-08.md) 的争抢系数）。

### 0.1 SQL 层：这 692ms 是什么

```sql
SELECT DISTINCT cwd FROM usage_event WHERE cwd IS NOT NULL ORDER BY cwd
```

| 项 | 实测（2026-10-13） |
|---|---|
| `EXPLAIN` | `type=ALL`，`rows=540412`，`Using where; Using temporary; Using filesort` |
| 耗时中位（3 次） | **774ms**（首跑冷 **3301ms**） |
| 表规模 | `usage_event` **504,542 行**；不同 `cwd` **997** 个；`project_alias` 105 行 |
| `usage_event` 上的索引 | `ts` / `(member_id,ts)` / `session_id` / `provider` / `model` / `source` / `user_id` / `report_token_id` / `(ts,seq,event_id)` —— **没有 `cwd`** |

`cwd` 是 `TEXT`：**前缀索引救不了 `DISTINCT`**（2026-10-04 实测 `cwd(64)` 前缀索引
仍 `Table scan`，`DISTINCT cwd` 反而 304→320ms，见
[线上性能探索 2026-10-04](性能探索-线上-2026-10-04.md) §「索引」）。

## 1. 改了什么

### 1.1 看板：候选从「首帧」挪到「打开表单」（`packages/web-portal/src/views/ProjectsView.vue`）

- `load()` 只再取**规则列表**一个请求（37ms）；候选（目录 + 人员名册）改由 `open()` 触发的
  `ensureCatalog()` / `ensureRoster()` 去取，**读过就留在本次页面驻留期内复用**；
- 「刷新」按钮对**已经读过**的候选顺带重取一次（不阻塞列表），没读过就不取 —— 那正是要避免的全表扫；
- 表单里的文案分三态：**正在读 / 读到了（报个数）/ 没读到（缺权限或失败）**。
  ⚠️ 把「正在读」说成「读不到目录候选（需要 `stats:read`）」会让人去查一个不存在的权限问题。

### 1.2 服务端：候选加 2 分钟进程内缓存（`packages/server/src/stats-route.ts`）

- 键 = `applyDataScope()` **已经算好的 filter**（逐字段排序后序列化）。
  🚨 这是**安全边界**：同一份目录对「部门视角」与「只看自己」是两个答案，键错了就是
  把别人的目录名发给只看自己的人，而响应看起来完全正常；
- 只缓存**成功**结果（把失败的空清单缓存 2 分钟会看起来像数据丢了）；
- 命中时**连库都不开**；过期顺手删键，上限 64 个（线上键数 = 1 + 非管理员人数）。

`e2e-admin.ts` 里新增三条断言钉住这件事：①甲看不到 `D:\b-only`；②换一个人就换一份候选
（乙看得到自己那份 `D:\b-only`，也有与甲同目录的 `D:\proj\packages\core`）；③同一范围的
**第二次**请求走缓存命中，内容与第一次逐字相同（这一条是**命中路径**唯一的覆盖）。

## 3. 还留着的**结构性**成本（刻意没在这一轮动）

| 项 | 现状 | 为什么没动 / 后续怎么做 |
|---|---|---|
| `DISTINCT cwd` 全表扫 | 774ms，随表**线性**增长（10-04 是 206,531 行 / 228.9ms → 10-13 是 504,542 行 / 774ms） | 修它要动 schema：①把 `cwd` 从 `TEXT` 改成 `VARCHAR(512)` 才能建**可覆盖**的索引（改列类型 = 线上表重建，最重的一档）；②或建一张「目录清单」小表（`(cwd, member_id)`），在**入库事务**里 upsert、迁移时一次性回填。两者都要走一次 `PORTAL_SCHEMA_VERSION` 升级与两后端迁移用例 |
| 缓存 TTL 内的陈旧 | 新出现的目录最多 2 分钟不进候选 | 候选可以手填，且表单里说明；比「每来一个人扫一遍全表」划算 |
| 表单下拉一次渲染 997 个 `el-option` | 打开表单时的一次性成本（百毫秒级） | 真要再快就换 Element Plus 的虚拟化 `el-select-v2`；这一轮的卡顿不在它（打开表单才会渲染） |
| 冷进程里**第一次打开表单**仍要等 ~692ms | 之后 2 分钟内都是缓存命中（0ms 开库） | 想连第一次也秒开，可以在列表渲染后**空闲时预取**一次候选（仍不进关键路径）。刻意没默认开：这一页的访问次数远多于「打开表单」的次数，惰性取数对 2 核的库里更省 |
| 全站并发争抢 | 与这一页无关：一个客户端把「全年」当默认视图在轮询（见 10-08 那篇） | 那是**部署/客户端**问题，不在这一页的预算里 |

## 4. 「###东站系统」这类名字是怎么回事

线上两条规则的匹配值与归一化名都是 `###东站系统` / `###申迪项目`，看着像正则语法糖。
真相是**目录名本身就叫这个**（`D:\###东站系统`、`D:\###申迪项目`，
还有 `D:\EV录屏\Desktop\###资管\代码原型\suit-jyzg-product`）。

- **匹配不是正则**：`prefix` 只有两种写法，靠「含不含路径分隔符」区分 ——
  **仓库名**（不含分隔符）＝ cwd 的任一路径段**逐字全等**；**路径前缀**（含分隔符）＝
  整条路径按分隔符边界前缀匹配。都是字面量比较，没有任何正则（唯一实现：
  `packages/core/src/db/project-alias.ts`）；
- **`###` 只在匹配值里必需**（要跟真实目录名逐字相同才能命中），
  **归一化名（`alias`）是自由文本** —— 去掉 `###` 立刻在看板上生效，不动历史数据；
- 这两条是 2026-10-13 那批 105 条规则里「别名沿用目录名」的产物（见
  [online-project-rules skill](../.agents/skills/online-project-rules/SKILL.md) §6.3），
  82 条新项目的**业务中文名**同样留待人工拍板 —— 改 `alias` 一条即可。
