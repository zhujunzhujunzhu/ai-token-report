# 部门前端重构

## 业务梳理

部门前端 `packages/web-portal` 展示全员已经上报的数据；它与只看本机日志的
`web-local` 是两个独立应用。服务端接口与上报链路保持现有契约。

| 业务 | 使用者 | 数据 / 操作 | 页面 |
|---|---|---|---|
| 身份登录 | 已开通登录账号的成员 | 用户名 + 密码 + 图形验证码，取得服务端姓名、部门、角色 | 登录 |
| 部门概况 | 全部成员 | 总量、命中率、调用、会话、平均调用、未署名占比、人员排行 | 用量总览 |
| 用量分析 | 全部成员 | 时间趋势，按厂商、模型、项目分组，人员下钻 | 用量分析 / 人员详情抽屉 |
| 调用追溯 | 全部成员 | 服务端分页的事件明细 | 调用明细 |
| 采集检查 | 全部成员 | 未署名事件、数据时间边界、最近上报 | 采集诊断 |
| 账号与凭证管理 | 管理员 | 开通登录、重置密码、发放上报 Token、角色调整、重置与吊销 | 人员管理 |

登录使用用户名、密码和一次性图形验证码。上报 Token 保留供 CLI / 插件使用，
不会被当作密码。身份与权限只采信服务端凭证表；缺少角色按普通成员处理。
管理接口继续由服务端鉴权，前端路由守卫只负责导航体验。

## 页面与工程拆分

- `router/`：Hash 路由、懒加载页面、登录与管理员守卫；兼容现有静态托管。
- `layouts/`：桌面侧栏、移动端导航、面包屑和身份菜单。
- `stores/session.ts`：会话恢复、登录、退出、权限与过期提示。
- `stores/dashboard.ts`：共享筛选、按页面取数、轮询、分页、过期响应隔离与人员详情。
- `stores/members.ts`：只在管理员页面取人员数据，退出清理凭证列表，业务失败保留表单。
- `api/`：同源 Cookie 请求与接口契约；不参与排版。
- `components/`：Element Plus 表单、表格、分页、反馈、抽屉；Chart.js 趋势图。
- `views/`：五个业务页面与登录页，组合组件，不重算指标。
- `styles/`：统一浅色主题、青蓝强调色、留白、响应式布局。

使用 Vue 3 + TypeScript + Vue Router + Pinia + Element Plus。
Element Plus 显式导入所需组件，样式在入口统一加载；三个 Store 分文件组织。
参考：[Element Plus](https://element-plus.org/en-US/guide/quickstart)、
[Pinia](https://pinia.vuejs.org/core-concepts/)、
[Vue Router](https://router.vuejs.org/guide/essentials/history-mode)。

## 必须保持的行为

1. 未登录不请求统计与人员接口。401 清理会话，403 显示无权限，503 显示服务端未就绪。
2. 每次恢复会话都向服务端验证；浏览器不保存可信角色。
3. 退出或切换身份时清空统计及凭证列表，忽略上一会话的迟到响应。
4. 人员候选从同窗口、不带人员筛选的查询取回，精确多选不会自锁。
5. 具名周期交由服务端解析；自定义范围只传 from/to，不混传 period。
6. 所有用量及派生指标只展示服务端结果，不展示金额，不在前端合计或重算口径。
7. 空态、首次加载、更新失败、无权限明确区分。轮询失败保留旧数据并提示。
8. 删除 / 重置凭证需在页面确认；环境变量凭证不可编辑，最后管理员护栏以服务端为准。
9. 诊断中的恒等式恒为零是存储结构保证，不渲染为一次真实的数据校验成功。

## 登录服务拆分

- `server/src/auth/password.ts`：使用 [@noble/hashes](https://github.com/paulmillr/noble-hashes) 的 scrypt（N=32768、r=8、p=1），每次随机盐。密码 12～128 字符；归一 BOM / CR，不 trim 密码。
- `auth/captcha.ts`：随机四位数字，纯 PNG 位图；响应不含答案、SVG 或文本元数据，不需要 native canvas。
- `auth/portal-auth.ts`：验证码绑定 HttpOnly Cookie，2 分钟有效，每次提交后作废。使用 [rate-limiter-flexible](https://github.com/animir/node-rate-limiter-flexible) 限流：每账号 15 分钟 5 次密码尝试、全局每分钟 60 次登录 / 120 次验证码，KDF 最多并发 4 个。
- `app.ts`：唯一 HTTP 分发，使用 [hono/cookie](https://hono.dev/docs/helpers/cookie)。新增 GET `/api/v1/auth/captcha`、POST `/auth/login`、GET `/auth/session`、POST `/auth/logout`（后三者同样位于 `/api/v1`）。
- `member-admin.ts`：账号设置仍走原子落盘后更新内存的唯一写通路。POST `/api/v1/admin/members/login` 接收 token（成员定位）、username、password；不返回哈希或密码。

登录会话为服务端随机标识，8 小时绝对有效期；Cookie 为 HttpOnly + SameSite=Strict，HTTPS 下加 Secure。页面不再保存 Token / 密码到 localStorage，并清除旧版本保存的 Token。
角色每次请求重读；密码变更、账号变更、凭证吊销或 Token 重置都会使对应旧会话失效。服务端重启也会清除会话。后台 POST 要求同源和 `X-Portal-Request: 1`；原 Bearer API 兼容现有客户端。

## 首次部署与已有数据迁移

没有默认用户名或默认密码。首次使用需在服务进程的环境中配置：

| 环境变量 | 用途 |
|---|---|
| `ATR_ADMIN_TOKEN` | 部署管理员的独立随机上报凭证，沿用已有冷启动机制 |
| `ATR_ADMIN_USERNAME` | 登录用户名，3～64 位字母、数字、点、下划线或连字符，首位字母 / 数字，不区分大小写 |
| `ATR_ADMIN_PASSWORD` | 登录密码，12～128 字符，由部署环境注入 |
| `ATR_ADMIN_NAME` | 可选显示名，默认「管理员」 |
| `ATR_PORTAL_ORIGIN` | HTTPS 反向代理部署时填写公开源，例如 `https://tokens.example.com`；用于同源验证及 Secure Cookie |

配置后执行 `bun run build:portal`、`bun run server`。以部署账号登录，在「人员管理」添加成员后继续设置登录；旧成员点击「设置登录」即可开通，不改历史归属与上报 Token。用户名需唯一。密码无法查看；遗忘时管理员重置。

环境变量管理员不落文件，也不能在页面修改；在部署环境更换密码后重启。文件账号新增可选 `username` / `passwordHash`，既有格式照常解析。旧 Token 仍可用于上报，但未开通账号的成员不能密码登录。不要把明文密码写入 credentials.json。

会话与验证码存于当前服务进程内，适合当前单进程部署；多实例部署需共享会话 / 验证码 / 限流存储，当前不支持随机分流。

## 登录验收

```bash
bun test packages/server/test/portal-auth.test.ts packages/web-portal/test
bun run packages/server/verify/verify-login.ts
bun build packages/server/verify/verify-login.ts --target=node --outfile=.bun-cache/verify-login.mjs
node .bun-cache/verify-login.mjs
bun run packages/server/test/e2e-admin.ts
bun test packages/server/test/http-contract.test.ts
```

双运行时 HTTP 验收使用隔离的临时凭证与验证码工厂，不为生产接口增加任何测试绕过参数。
