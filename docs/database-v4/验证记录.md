## 实际执行方式

```bash
bun run packages/server/verify/verify-database-design.ts
```

脚本读取 `ATR_MYSQL_URL`，但控制连接固定使用 `information_schema`，不会进入 URL 原来指定的业务库。它生成 `atr_v4_verify_<时间>_<随机后缀>`，只在本次成功创建的 schema 中执行 MySQL DDL 与测试，最后只删除该随机 schema。SQLite 使用独立临时文件，并保留结果数据库供检查。数据库不可连接、建库失败或清理失败都返回非零退出码。

本机默认开发账号可以连接 MySQL，但没有 `CREATE DATABASE` 权限，第一次真实执行明确失败，没有跳过 MySQL。最终成功运行使用已有开发容器 `local-database-review-mysql` 的管理凭据，只在内存中读取并传给验证进程；未输出密码，未扩大普通开发账号的权限，未修改业务 schema。其他机器需提供可创建、删除隔离 schema 的测试连接；这不是正式应用运行账号的权限要求。

严格类型检查使用临时配置继承 `packages/server/tsconfig.json`，仅将 `packages/server/verify/verify-database-design.ts` 加入 `include`，通过现有 TypeScript 执行 `--noEmit`。生产 tsconfig 和 package.json 均未修改。

## 覆盖内容

- 两份 SQL 在真实引擎中创建 17 张表，种入两个角色、12 项权限及身份锁单例。SQL 不包含 `ALTER` / `DROP`，不创建管理员账号，也不伪造迁移完成记录。
- 人员 UUID、部门外键、状态约束、用户名唯一、一人一个账号、角色关系唯一、Token 摘要唯一、过期时间及安全整数约束。
- 管理员新上报 Token 只得到显式填写的两项 scope；scope 与人员当前角色权限取交集，不能越权。
- `report_tokens.version` 默认 1；轮换递增版本，旧版本 CAS 更新失败。轮换不修改旧事件，也不使独立的后台会话失效；修改账号密码版本使旧会话校验失败。
- 挑战答案以随机部署密钥生成 HMAC，并绑定挑战 ID；浏览器 binding 只保存摘要。验证码第一次 CAS 消费成功，第二次失败；同一限流主体只有一个桶。
- `event_id` 去重保留首条记录及四个独立 token 列。改名、轮换 Token 后，原始事件整行保持一致；使用不属于该人员的 Token 写事件会被复合外键拒绝。
- 历史人员、Token 和部门引用阻止物理删除；业务写入与成功审计一起回滚。
- 存在同名人员时，历史映射仍可以保持 `pending` 且 `member_id` 为空，不自动合并。
- 两条独立数据库连接并发执行原型降级事务，通过身份锁单例串行判断，最终保留一个可登录的管理员。此探针使用测试内的事务函数，**不表示应用已经实现完整最后管理员护栏**，也不是多个服务进程的 HTTP 测试。

## 双库边界与后续要求

MySQL 目标明确为 8.4，文本使用 `utf8mb4_0900_bin` 的精确、NO PAD 比较。已验证大小写和尾空格不同的事件键在两个引擎中分别保留。原始事件键不在数据库内 trim；HTTP 层现有归一规则另行保留。

MySQL 用 `CHAR_LENGTH`，SQLite 用 `length` 检查文本容量。已验证中文与 emoji 的 32 字符人员名、64 字符部门名以及超限拒绝。数据库按 Unicode 字符计容量；应用仍须复用既有 `validateName` 的 **32 个 UTF-16 单位**约束，两者不能混为一谈。

`usage_event` 保留空 `provider` / `model` 和负 `turn` / `step`，真实兼容用例已通过。事件键容量上限统一为 255 字符；旧 SQLite 中超过目标容量的存量必须在迁移预检中报告并阻止迁移，不能截断、丢弃或改写。

数据库摘要列只检查 64 位十六进制形状，不能独立证明调用方真正做过哈希。验证确认本次造数中的原 Token、session、binding 与 HMAC 密钥没有出现在数据库行中；生产应用仍须正确计算摘要，并对审计元数据做字段白名单处理。

`password_hash` 当前容量/格式约束针对现有 `$atr-scrypt$1$` 编码。未来更换 KDF 或编码版本，需要显式调整 schema 与应用验证，不能悄悄写入不兼容格式。

迁移表包含 `last_completed_step` 和 `checkpoint_json`。原型验证只在 catalog 查询确认隔离库表可用后写入本次 DDL 校验和与完成状态；原型阶段没有实现 MySQL 逐 DDL 恢复、失败注入、旧库逐字段对账和 `ingest_run` 迁移。后续运行时落地结果见下文。

## MySQL 长密码认证故障定位

Bun 1.4.2 / MySQL 8.4.9 / `caching_sha2_password` 的 24 个独立新账号首次认证组合实测：16、19 字符均成功；20、32、64、128 字符均失败 1045，四种构造参数入口一致。真正 Node v22.21.1/mysql2 的相同 64 位随机十六进制密码首次认证成功；先用 Node 登录不能修复 Bun。结果与 [Bun 官方 issue #26195](https://github.com/oven-sh/bun/issues/26195) 一致。

保留强密码及原认证策略，MySQL QA 采用 Node/mysql2。运行时仅在 Bun 实际 1045 且密码超过 19 字符时追加排障提示，不提前拒绝、不自动切换驱动。真实故障提示验证 21 次断言通过，包含 get/transaction/withConnection、原 cause 保留、短错误密码保持原错误和无秘密泄露。修改后 core typecheck、方言 16 项/53 次断言、真正 Node 双库基础层 14 次断言通过。

矩阵、首次登录顺序和所有本次随机库/账号清理状态已脱敏保存于 [mysql-auth-diagnosis.json](mysql-auth-diagnosis.json)。未改动 root 账号、全局认证策略、既有 QA 库或 `ai-token`。
