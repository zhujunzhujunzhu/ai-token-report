# 线上服务器性能探索（2026-10-04）

> 一次性**只读**探查：主机资源 → 服务端进程 → MySQL 全库 → 看板取数 SQL → 每请求开销。
> 所有结论都来自线上 `117.72.173.21` 的实测，脚本落在 `.artifacts/perf-explore/`。
> 全程**没有写入任何数据、没有改动任何配置**（`online-probe.ts` 的只读闸门 + 只用 `SELECT`）。

---

## 0. 结论速览

| # | 发现 | 实测证据 | 影响 |
|---|---|---|---|
| **1** | 🚨 **每个 API 请求固定打库 ~42 条 SQL**，与端点、与是否鉴权通过都无关。真业务查询只有 1 条 | 45 次 401 → +1893 条（42/次）；20 次候选目录 → 843 条（42/次）；20 次静态 → +3 | **第一瓶颈**。一个看板约 9 个请求 ⇒ **~380 条语句 / 次渲染**；那 ~50ms/请求的"固定开销"就是它 |
| **2** | 🚨 **汇总表被最主流的查询绕过**：`usage_rollup_*` 的键里**没有来源列**，而线上请求几乎都带 `source=dsh` | `portal.ts:681` 显式提前返回 false；`overview` / 所有 `breakdown` **根本没有 rollup 分支** | 花大工程做的 v8/v12 三张汇总表，对真实流量**几乎无效**（仍在每 5 分钟白维护） |
| **3** | 🚨 **今天数据量暴涨 3.75×**：Codex 历史日志在凌晨 02–03 点被批量补录 **13.7 万条**（占全表 **69%**），表从 5.2 万 → **19.5 万** | `received_at_ms` 分布：02 点 91,998 条 + 03 点 45,754 条 | 把下面所有取数成本整体推高约 **3–4 倍**；且这批是**历史数据**，任何"年"窗口都吃满 |
| **4** | ⚠️ **`source` 与 `cwd` 两列没有索引** → 全表扫描 | `EXPLAIN`：两者均 `type=ALL` + `Using temporary`；实测 87ms / 229ms | "来源目录""项目目录"两个候选端点随数据量**线性变差** |
| **5** | ⚠️ 重聚合查询在 30 天窗口下已达 **66–330ms** | 见 §5 表 | 与 10-01 基线（52K 行时 20–80ms）相比劣化 ~3–4× |
| **6** | ⚠️ 主机**内存偏紧**：4GB 总内存，available 仅 **772MB**，swap 已用 **451MB** | `free -m`、`vmstat` | 目前够用（buffer pool 命中率 ~100%），但这是**最先到顶**的资源 |
| **7** | ⚠️ **可观测性缺口**：`slow_query_log=OFF`、`long_query_time=10s`、`performance_schema` 语句摘要为空 | `SHOW VARIABLES`；摘要表 0 行 | 真出问题时**没有任何慢查询证据可查** |
| **8** | ⚠️ 请求日志无轮转：`ai-token-server-out.log` **21.8MB / 28.6 万行**，每请求写 2 行 | `ls -la`、`wc -l` | 运维卫生问题，非性能瓶颈 |

**一句话**：现在**不慢在机器上**（CPU load 0.32/2 核、磁盘 29%、buffer pool 命中率 ~100%），
慢在**每次请求都把同一份 schema 闸门重跑一遍（×42 条）**，而且**该救命的汇总表因为缺一个 `source` 维度而全程缺席**。
叠加今天 3.75× 的数据暴涨，单次看板取数已经从"几十毫秒"变成"**约 1.0–1.5 秒**"。

## 3. 今天到底发生了什么：3.75× 的数据暴涨

`received_at_ms` 按小时分布（近 24h）：

```
2026-10-04 03   45,754   ← 批量补录
2026-10-04 02   91,998   ← 批量补录（合计 137,752 条）
2026-10-04 01      227
2026-10-04 00      428
2026-10-03 23      881
2026-10-03 22      652
...（其余小时 100~900 条）
```

- 按**接收时刻**看：10 月入库 143,630 条，其中 **95.9% 集中在今天凌晨 2–3 点**。
- 按**事件时刻**看：`codex` 的 13.5 万条落在 4–9 月。
- ⇒ 一次**历史日志批量导入**（Codex 来源），把表从 5.2 万撑到 19.5 万。

`source` 维度带来的无索引扫描（见 §5.3）。

## 4. 瓶颈一（结构性）：每请求 42 条 SQL，全是 schema 闸门

### 4.1 实测

| 实验 | 请求数 | `Queries` 增量 | 每请求 |
|---|---|---|---|
| `/api/v1/stats/overview`（**无 token，401**） | 45 | +1,893 | **42.1** |
| `/api/v1/stats/groups`（候选目录） | 20 | +843 | **42.2** |
| `/api/health` | 20 | +861 | **43.1** |
| **静态首页 `/`** | 20 | +3 | **0.15**（背景噪声） |

⇒ **只要进 `/api/*`，就固定 ~42 条 SQL**。HTTP 层耗时（`curl` 视角）：

```
/api/health                  200   total 0.050s   ttfb 0.049s
/api/v1/stats/overview(401)  401   total 0.054s   ttfb 0.054s
/                            200   total 0.001s   ttfb 0.001s   ← 静态
```

**那 ~50ms 的"固定开销"＝ 42 次往返 MySQL。** 本地回环单次 ~1.2ms × 42 ≈ 50ms，完全吻合。

### 4.2 42 条 SQL 是怎么来的（代码侧）

`ensurePortalReady()` 每次都**重读真实结构**（刻意不缓存，见其注释：运行中改结构要立刻拒绝），
而 `verifyCurrentMysql()` 的语句数**随表数增长**：

```
5 条全库批量目录（tables / columns / statistics / foreign keys / …）
+ 27 条 CHECK —— 每张表 1 条（本库实测 27 张表）
+ 1 条 event_id 排序规则
+ readPortalState（版本状态）
≈ 35–42 条 / 次 openPortalStore()
```

> ⚠️ 文档里"19 张表 116 条 → **5 条**"的说法**不完整**：CHECK 那一段仍是**每表一条**循环
> （`portal-migrations.ts:476-481`，注释也承认"20 张表各查一次仍然比全库一次快"）。
> 随着表数从 19 涨到 27，闸门语句数也一起涨。

**鉴权路径也开库**：`stats-route.handle()` 第 1 步 `authorizeDatabase()` 会调
`IdentityRepository.isRegistered()` / `resolveBearer()`，而 `repository.ts:47` 就是
`await openPortalStore(this.target)` —— 所以**连 401 都要跑一遍闸门**。
一个通过鉴权的看板请求，从鉴权到取数可以开到 **2–4 次** `openPortalStore()`。

### 4.3 放大效应：一个看板 ≈ 380 条语句

线上日志（近 3000 行）里，一次看板渲染会连发：

```
overview  + series  + breakdown?by=user + breakdown?by=group
+ groups + members + providers + sources (+ projects)
≈ 9 个请求
```

⇒ **9 × 42 ≈ 378 条 SQL / 次页面刷新**，其中真正的业务查询只有 9 条。
**96% 以上的 SQL 是闸门。**

## 5. 瓶颈二（结构性）：汇总表在最主流查询上被绕过

本仓有 v8/v12 的三张汇总表（`usage_rollup_day` / `_hour` / `_hod`），并且**确实在增量维护**：

| 表 | 行数 | 覆盖 |
|---|---|---|
| `usage_rollup_day` | 326 | 2026-04-07 → 10-04（全量） |
| `usage_rollup_hour` | 653 | 2026-09-04 → 10-04（近 30 天） |
| `usage_rollup_hod` | 515 | 全历史折叠 |

水位 `built_through = 2026-10-04 11:31:57`（**近实时**），与原始表只差 17 条。
日志里也能看到 `[rollup] 定时补齐：incremental，日格 2 / 小时格 2 / 时段格 2`。

**但它读不到。** `portal.ts` 里 rollup 快路径只挂在两个地方，且带三道安全阀：

| 位置 | 条件 | 结果 |
|---|---|---|
| `overview`（totals/sessions/…） | **没有 rollup 分支** | 永远走原始表 |
| 所有 `breakdown`（by=user/group/provider/model/project/day/hour） | **没有 rollup 分支** | 永远走原始表 |
| `series()`（`portal.ts:1092`） | `!withCost` **且** `#rollupUsable()` | 有条件命中 |
| `hourOfDay()`（`portal.ts:763`） | `#rollupUsable()` | 有条件命中 |

而 `#rollupUsable()` 里有一条**显式提前返回**（`portal.ts:672-681`，注释原文）：

> 🚨 **按来源筛选/分组时必须退原始表**：`usage_rollup_*` 的键是
> `(day_key, hour_of_day, member_id, provider, model)` —— **没有来源列**。

```ts
if ((this.#filter.sources?.length ?? 0) > 0) return this.#rollupState   // = false
```

**线上日志里 `source=dsh` 是绝大多数请求都带的参数**（例如
`/api/v1/stats/overview?identity_view=member&period=year&source=dsh&member_id=…`）。
再加上该请求同时带 `member_id=`（`#rollupSeries` 要求 `isTimeWindowOnly`），
以及查看者是管理员（很可能有 `cost:read` ⇒ `withCost=true` 直接短路）——
**三条路全断**。

> ⇒ 结论：**汇总表当前对真实流量基本无效**，却仍在每 5 分钟做一次写入维护。
> 这不是"白做"（口径已被测试钉住、阈值到了就能用），但**现在是纯成本没有收益**。

### 6.1 EXPLAIN：两个真正的索引缺口

| 查询 | 计划 | 结论 |
|---|---|---|
| `DISTINCT cwd` | `type=ALL`，rows 206,531，`Using temporary` | 🚨 **无索引，全表扫** |
| `DISTINCT source` | `type=ALL`，rows 206,531，`Using temporary` | 🚨 **v9 新增列，无索引** |
| 明细 `ORDER BY ts DESC, seq DESC, event_id DESC LIMIT 100` | `type=ALL` + `Using filesort` | 🚨 排序键与索引（`ts`）不一致 |
| `by=user` | `Using index`（覆盖） | ✅ 良好 |
| `hour_of_day` 折叠 | `range` on `idx_usage_event_ts`，`Using temporary` | ⚠️ 尚可 |
| `by=group` JOIN | 驱动表是 8 行的关联表，逐组 `ref` 查 `usage_event` | ⚠️ 依赖人员基数 |

现有索引（8 个）全部在 `usage_event`，但**没有** `source`、`cwd`、也没有
`(ts DESC, seq DESC, event_id DESC)`。

## 7. 明确**不是**瓶颈的（排除项）

| 候选 | 实测 | 排除理由 |
|---|---|---|
| **CPU** | load **0.32**/2 核；服务进程 CPU `0%` | 远未饱和 |
| **磁盘 IO** | 磁盘 29%；`vmstat wa=0`；`bi/bo≈0` | 无压力 |
| **buffer pool 太小** | 512MB vs 表 105MB，命中率 **~100%**（reads 1132 / 27.2G） | 完全够；文档里"128MB→1GB 提升 103×"是**开发容器**的坑，**不是线上** |
| **入库链路** | `POST /api/v1/token-usage` ACK **207–265ms**（日志实测） | 与文档一致，客户端超时 15s 余量充足 |
| **Bun 运行时** | 切换后无新增报错，进程健康 | 正常 |
| **连接池** | 10 条空闲连接 / `max_connections 100` | 富余 |
| **数据库体积** | 整库 105MB | 远未到需要归档的规模 |

> ⚠️ 顺带纠正一个容易误读的数字：`Queries` 累计 **5,431 万**、`Innodb_rows_read` **101 亿**、
> `Bytes_sent` **68.9GB** —— 那是 **5.5 天的累计值**（平均 ~114 查询/秒的**历史**形态）。
> **当前瞬时速率只有 ~0.3 查询/秒**（10 秒采样：Queries +3）。
> 也就是说：历史上有过一段持续的重负载（每次请求 42 条 ⇒ 请求量不大也会推高计数），
> **现在服务是闲的**。不要把累计计数当成当前瓶颈。

## 8. 优化建议（按性价比排序）

### P0 —— 当日可做，零语义风险

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **打开慢查询可观测性**：`slow_query_log=ON`、`long_query_time=0.2`、保留 `performance_schema` 语句摘要 | 从"盲"到"可查" | 极低（不改任何计算） |
| 2 | **给 `source` 建索引**：`idx_usage_event_source_ts (source, ts)` | 来源目录 87ms → 数 ms；带 `source=` 的计数走索引 | 低（DDL，需迁移版本，见下） |
| 3 | **给 `cwd` 建前缀索引**（如 `(cwd(64))`）或改写项目目录查询 | 项目目录 229ms → 数 ms | 低 |
| 4 | 给日志加**轮转**（logrotate / pm2 `max_size`） | 消除 21.8MB 无界增长 | 极低 |
| 5 | 给明细分页加 **`(ts DESC, seq DESC, event_id DESC)` 索引**，或改**键集分页** | 108ms → 数 ms，消除 filesort | 中（改分页契约） |

> ⚠️ 按本仓规矩，**任何 DDL 都是新 schema 版本 + 显式迁移 + checksum**，不能自愈

2. **汇总表对真实流量无效**：`usage_rollup_*` 键里没有 `source` 列，

### 索引为什么没建

# 附录 B：第二轮实测（2026-10-04 深夜）—— 推翻与坐实

## B.0 一句话

**上一轮说「业务查询才是主体、闸门已不是瓶颈」—— 这句话是错的。**
按**语句条数**算，闸门占 **79%**（2447 / 3079）；按**端到端耗时**算，
「筛选栏那个来源下拉框」是慢查询日志里的**第一名**。两件事都指向同一个动作：
**把已经写好但没部署的闸门合并部署上线，再加一条 `(source)` 索引（v14）。**

## B.1 证据一：general log 采样（空闲 6 秒，3079 条语句）

采样时看板没有人工访问，语句全部来自服务端自己 ⇒ 每一条都是**固定开销**。

| 类别 | 条数 | 占比 | 指纹 |
|---|---|---|---|
| **迁移闸门** | **2447** | **79%** | 逐表 CHECK 1487 + 逐版本账本 540 + 8 条结构探针各 60 |
| 配置类 | 441 | 14% | `provider_alias` / `project_alias` / `model_price` / 权限角色 |
| 身份会话类 | 159 | 5% | `auth_sessions` / `login_accounts` |
| 业务聚合 | 240 | 7% | `usage_event` 上的 `SUM/GROUP BY` |

**闸门的构成**（每条 HTTP 请求）：

```
9  × SELECT version,… FROM portal_schema_migrations WHERE version=N   ← 逐版本各查一次
27 × SELECT … FROM information_schema.table_constraints
        WHERE t.table_name = 'usage_event' …                          ← 逐表各查一次 CHECK
8  × 其余结构探针（表清单 / 引擎 / 列 / 索引 / 外键 / 排序规则）
```

⇒ **每请求约 45 条**。这与上一轮「42 条」的数量级一致，但上一轮**没有解释它从哪来**，
而这一轮把来源逐条对到了代码与 SQL 指纹。

**它之所以是主因，不是单条慢，而是「条数 × 往返」**：
每条都是走网络往返的亚毫秒查询（实测单条 0.2–1.0ms），
45 条串行 ≈ 30–45ms，**乘上每次渲染 9 个请求** ≈ 0.3–0.4 秒的**纯固定开销**。
上一轮按「单条耗时」排序，于是把它排到了业务聚合后面 —— 那是**度量口径**的问题。

## B.3 🔴 `SELECT DISTINCT source` 是慢查询日志的第一名

按「指纹归类 + 总耗时」重排慢日志（`long_query_time=0.3` 已在本轮开启）：

| 总耗时 | 条数 | max | 指纹 |
|---|---|---|---|

| 14.3s | 1 | 14.265 | （我自己造数的 `a JOIN b ON session_id`，已排除） |
| 6.8s | 37 | 1.031 | 人员目录聚合（真看板流量） |
| 6.5s | 19 | 0.397 | 我自己的探针（已排除） |
| … 其余全是**闸门**的逐表 CHECK，单条 0.1–1.0ms | | | |

时间分布：`23 点 561 次 / 22 点 25 次 / 21 点 86 次`。

**为什么它这么慢**：

```
EXPLAIN SELECT DISTINCT source FROM usage_event ORDER BY source
  → type=ALL  rows=224453  Using temporary; Using filesort
```

- 库里**只有 4 个来源值**（`dsh` 59952 / `codex` 135035 / `workbuddy` 1366 / `claude-code` 551），
  却要**扫 22 万行**去求 4 个不同的值。
- 线上 8 个索引**没有一条以 `source` 起头**（`idx_usage_event_ts(ts)` 只能被优化成

- 而这个查询服务的是**筛选栏的下拉框**（`GET /api/v1/stats/sources`）——
  候选列表**刻意不带时间窗、不带任何筛选**（`#sources()` 的注释已说明），
  所以它没有任何「顺便走 `idx_ts`」的机会。

**656 次调用累计 120.1 秒**，比所有业务聚合查询加起来还多。

## B.4 ✅ 坐实：闸门合并有效，且**还没部署**


而线上 `dist/main.mjs` 里 `grep -c "withPortalStoreScope"` = **0**、
合并闸门痕迹 = **0** ⇒ **线上跑的还是旧版**。这就是「代码写好了但没上线」。

## B.5 ✅ v14：`usage_event(source)` 单列索引（本轮新增的迁移）

本机隔离库（20 万行 / 来源基数 4）实测：

| | 加索引前 | 加索引后 |
|---|---|---|
| `DISTINCT source` | 13 / 13 / 7 ms | **1 / 1 / 0 ms** |
| `WHERE source='dsh'` | 7 / 6 / 7 ms | 7 / **2 / 2** ms |
| 执行计划 | `type=ALL rows=224453 Using temporary` | `type=range rows=4 Using index for group-by` |
| 建索引耗时 | — | 226ms（20 万行） |
| 索引体积 | — | 20 万行约 1.1MB（数据 8.52MB / 索引共 8.03MB） |

**关键是 `Using index for group-by`** —— MySQL 的 **loose index scan**：
读「来源个数」个索引项，**与表多大完全无关**。这是它与「随便加个索引」的本质区别。

### 🚨 踩到并已修掉的坑

1. **不能加第二列**：`(source, ts)` 会让 loose index scan **完全失效**
   （退回 `Using temporary`，20 万行仍 13ms，**收益精确归零且不报错**）。
   已写一条测试专门钉住「只有一列」（`portal-v14.test.ts`）。
2. **`cte_max_recursion_depth` 默认 1000**：造数用 `WITH RECURSIVE … n < 10000`
   直接 errno 3636。改用「seq 表 + 笛卡尔放大」。
3. **闸门必须核对这条索引**：MySQL 的批量目录查询带了 `AND non_unique=0`，
   **普通索引根本不在那份目录里** —— 不单独核对的后果不是「闸门放行坏库」，
   而是「索引缺失也照样放行」⇒ **一次部署报成功，优化却不存在**。
4. **上一轮的 v9 测试因此失败**：它靠「建当版再 `DROP COLUMN source`」造 v8 库，
   而 v14 的索引让两个后端都拒绝删列。更麻烦的是 **`DROP INDEX` 本身也分方言**：
   SQLite 是 `DROP INDEX IF EXISTS x`，MySQL **没有** `IF EXISTS` 且必须带 `ON <表>`
   （写成 `DROP INDEX IF EXISTS x` 是 errno 1064 语法错）。已按 `store.kind` 分派。
   ⚠️ 已确认**生产迁移链不受影响**：`upgradeV8ToV9()` 只加列从不删列，
   唯一的 `DROP COLUMN` 是 v5 重建 `members.department_id`，与 `source` 无关。

| P1 | 部署并实测端到端收益 | 17.9s 的基线要在同一口径下对比 | ⏳ 待部署 |

| P3 | 汇总表加 `source` 维度（重做 v8 三张表） | 服务「按来源取数」 | ⏳ 未做：代价是重建全部汇总行 + 三张表换主键，与水位事务纠缠 |

## B.7 方法论：这一轮为什么会推翻上一轮

上一轮的三条「实测」全部是**应用层计时一条 SQL**，于是得出「单条 100–330ms，业务查询是主体」。
这个口径漏掉了两件事：

1. **条数**。45 条 × 0.5ms 与 1 条 × 200ms 在应用层看都是「几十毫秒」，
   但前者会随**请求数**放大到 9 倍。
2. **候选类端点**。它们「单条不慢」（DISTINCT 只要 0.3s 而已），
   却是**打开看板必发**的请求，且 6 秒内发了 86–561 次。

⇒ **看数据库负载必须看「条数 × 分布」，而不是「单条耗时排序」**。
判据：先按指纹归类慢日志拿到总耗时，再用 `general_log` 短窗采样拿到**条数分布**，
两者交叉才能定位「谁贵 × 谁多」。

## C.3 闸门里最贵的一条：CHECK 查询的连接顺序（161ms → 23.8ms）

同一台线上库（27 表 / 226 条 CHECK）上，六种写法的**服务端**耗时：

| 写法 | server_ms | 行数 |
|---|---|---|
| `JOIN`（部署中的现值） | **161.15** | 226 |
| **`STRAIGHT_JOIN`** | **23.78** | 226 |
| 只查 `table_constraints` | 1.48 | 226 |
| 只查 `check_constraints` | 0.57 | 226 |
| 表名白名单子查询 | 2.29 | 226 |
| `check_constraints` 按名清单收窄 | 162.67 | 226 |

**为什么**：普通 `JOIN` 时 MySQL 自选驱动表，实测它选**实例级**的
`check_constraints` —— 每个请求都要把整个实例的 CHECK 视图物化一遍，只为挑出本库那 226 行；
强制本库 `table_constraints`（已被 `table_schema=DATABASE()` 收窄）作驱动表就绕开了。

**等价性不是推断**：两种写法按 `COUNT(*) + SUM(CRC32(table|name|clause|enforced))`
取指纹，都是 `226 / 451807555195`（内连接可交换，`STRAIGHT_JOIN` 只固定顺序）。
⇒ 已改成 `STRAIGHT_JOIN`，**往返条数不变**（仍是一条），闸门语义一个字没动。

> 复现：`.artifacts/perf-2026-10-07/gate-variants.sql`（耗时）与
> `gate-equivalence.sql`（指纹）。

### 为什么金额那条 JOIN 不能再减

`EXPLAIN ANALYZE`（全年窗口 197,425 行）逐节点实测：

```
Filter ts                     213ms   (扫 usage_event)
Index lookup model_price(e)  +762ms   (每行一次，3.9µs)
Index lookup model_price(b)  +974ms   (每行一次，4.9µs)   ← 基础价
Aggregate using temporary    +1571ms  (按 provider/model/price_id/currency/slot 建临时表)
```

- **第二条 JOIN 删不掉**：线上价表里 `provider='*'` 有 **18 行基础价**，而
  **109,464 / 197,452（55%）的事件没有专属价**，只能靠基础价（`mp_e.price_id IS NULL` 时）。
  两条 JOIN 各要 19.7 万次索引查找，这是精确逐事件定价在 2 vCPU 上的固有成本。
- 想再快只能换**架构**：给汇总表补 `source` 与价格维度（附录 B 的 P3）、
  或对聚合结果做带失效语义的缓存 —— 两者都涉及口径/新鲜度的取舍，不是纯优化。

## C.6 第四轮：🔴 请求作用域此前对**真实形状**根本没生效（闸门每请求白跑 3 遍）

> 这一节**推翻附录 A.3**的结论（「请求作用域零差异 ⇒ 不是收益来源」）。
> 它当时是对的（A/B 确实量到零差异），但**原因判错了**：不是「一个请求只开一次库」，
> 而是**作用域没能复用**——它在引用计数归零时就真关连接并把 entry 摘掉了。

一个带会话的看板请求会**串行**开 4 次库，每处都在 `finally` 里 `close()` 完才轮到下一处：

```
isRegistered()            → open … close
resolveSession()          → open … close     ← 每次都是新开库 + 重过一遍闸门
authorize() → reauthenticate
openPortalStats()         → open … close(由 session.close())
```

`portal-scope.ts` 的 `close()` 原本写成「refs 归零 ⇒ `store.close()` + 从作用域表摘掉」，
于是**后一次 open 又过一遍闸门**。实测（`Questions` 差值 / 10 次同一路由）：

| 请求 | 修前 | 修后 |
|---|---|---|
| 带会话的 `/api/v1/stats/groups` | **55.3 条 SQL** | **31.3 条** |
| 未鉴权的 401（只走一次 `isRegistered`） | 11.3 条 | 11.3 条（不变） |

55.3 ≈ **4×闸门(9)** + 鉴权(~18) + 业务(1)；401 = **1×闸门** + 1 ⇒ 差的就是那 3 遍白跑的闸门。

**改法**：连接的生命周期归**作用域**，不归 lease —— `close()` 只递减引用计数，
真关只在作用域退出时一次（`portal-scope.ts` 的 `finally`）。作用域退出后**仍然重新开库过闸门**
（既有反向用例继续钉住，不是 TTL 缓存）；新增一条用**连接级状态**（SQLite `PRAGMA cache_size`）
证明「关掉再开拿到同一条连接」的用例 —— 它在旧语义下实测为**红**（拿到默认 `-2000`）。

> ⚠️ 顺带修掉一条**恒真断言**：原来那条「作用域内开 4 次库，闸门只跑一遍」算的是
> `saved = outside - perGate*3` 再断言 `> 0` —— 它对实现没有任何约束力，
> 所以这个退化活了三个月。现在它只断言「作用域外基线是实打实的 4 遍闸门」，
> 复用本身由连接身份那条用例负责。
