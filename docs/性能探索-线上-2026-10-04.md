# 线上服务器性能探索（2026-10-04）

> 一次性**只读**探查：主机资源 → 服务端进程 → MySQL 全库 → 看板取数 SQL → 每请求开销。
> 所有结论都来自线上 `117.72.173.21` 的实测，脚本落在 `.artifacts/perf-explore/`。
> 全程**没有写入任何数据、没有改动任何配置**（`online-probe.ts` 的只读闸门 + 只用 `SELECT`）。

---

## 0. 结论速览

| # | 发现 | 实测证据 | 影响 |
|---|---|---|---|
| **1** | 🚨 **每个 API 请求固定打库 ~42 条 SQL**，与端点、与是否鉴权通过都无关。真业务查询只有 1 条 | 45 次 401 → +1893 条（42/次）；20 次候选目录 → 843 条（42/次）；20 次静态 → +3 | **第一瓶颈**。一个看板约 9 个请求 ⇒ **~380 条语句 / 次渲染**；那 ~50ms/请求的"固定开销"就是它 |
| **2** | 🚨 **汇总表被最主流的查询绕过**：`usage_rollup_*` 的键里**没有来源列**，而线上请求几乎都带 `source=dsh` | `portal.ts:681` 显式提前返回 false；`overview` / 所有 `breakdown` **根本没有 rollup 分支** | 花大工程做的 v8/v12 三张汇总表，对真实流量**几乎无效**（仍在每 5 分钟白维护） |
| **3** | 🚨 **今天数据量暴涨 3.75×**：Codex 历史日志在凌晨 02–03 点被批量补录 **13.7 万条**（占全表 **69%**），表从 5.2 万 → **19.5 万** | `received_at_ms` 分布：02 点 91,998 条 + 03 点 45,754 条 | 把下面所有取数成本整体推高约 **3–4 倍**；且这批是**历史数据**，任何"年"窗口都吃满 |
| **4** | ⚠️ **`source` 与 `cwd` 两列没有索引** → 全表扫描 | `EXPLAIN`：两者均 `type=ALL` + `Using temporary`；实测 87ms / 229ms | "来源目录""项目目录"两个候选端点随数据量**线性变差** |
| **5** | ⚠️ 重聚合查询在 30 天窗口下已达 **66–330ms** | 见 §5 表 | 与 10-01 基线（52K 行时 20–80ms）相比劣化 ~3–4× |
| **6** | ⚠️ 主机**内存偏紧**：4GB 总内存，available 仅 **772MB**，swap 已用 **451MB** | `free -m`、`vmstat` | 目前够用（buffer pool 命中率 ~100%），但这是**最先到顶**的资源 |
| **7** | ⚠️ **可观测性缺口**：`slow_query_log=OFF`、`long_query_time=10s`、`performance_schema` 语句摘要为空 | `SHOW VARIABLES`；摘要表 0 行 | 真出问题时**没有任何慢查询证据可查** |
| **8** | ⚠️ 请求日志无轮转：`ai-token-server-out.log` **21.8MB / 28.6 万行**，每请求写 2 行 | `ls -la`、`wc -l` | 运维卫生问题，非性能瓶颈 |

**一句话**：现在**不慢在机器上**（CPU load 0.32/2 核、磁盘 29%、buffer pool 命中率 ~100%），
慢在**每次请求都把同一份 schema 闸门重跑一遍（×42 条）**，而且**该救命的汇总表因为缺一个 `source` 维度而全程缺席**。
叠加今天 3.75× 的数据暴涨，单次看板取数已经从"几十毫秒"变成"**约 1.0–1.5 秒**"。

## 3. 今天到底发生了什么：3.75× 的数据暴涨

`received_at_ms` 按小时分布（近 24h）：

```
2026-10-04 03   45,754   ← 批量补录
2026-10-04 02   91,998   ← 批量补录（合计 137,752 条）
2026-10-04 01      227
2026-10-04 00      428
2026-10-03 23      881
2026-10-03 22      652
...（其余小时 100~900 条）
```

- 按**接收时刻**看：10 月入库 143,630 条，其中 **95.9% 集中在今天凌晨 2–3 点**。
- 按**事件时刻**看：`codex` 的 13.5 万条落在 4–9 月。
- ⇒ 一次**历史日志批量导入**（Codex 来源），把表从 5.2 万撑到 19.5 万。

**对性能的直接影响**：本次实测的 30 天窗口是 94,751 行；而 10-01 的基线报告里同样口径是

`source` 维度带来的无索引扫描（见 §5.3）。

## 4. 瓶颈一（结构性）：每请求 42 条 SQL，全是 schema 闸门

### 4.1 实测

| 实验 | 请求数 | `Queries` 增量 | 每请求 |
|---|---|---|---|
| `/api/v1/stats/overview`（**无 token，401**） | 45 | +1,893 | **42.1** |
| `/api/v1/stats/groups`（候选目录） | 20 | +843 | **42.2** |
| `/api/health` | 20 | +861 | **43.1** |
| **静态首页 `/`** | 20 | +3 | **0.15**（背景噪声） |

⇒ **只要进 `/api/*`，就固定 ~42 条 SQL**。HTTP 层耗时（`curl` 视角）：

```
/api/health                  200   total 0.050s   ttfb 0.049s
/api/v1/stats/overview(401)  401   total 0.054s   ttfb 0.054s
/                            200   total 0.001s   ttfb 0.001s   ← 静态
```

**那 ~50ms 的"固定开销"＝ 42 次往返 MySQL。** 本地回环单次 ~1.2ms × 42 ≈ 50ms，完全吻合。

### 4.2 42 条 SQL 是怎么来的（代码侧）

`ensurePortalReady()` 每次都**重读真实结构**（刻意不缓存，见其注释：运行中改结构要立刻拒绝），
而 `verifyCurrentMysql()` 的语句数**随表数增长**：

```
5 条全库批量目录（tables / columns / statistics / foreign keys / …）
+ 27 条 CHECK —— 每张表 1 条（本库实测 27 张表）
+ 1 条 event_id 排序规则
+ readPortalState（版本状态）
≈ 35–42 条 / 次 openPortalStore()
```

> ⚠️ 文档里"19 张表 116 条 → **5 条**"的说法**不完整**：CHECK 那一段仍是**每表一条**循环
> （`portal-migrations.ts:476-481`，注释也承认"20 张表各查一次仍然比全库一次快"）。
> 随着表数从 19 涨到 27，闸门语句数也一起涨。

**鉴权路径也开库**：`stats-route.handle()` 第 1 步 `authorizeDatabase()` 会调
`IdentityRepository.isRegistered()` / `resolveBearer()`，而 `repository.ts:47` 就是
`await openPortalStore(this.target)` —— 所以**连 401 都要跑一遍闸门**。
一个通过鉴权的看板请求，从鉴权到取数可以开到 **2–4 次** `openPortalStore()`。

### 4.3 放大效应：一个看板 ≈ 380 条语句

线上日志（近 3000 行）里，一次看板渲染会连发：

```
overview  + series  + breakdown?by=user + breakdown?by=group
+ groups + members + providers + sources (+ projects)
≈ 9 个请求
```

⇒ **9 × 42 ≈ 378 条 SQL / 次页面刷新**，其中真正的业务查询只有 9 条。
**96% 以上的 SQL 是闸门。**

## 5. 瓶颈二（结构性）：汇总表在最主流查询上被绕过

本仓有 v8/v12 的三张汇总表（`usage_rollup_day` / `_hour` / `_hod`），并且**确实在增量维护**：

| 表 | 行数 | 覆盖 |
|---|---|---|
| `usage_rollup_day` | 326 | 2026-04-07 → 10-04（全量） |
| `usage_rollup_hour` | 653 | 2026-09-04 → 10-04（近 30 天） |
| `usage_rollup_hod` | 515 | 全历史折叠 |

水位 `built_through = 2026-10-04 11:31:57`（**近实时**），与原始表只差 17 条。
日志里也能看到 `[rollup] 定时补齐：incremental，日格 2 / 小时格 2 / 时段格 2`。

**但它读不到。** `portal.ts` 里 rollup 快路径只挂在两个地方，且带三道安全阀：

| 位置 | 条件 | 结果 |
|---|---|---|
| `overview`（totals/sessions/…） | **没有 rollup 分支** | 永远走原始表 |
| 所有 `breakdown`（by=user/group/provider/model/project/day/hour） | **没有 rollup 分支** | 永远走原始表 |
| `series()`（`portal.ts:1092`） | `!withCost` **且** `#rollupUsable()` | 有条件命中 |
| `hourOfDay()`（`portal.ts:763`） | `#rollupUsable()` | 有条件命中 |

而 `#rollupUsable()` 里有一条**显式提前返回**（`portal.ts:672-681`，注释原文）：

> 🚨 **按来源筛选/分组时必须退原始表**：`usage_rollup_*` 的键是
> `(day_key, hour_of_day, member_id, provider, model)` —— **没有来源列**。

```ts
if ((this.#filter.sources?.length ?? 0) > 0) return this.#rollupState   // = false
```

**线上日志里 `source=dsh` 是绝大多数请求都带的参数**（例如
`/api/v1/stats/overview?identity_view=member&period=year&source=dsh&member_id=…`）。
再加上该请求同时带 `member_id=`（`#rollupSeries` 要求 `isTimeWindowOnly`），
以及查看者是管理员（很可能有 `cost:read` ⇒ `withCost=true` 直接短路）——
**三条路全断**。

> ⇒ 结论：**汇总表当前对真实流量基本无效**，却仍在每 5 分钟做一次写入维护。
> 这不是"白做"（口径已被测试钉住、阈值到了就能用），但**现在是纯成本没有收益**。

### 6.1 EXPLAIN：两个真正的索引缺口

| 查询 | 计划 | 结论 |
|---|---|---|
| `DISTINCT cwd` | `type=ALL`，rows 206,531，`Using temporary` | 🚨 **无索引，全表扫** |
| `DISTINCT source` | `type=ALL`，rows 206,531，`Using temporary` | 🚨 **v9 新增列，无索引** |
| 明细 `ORDER BY ts DESC, seq DESC, event_id DESC LIMIT 100` | `type=ALL` + `Using filesort` | 🚨 排序键与索引（`ts`）不一致 |
| `by=user` | `Using index`（覆盖） | ✅ 良好 |
| `hour_of_day` 折叠 | `range` on `idx_usage_event_ts`，`Using temporary` | ⚠️ 尚可 |
| `by=group` JOIN | 驱动表是 8 行的关联表，逐组 `ref` 查 `usage_event` | ⚠️ 依赖人员基数 |

现有索引（8 个）全部在 `usage_event`，但**没有** `source`、`cwd`、也没有
`(ts DESC, seq DESC, event_id DESC)`。

## 7. 明确**不是**瓶颈的（排除项）

| 候选 | 实测 | 排除理由 |
|---|---|---|
| **CPU** | load **0.32**/2 核；服务进程 CPU `0%` | 远未饱和 |
| **磁盘 IO** | 磁盘 29%；`vmstat wa=0`；`bi/bo≈0` | 无压力 |
| **buffer pool 太小** | 512MB vs 表 105MB，命中率 **~100%**（reads 1132 / 27.2G） | 完全够；文档里"128MB→1GB 提升 103×"是**开发容器**的坑，**不是线上** |
| **入库链路** | `POST /api/v1/token-usage` ACK **207–265ms**（日志实测） | 与文档一致，客户端超时 15s 余量充足 |
| **Bun 运行时** | 切换后无新增报错，进程健康 | 正常 |
| **连接池** | 10 条空闲连接 / `max_connections 100` | 富余 |
| **数据库体积** | 整库 105MB | 远未到需要归档的规模 |

> ⚠️ 顺带纠正一个容易误读的数字：`Queries` 累计 **5,431 万**、`Innodb_rows_read` **101 亿**、
> `Bytes_sent` **68.9GB** —— 那是 **5.5 天的累计值**（平均 ~114 查询/秒的**历史**形态）。
> **当前瞬时速率只有 ~0.3 查询/秒**（10 秒采样：Queries +3）。
> 也就是说：历史上有过一段持续的重负载（每次请求 42 条 ⇒ 请求量不大也会推高计数），
> **现在服务是闲的**。不要把累计计数当成当前瓶颈。

## 8. 优化建议（按性价比排序）

### P0 —— 当日可做，零语义风险

| # | 动作 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **打开慢查询可观测性**：`slow_query_log=ON`、`long_query_time=0.2`、保留 `performance_schema` 语句摘要 | 从"盲"到"可查" | 极低（不改任何计算） |
| 2 | **给 `source` 建索引**：`idx_usage_event_source_ts (source, ts)` | 来源目录 87ms → 数 ms；带 `source=` 的计数走索引 | 低（DDL，需迁移版本，见下） |
| 3 | **给 `cwd` 建前缀索引**（如 `(cwd(64))`）或改写项目目录查询 | 项目目录 229ms → 数 ms | 低 |
| 4 | 给日志加**轮转**（logrotate / pm2 `max_size`） | 消除 21.8MB 无界增长 | 极低 |
| 5 | 给明细分页加 **`(ts DESC, seq DESC, event_id DESC)` 索引**，或改**键集分页** | 108ms → 数 ms，消除 filesort | 中（改分页契约） |

> ⚠️ 按本仓规矩，**任何 DDL 都是新 schema 版本 + 显式迁移 + checksum**，不能自愈
> （`AGENTS.md`：上报库绝不自动重建）。加索引属于受控 DDL，要走 v13 流程。

### P1 —— 结构性，收益最大
