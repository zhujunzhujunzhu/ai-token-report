# 初始化性能与失败恢复（2026-09-27）

本轮修复针对首次扫描、CLI 普通统计的多余全量读取，以及统计请求长期没有结果的失败路径。

## 确认的问题与改动

- Windows / Node 24.19.0 的递归 `fs.watch()` 接收 8.3 短路径时，新增子目录可触发
  `Assertion failed: !_wcsnicmp(filename, dir, dirlen), file src\win\fs-event.c, line 72`。
  独立复现退出码为 `-1073740791`，普通 try/catch 无法拦截原生断言。
  监听入口改用 `realpathSync.native()` 后，同一复现退出码为 0；增量文件路径继续保持调用方根目录，兼容目录联接。
  这是本次验收中复现的崩溃，不能据此断言用户此前所有加载失败都由它导致。
- Worker 的请求原先没有截止时间。现有队列上限保留，新增 120 秒等待上限，超时终止线程、拒绝全部在途请求并释放定时器；后续查询可恢复。
  页面请求另设 125 秒上限，覆盖 HTTP 连接和响应体读取，显示可重试错误。
- 两种扫描路径逐帧消费 JSONL，保留跨帧尾行，不再先拼接完整文件的解压文本。
  通用异步解码最多并发四帧，避免为长会话同时创建数万原生解压任务。
  计费记录仍按既有事务和水位线规则提交，不改变四项 token、去重和项目归属。
- CLI 普通统计直接查询已有压缩索引，不再把全部原始记录取回后重新聚合。
  Web 服务和上报依赖改为在相应子命令执行时加载。交叉表与 JSON 的 provider 趋势仍按需读取原始记录，以保留输出契约。
- 固定设计 DDL 为 LF 换行，修复 Windows checkout 下已有的 DDL 字节对账测试失败，不改变 SQL 内容。

## 实测结果

本机 Windows，Node 24.19.0 / Bun 1.4.2；未清空操作系统文件缓存。

### 真实 DSH 与日志副本

使用 207 份日志、87,586,769 压缩字节，在临时 profile 中运行真实 DSH Web。
测试只读日志副本，禁用上报，不复制身份。统计期间另请求配置接口以观察宿主响应性。

| 项目 | 修复前 | 修复后 |
|---|---:|---:|
| 首次 HTTP 摘要（空本地库） | 4,889 ms | 4,176 ms |
| 强制刷新 | 178 ms | 178 ms |
| 详情首页 | 未测 | 25 ms |
| 冷查询同时访问配置接口 | 未测 | 14 ms |

两次统计的计费记录数均为 16,757。两次完整宿主启动分别约 12.8 / 10.1 秒，含 DSH 自身启动成本，不能归因于插件优化。
这是单次端到端记录，不是 P95 或生产延迟保证；原先的无限加载未在这批日志中复现。
最终产物再次验收：宿主启动 9,695 ms、首次摘要 4,567 ms、强制刷新 196 ms、详情 23 ms，冷查询期间配置接口 13 ms，结果仍为 16,757 条。

### CLI 百万事件

独立合成库，100 万事件、1 万会话、相同原始列和月份窗口，默认分组 JSON 输出。
比较旧 CLI 的全量物化路径与新 CLI 的索引路径；扫描内核、运行时及数据库相同，日志目录为空，不把它当首次日志扫描基准。

| 项目 | 修复前 | 修复后 |
|---|---:|---:|
| 第一轮（新路径包含首次派生索引构建） | 4,929 ms | 5,048 ms |
| 后续三次进程总耗时 | 5,372 / 5,376 / 5,189 ms | 243 / 241 / 238 ms |
| 后续中位数 | 5,372 ms | 241 ms |

重复查询约快 22 倍；首次索引成本仍然存在。两种路径均断言 100 万调用、9,500 万 total token，并由回归测试逐列比较口径与各类输出。
