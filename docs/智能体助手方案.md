# 智能体助手方案（DSH agent 承载 · 只读问答）

> **状态**：方向已定，待拍板项见 §13。本文是**方案**，不是实施记录 —— 落地后按本仓惯例在本文件追加「实测结论」小节。
>
> **一句话**：助手的大脑是 **DSH 自己的 agent**（服务端托管的 headless dsh），我们**不写 agent loop、不管模型凭证、不做 LLM 适配层**；我们负责两件事 —— ①「工具能不能安全、准确地拿到本平台数据」这条缝（一端是你提供的 DSH 插件工具，另一端是现有只读统计面 `/api/v1/stats/*`），②**用户与会话的管理**（谁在用、每个会话属于谁、能不能续、怎么删）。

## 1. 已确认决策

| # | 决策 | 内容 |
|---|---|---|
| 1 | 大脑 | **DSH agent 能力**（`@deepseek-ai/dsh-agent` / `dsh-agent-loop`），模型凭证归 DSH |
| 2 | 承载 | **服务端上跑 headless dsh**（`dsh headless`），部门网页端里是一个对话入口 |
| 3 | 工具 | **由你提供**（DSH 插件工具形态），工具在**部门网页端这一侧**取数 |
| 4 | 能力边界 | **只读问答** —— 不给任何写操作，不给任意 SQL |
| 5 | 用户与会话 | **复用现有身份体系**（不新建用户表）；会话按人归属，可列出 / 续话 / 删除，归属校验在服务端 |

> 与上一版方向的差别：**删掉**了「自建 tool-calling loop」「OpenAI 兼容网关适配器」「服务端模型 key 与出网凭证」整块；
> **保留并加强**的是与 DSH 无关的那一层 —— 只读数据缝、数据范围、口径单一真源、权限码、审计、**用户与会话归属**、助手自身用量入账。

## 2. 我们做什么 / 不做什么

| | 内容 |
|---|---|
| ✅ 做 | 专用 headless profile（把危险工具关掉）、**用户与会话管理**、提问者身份→工具的传递、只读工具面契约、SSE 转发、权限码、审计、助手自身用量入账、网页端对话面板与会话列表 |
| ❌ 不做 | agent loop、工具编排策略、模型选择与 prompt 工程主体、模型凭证存储、LLM 供应商适配、任何写操作、任意 SQL、**第二套用户/登录体系** |

**为什么不做自建 loop**：本仓已经有一份「谁的会话、什么模型、怎么算」的实现（插件），再写一份 agent loop 就是第二个口径与第二个凭证面；而 DSH 侧本来就把 loop 做完了。

## 3. 数据流

```
浏览器（已登录会话：账号密码 + 验证码 + cookie，或 Bearer）
  │  POST /api/v1/assistant/chat      ← SSE（fetch + ReadableStream，不能用 EventSource）
  ▼
packages/server  assistant-route.ts
  │  ① authorize()：401 / 403 / 503 三分（沿用现有语义）
  │  ② 平台会话：新建或续话 —— 校验 assistant_session.member_id == 提问者
  │  ③ 铸一张「提问者作用域票据」（memberId + permissions + 过期）
  │  ④ spawn headless dsh --session-id <dshSessionId>（专用 profile，票据经 env 注入）
  ▼
dsh headless --json "<问题>"          ← 大脑与模型在这里，不归我们
  │  模型决定调工具
  ▼
你的 DSH 插件工具（部门网页端一侧）
  │  GET /api/v1/stats/*（带票据）
  ▼
packages/server  stats-route.ts  → applyDataScope() 收窄到提问者
  │  只读原始列 + shared/metrics 派生指标
  ▼
工具结果（经投影层）→ 模型 → 答案
  │  dsh 的 --json 事件逐行 → SSE → 浏览器
  ▼
网页端渲染（工具调用过程可见、数字可溯源）＋ 会话落库（元数据）
```

★ **两条关键性质**：
1. 工具与统计接口之间是一条**真 HTTP 边界**，走现有鉴权与现有数据范围实现 —— "工具能不能越权"在服务端就被回答了，不依赖提示词、不依赖工具实现者的自觉。
2. **平台会话是"谁能访问这个 dsh 会话"的权威**，DSH 的持久化会话只是 agent 的事实源。两者必须成对管理（见 §7）。

## 4. 🚨 安全边界（本方案最重要的一节）

### 4.1 专用 profile：这是「加一个输入框」与「把服务器 shell 开放给全公司」之间的区别

实测（`dsh --profile headless --dump-config`）headless 默认带：

```
tool-bash / tool-pwsh / tool-jobs / tool-fs / tool-fs-search / tool-web
tool-subagent / tool-subagent-control / tool-workflow / tool-todo / tool-goal / tool-ralph
skill / skill-filesystem / plugin-manager(tools)
sandbox(read-only|workspace-write|danger-full-access) + approval(ask|never)
```

直接把它装在部门服务端上，任何一个能打开看板助手的人都能让 agent 去读服务器文件、跑命令、访问外网。
**因此必须派生一个专用 profile**（`dsh --from-default-profile headless` 再逐条裁掉），只保留：

- 只读统计工具（你提供的那批）
- 最小必要的会话能力（`dsh-session*`）
- 显式的沙箱与审批策略：`sandbox: read-only`、**不给 `danger-full-access`**、审批不设 `never`
- 关掉 `tool-web`（否则模型可以拿 cwd / 人名去外网搜，等于第二条数据外流面）

⚠️ 这个 profile 的**组成必须在 CI 里被断言**，不能靠"部署时记得删"：写一个 `--dump-config` 后的结构断言（例如「产物里不得出现 tool-bash / tool-pwsh / tool-fs / tool-web / plugin-manager」），否则下一次 DSH 升版新增一个工具就会静默回到默认集。

### 4.2 身份：工具必须带**提问者本人**的身份

推荐做法（**这一条需要你确认**，见 §13-1）：

1. 服务端处理一次提问时，为它铸一张**短期作用域票据**：`memberId` + 该身份当前 `permissions` + 过期时间（分钟级），随 spawn 经环境变量注入（如 `ATR_ASSISTANT_TICKET`）。
2. 你的工具读这张票据，用它去调 `http://127.0.0.1:<port>/api/v1/stats/*`。
3. 数据范围由 `stats-route.ts` 的 `applyDataScope()` 决定：**内置 `admin` 角色=全部门，其它任何角色=只有他自己**（判据是角色码，不是权限码 —— 这条已在仓内定死，助手不得另立一套）。

🚨 **绝不使用一把固定的高权凭证**给所有提问。那样「看板上谁能问出全员数据」就只由提示词决定，而提示注入必然发生；一把固定凭证还会让所有提问者在审计里变成同一个人。

### 4.3 只读

- 工具面**一对一映射现有 `GET /api/v1/stats/*`**，一个写路径都不开。
- **不提供任意 SQL / 表达式工具**：那既是注入面，也必然变成第二个口径实现（SQL 里一旦出现 `cache_read/(cache_read+input)` 这类公式就违反了「口径只在 `shared/metrics.ts`」）。
- 模型输出永不执行；工具参数由服务端校验（复用现有手写解析 + 400 语义，非法值不许静默当成没给）。

### 4.4 合规：两个必须先说清的面

| 面 | 事实 | 建议 |
|---|---|---|
| 数据**出网**发给模型 | 用量数字与**人名**会进模型请求体；DSH 的模型若是公网服务，这就是一条新的数据外流面 | ★ 工具结果的**投影层默认脱敏人名**（返回 `member_id` + `成员A`），网页端拿 `member_id` 用名册在**本地**还原真名 —— 模型永远看不到真名，页面照样显示真名 |
| 对话**正文** | 本仓合规基线是 `includeContent: false`（只采 token 数值与模型名，不采内容） | 助手默认**不存对话正文**，只存元数据审计（谁、何时、调了哪些工具、耗时、退出码）。要存正文就单独一个开关 + 明确告知 + 保留期，不要默认开 |

### 4.5 助手的金额口径不得重算

金额三态在助手侧同样成立：没有 `cost:read` 时**字段整个不下发**（不是 0）、`unpricedRate` 必须显式（未计价 ≠ 省了钱）、**多币种绝不相加**、同一 `(provider, model)` 先分组算完再求和。
投影层只搬运，不做任何换算；趋势金额在多币种时禁用那条规则同样适用于助手（助手可以说"有 N 种币种，请看分布表费用列"，但不能给出一个合计）。

## 5. 工具面：我们提供给你那些工具的接口

### 5.1 工具清单（全部只读，一对一映射现有端点）

| 工具 | 背后的端点 | 备注 |
|---|---|---|
| `stats_overview` | `/api/v1/stats/overview` | 总览卡片 + 未归属占比 |
| `stats_series` | `/api/v1/stats/series?bucket=day\|hour` | 趋势；多币种时不给金额合计 |
| `stats_breakdown` | `/api/v1/stats/breakdown?by=member\|group\|provider\|model\|project\|source` | 排行 / 分布，助手主力 |
| `stats_records` | `/api/v1/stats/records?limit&offset` | 明细；**行数上限**（投影层截断并明说截断） |
| `stats_diagnostics` | `/api/v1/stats/diagnostics` | 覆盖率 / 数据边界（回答"为什么少了一块"） |
| `stats_candidates` | `/members` `/groups` `/providers` `/projects` `/sources` | 把"张三"这类自然语言变成稳定 ID |
| `stats_pricing` | `/api/v1/stats/pricing` | 只读单价快照（需 `cost:read`），回答"这钱按哪个价算的" |
| `metrics_contract`（可选） | 无需端点，返回 `shared/metrics.ts` 的口径说明文本 | 让"缓存命中率怎么算的"只有一个答案 |

> 会话相关**不进工具面**：助手不通过工具管理会话，会话由服务端的路由层按登录身份管（§7）—— 让模型去操作"会话"等于把归属权交到提示词手里。

### 5.2 投影层：给模型的载荷 ≠ 接口原样响应

★ 这是**一处实现**，不是每个工具各写一份（各写一份必然漂移，且不会报错）：

- **人名脱敏**（§4.4）；`cwd` 折叠成项目名（复用 `core/src/db/project-alias.ts`，原值不进模型）；
- 丢掉与回答无关的字段（票据、内部 id、chunk 元数据），控制 token；
- 行数 / 时间窗上限，并在结果里**明写"已截断"**（悄悄截断会让模型据半份数据下结论）；
- **时间窗必须显式**：用户没说时间时用「最近 7 天」，且回答里必须写清窗口（"本月"在自然语言里歧义太大）。

### 5.3 契约位置

`packages/shared/src/assistant.ts`：工具名枚举、票据字段、会话 DTO、SSE 事件类型（`delta` / `tool_call` / `tool_result` / `done` / `error`）、错误码。
理由与全仓一致：前端要渲染工具调用过程与会话列表，契约必须单一真源，对不上时 `bun run typecheck` 直接失败。
⚠️ zod 只准从 `@ai-token-report/shared/schemas` 子路径进（S12.5 准入断言），别在根入口 re-export。

## 6. 服务端结构（不新增包）

```
packages/server/src/
  assistant-route.ts          # POST /api/v1/assistant/chat（SSE）
                              # GET/DELETE /api/v1/assistant/sessions*（会话管理，§7）
  assistant/
    ticket.ts                 # 作用域票据：铸造 / 校验 / 过期（唯一实现）
    session-store.ts          # 平台会话：建 / 续 / 列 / 删 + 归属校验（唯一实现）
    profile.ts                # headless profile 的定位与装配期校验
    spawn.ts                  # spawn dsh headless --json，逐行事件 → SSE（node:child_process）
    project.ts                # 投影层（§5.2，唯一实现）
    quota.ts                  # 每用户 in-flight=1 / 会话内串行 / 轮数 / 时长上限
    audit.ts                  # 元数据审计（不写正文）
```

**为什么 spawn 子进程而不是在我们的进程里 import dsh**：版本与依赖隔离（DSH 是 bun 全局安装的 ESM 包树）、崩溃隔离、升级只需换 dsh 版本。**代价**：每次提问的冷启动开销（DSH 引导 + 插件装载）—— 这是本方案第一个该实测的数字（§13-4）。若冷启动不可接受，二期可改为常驻 `dsh web` + `dsh-api-gateway` 驱动（与 GUI 同一条通路），但那要自己管会话隔离与身份绑定。

**必须保留的既有约束**：

- 服务端不得依赖 `Bun.serve` / `Bun.file()`（npm 发布产物要跑在 Node 上）→ spawn 用 `node:child_process`，流式逐行读 stdout；`serve-node.ts` 目前是 `Buffer.from(await response.arrayBuffer())`（**非流式**，见该文件 199 行），SSE 要落地必须先确认/改造这一处的流式支持。
- `idleTimeout` 已设 120 秒，但一次 agent 提问可能超过（多轮工具调用）→ 需要心跳或显式上限，别让客户端拿到 `ECONNRESET` 而服务端毫无日志。
- 鉴权状态码映射只在 `server/src/http/auth.ts` 的 `authorize()`；请求体读取只在 `http/body.ts`。新路由必须复用，不许自写。

## 7. 用户与会话管理

### 7.1 用户：复用身份库，**不新建第二套用户体系**

| 问题 | 答案 | 真源 |
|---|---|---|
| 谁是助手的用户 | 平台现有人员（`member`）—— 能登录后台的人 | `packages/server/src/identity/`（member / role / permission） |
| 谁**能用**助手 | 角色里带 `assistant:chat`（新权限码，§9） | 同上，改角色即可，不给人开特例 |
| 怎么登录 | 复用现有后台登录（账号密码 + 验证码 + cookie / Bearer） | `server/src/auth/portal-auth.ts` |
| 匿名能不能用 | **不能**。助手的每一次提问都必须落在一个 `member_id` 上 | 同上（"未署名 = 不采集"的同一条逻辑） |

🚨 **不要在助手侧建用户表、不要把助手的登录与平台登录分开**。分开的后果是同一人在两个系统里有两个身份，而"数据范围"是按人收窄的 —— 那就等于凭空造出一个能看全员数据又不被审计的入口。

**每用户的配额与开关**（`quota.ts`）：in-flight=1、每日提问次数、每日（若二期做）预算。管理员要停掉某人的助手使用权时**改角色权限**，而不是在助手侧加一个"禁用"旗标（两处开关必然不一致）。

### 7.2 平台会话 vs DSH 会话：两个东西，权威各是谁

| | 平台会话（我们的库） | DSH 会话（DSH 的持久化） |
|---|---|---|
| 是什么 | 一次"对话"的业务对象：标题、归属人、状态、轮数、花费 | agent 的事实源：消息、工具调用、模型往返 |
| 权威回答 | **谁能读/续/删它** | 这次对话实际发生了什么 |
| 存放 | portal 库（schema v13） | DSH 的 sessions 目录（`dsh --session-id` 续话用它） |
| 一对一 | 平台会话 1 : 1 dsh session id（首次提问后回填） | —— |

🚨 **`--session-id` 能续任何持久化会话**。所以：
1. 续话时**只认平台会话行里的 `dsh_session_id`**，绝不接受客户端直接提交的 dsh session id；
2. 平台会话行必须带 `member_id`，续话/列表/删除一律先校验归属（非管理员只碰自己的）；
3. 会话 id 用不可猜的形式（UUID），并仍旧做归属校验 —— 不做"靠 id 猜不到"的安全。

### 7.3 表结构（portal schema v13）

```
assistant_session
  session_row_id   PK            -- 平台会话 id（对外暴露）
  member_id        FK → member   -- 归属（RESTRICT：人不能被删成无主会话）
  dsh_session_id   NULL          -- 首次提问后回填；UNIQUE
  title            TEXT          -- 首问截断（不调模型生成标题 = 不多花一次钱）
  status           TEXT          -- active | ended | failed
  created_at_ms / last_active_at_ms / ended_at_ms
  turn_count / tool_call_count / last_error

assistant_turn                   -- 每次提问一行（元数据，不含正文）
  turn_id PK / session_row_id FK / seq
  asked_at_ms / finished_at_ms / status
  tool_calls_json                -- 调了哪些工具、什么参数、截断了没有
  exit_code / error_code
  prompt_tokens / completion_tokens   -- 见 §10：这一列可选，优先靠上报链路
```

- **默认不存对话正文**（§4.4）；要存就单独开关 + 保留期，并且**只在同一张表里加列**，不要另起一张"内容表"（那会让"删会话"变成删两处）。
- 断言一律写 `PORTAL_SCHEMA_VERSION`，绝不写死版本号。
- 迁移必须能回滚（沿用 v7→v12 的迁移链验证方式）。

### 7.4 可见性：本人 / 管理员

| 身份 | 会话列表 | 对话内容 | 删除 |
|---|---|---|---|
| 本人 | 只看自己的 | 自己的 | 自己的 |
| 非管理员角色（含自定义） | 只有自己 | 只有自己 | 只有自己 |
| 内置 `admin` | 全部（用于排障与成本核算） | ★ **见 §13-2**：默认只看元数据，不看正文 | 全部 |

★ 管理员能看"谁在用、问了多少次、花了多少钱、有没有报错"，这足以排障与核算；**看不看得到具体问了什么，是另一件事**，需要单独拍板（默认否）。
⚠️ 会话可见性**必须复用与看板同一条判据**（`admin` 角色码 = 全部门，其它 = 只有自己），不能"因为助手是新功能就顺手放宽"。

### 7.5 生命周期

| 动作 | 规则 |
|---|---|
| 新建 | 首次提问时由服务端创建（客户端不能指定归属人）；归属取当前登录身份 |
| 续话 | 校验归属 + 会话未 `ended`；同一会话内**串行**（DSH 会话是单写者，并发续话会串行化或拒绝） |
| 结束 | 用户显式结束 / 超时（如 30 分钟无活动）/ 管理员强制结束 |
| 删除 | 删平台行 + **同时删 DSH 侧的持久化会话**（§13-2 的隐私要点：只删平台行 = 用户以为删了、磁盘上还留着整段对话） |
| 保留期 | 会话元数据保留 N 天（可配），到期归档/删除；清理任务与"计划任务"（ARCHITECTURE §8 的 S10 待办）合并做，不要为它单独造一套调度 |
| 崩溃/重启 | 服务端重启后 `active` 会话必须仍能续（dsh session 在磁盘上）；重启时把无法恢复的会话标 `failed` 并在页面说明，**不许静默变成"新会话"** |

### 7.6 接口与页面

```
GET    /api/v1/assistant/sessions?limit&offset&member_id?   # 列表（按可见性收窄）
GET    /api/v1/assistant/sessions/:id                       # 详情（含轮次元数据）
POST   /api/v1/assistant/sessions/:id/end                   # 结束
DELETE /api/v1/assistant/sessions/:id                       # 删除（含 DSH 侧）
POST   /api/v1/assistant/chat                               # 提问（SSE，带或不带 session id）
```

- 状态码沿用仓内约定：`401` 身份无效 / `403` 权限不足或**不是自己的会话** / `503` 未部署助手 / `409` 会话状态冲突 / `400` 参数错。
- 管理员排障页 `/assistant/sessions`（需 `assistant:chat`；要看别人会话另需 `assistant:manage`，**建议新增这一个权限码**，别把"能用助手"与"能看所有人的会话"绑成一条）。
- 与现有三个管理页的分工要守住（仓内已有明确划分）：**人是谁在人员管理页、key 发给了谁在 appKey 页、助手会话在助手会话页** —— 不要把会话塞进人员管理页。

## 8. 部门网页端（`web-portal`）

- 入口：`/assistant` 页（需 `assistant:chat`）；未部署/未配置助手时**入口不出现**（与"服务端少返回字段按没有处理"同一条安全逻辑）。
- SSE 消费用 `fetch` + `ReadableStream`（要 POST + 会话/Cookie，`EventSource` 不支持）；dev 走 5198 → 8787 的 `/api` 代理，需确认代理不缓冲。
- 渲染四件事：**会话列表与切换**（含"结束/删除"）、**工具调用过程可见**（哪次查询、什么参数、截断了没有）、**每个数字可溯源**（点开显示来自哪个端点的原值）、**金额三态**（无 `cost:read` 一位金额都不出现）。
- 前端**零口径**：只排版，不重算（本仓铁律：浏览器半不重算任何度量；插件浏览器半是同一约束）。
- 现有门禁要跟着扩：`packages/web-portal/verify/verify-render.ts` 里"无 `cost` 时不得出现金额"的断言必须覆盖助手页；会话删除的确认文案要写清"连同对话记录一起删除"。

## 9. 权限与审计

- 新权限码（加进 `packages/server/src/identity/types.ts` 的 `PERMISSIONS`，并在角色配置页可用）：
  - `assistant:chat` —— 能用助手（问 + 管自己的会话）
  - `assistant:manage` —— 能看/强制结束/删除**别人的**会话（排障与成本核算）
  ★ **只加这两条，不要与 `stats:read` / `cost:read` 绑**（"能用助手"与"能看金额"是两件事，绑起来在页面上看不出来）；也不要拿 `members:read` 代替 `assistant:manage`。
- 审计：提问者、时间、会话 id、工具调用序列、耗时、dsh 退出码、票据 id；**不含对话正文**。
- 助手查询**不是管理变更**：不要塞进 `admin_audit_log`（那张表是管理动作的账）。

## 10. 助手自身的用量入账（本项目的独特一环）

助手自己会烧 token，而**我们正好是量 token 的平台** —— 不记这笔账说不过去。

★ 推荐让助手**走已有的上报链路**：助手 profile 里装本仓插件 + 一个专用人员身份（如「AI 助手」）+ 专用 appKey，于是它的用量自然进 `usage_event`（`source = dsh`，归属=那个专用人员），看板上按人员维度就能看出"助手花了多少"。

- 好处：**零新增写入路径**、零新增 source 枚举、不碰覆盖率口径（`core/src/db/stats.ts:504` 用 `registeredSources().length` 做来源收窄判断）。
- 若还想在页面上按会话看花费，再用 `assistant_turn` 的元数据做**关联**（§7.3 里那两列），但**不要**在助手侧另算一份金额 —— 金额口径只在 `shared/price.ts`，助手侧再算一遍就是第二个实现。
- 待确认（§13-3）：要不要一个**独立 source**（如 `portal-assistant`）以便与员工流量分开筛。要的话得动 `packages/core/src/types.ts` 的 `SessionSource` 受控枚举与注册表；**内部来源不扫日志**这件事与 `registeredSources()` 的语义要实测，别让"未注册来源"污染覆盖率。

## 11. 部署（服务端）

1. 服务器装 dsh（与线上运行时同一个 Node/Bun 决策），建目录与专用 profile：
   `dsh --from-default-profile headless` → 删危险工具（§4.1）→ `dsh plugin --profile <atr-assistant> add <你的工具包>` + 本仓插件。
2. 模型凭证归 DSH（`dsh-llm-deepseek-api-key`），**不进我们的库、不进页面、不进日志**。
3. **profile 组成与插件兼容窗口一起进部署前检查**：本仓已有先例 —— 插件 peer 范围不满足时 DSH 只是"跳过整个 bundle"，表现是面板消失 + 一条也不上报，**不是报错**。助手同理：profile 坏了会表现为"助手永远不回答"，所以 preflight 必须断言 `--dump-config` 的结果与「助手可用性自检」各一条。
4. 数据库迁移（schema v13）与回滚进 preflight/apply，沿用现有部署脚本的备份-切换-健检-回滚四段式。

## 13. 待拍板 / 待实测

1. **身份传递**：确认「每次提问铸一张短期作用域票据 → env 注入 → 工具用它调 `/api/v1/stats/*`」这条缝。票据放 env 还是放工具能读的临时文件（Windows / Linux 都要考虑进程环境可见性），也一并定。
2. **会话正文与 DSH 侧删除**：① 平台默认不存正文 —— 确认；② 管理员默认只看得见元数据、看不见别人问了什么 —— 确认；③ **删除会话时是否连带删除 DSH 侧的持久化会话**（建议"是"，否则"删除"是假的）；④ 正文本地留存期限（不存/30 天/永久）。
3. **你的工具怎么取数**：走 HTTP `127.0.0.1:<port>/api/v1/stats/*`（推荐：鉴权与数据范围只有一份），还是直接 `import @ai-token-report/core` 查库？（后者会让"数据范围"在工具侧出现第二份实现，需要额外护栏。）
4. **助手自身用量的可见性**：一期用"专用人员"区分够不够，还是要独立 `source`？（后者要动 `SessionSource` 枚举 + 实测覆盖率口径。）
5. **实测项（做方案时就该量）**：`dsh headless --json` 一次提问的冷启动耗时与首字延迟；`serve-node.ts` 的 SSE 流式改造量；一次典型提问的工具轮数分布（定配额）；`dsh headless --session-id` 续话在并发下的行为。
6. **合规**：模型服务是否公网（决定人名脱敏是否强制）。
7. **边界确认**：你说的"用户与会话管理起来"，是否还包括"**让助手帮管理员去管理用户/会话**"（即给助手写工具）？那与 §1 的只读边界冲突，需要单独拍板 —— 本方案按"管理面归网页端、助手只读"写。

## 14. 风险

| 风险 | 形态 | 对策 |
|---|---|---|
| 服务器 shell 暴露 | 最坏情况：任意看板用户能读写服务器 | 专用 profile + CI 结构断言（§4.1），S13.3 前排期硬门禁 |
| 提示注入 | 数据里藏指令 → 模型去查别人 | 数据范围在服务端（§4.2）；工具只读；不提供 SQL |
| 会话越权 | `--session-id` 读到别人的对话 | 平台会话绑 `member_id` + 续话只认库里的 id（§7.2） |
| 第二套用户体系 | 助手侧另建登录/用户表 | §7.1 明令禁止；权限走角色 |
| "删除"是假的 | 删了平台行，DSH 侧正文还在磁盘 | 删除动作必须连带 DSH 侧（§13-2） |
| 无主会话 | 先接 dsh 后补归属 | S13.2 排在 S13.3 之前 |
| 冷启动慢 | 每次提问等 DSH 引导 | §13-5 实测；必要时二期常驻 gateway |
| 成本失控 | 一个提问几十次工具调用 | 轮数 / 时长 / 并发 / 行数四项上限，超限明确报错（不静默降级成"没有数据"） |
| 口径漂移 | 助手用自己的除法或 SQL 公式 | 投影层只搬运；派生指标一律来自 `shared/metrics.ts` / `shared/price.ts` |
| DSH 升版静默失效 | profile 或 peer 窗口不满足 → 助手无声不答 | 部署 preflight 自检 + 复用 `verify:npm:plugin` 的兼容窗口判定 |
