# 上报性能与队列方案

适用规模：约 20 人，每人每天约 3 亿 token，总计约 60 亿 token/天。本文对应 2026-09-27 的实现。

## 1. 容量先看事件数

数据库每行是一条 usage 事件，不是一个 token。真正决定容量的是每天调用事件数、单批大小、集中补报的并发，以及看板查询的时间窗口。

下面只是容量换算示例，不能替代实际调用量：

| 平均每条事件的 token 数 | 全部门事件/天 | 按 8 小时集中使用计算的平均事件/秒 |
|---|---:|---:|
| 1,000 | 6,000,000 | 208.3 |
| 10,000 | 600,000 | 20.8 |
| 100,000 | 60,000 | 2.1 |

应结合 `/api/v1/stats/overview` 的 `calls`、实际批量大小和峰值补报测试评估部署。缓存 token 仍属于原有四列口径；本次没有修改任何 token 公式。

## 2. 接收方案

流程：客户端 pending/outbox → HTTP 有界队列 → 读取与校验正文 → 数据库鉴权 → 持有身份锁重新鉴权 → 分块 INSERT → 整批 COMMIT → HTTP 200 → 看板读取。

第一阶段使用进程内异步 FIFO，单消费者串行处理上报；不引入 Redis、消息中间件或新数据库表。只有上报排队，查询、登录、管理和健康检查仍由 HTTP 服务正常调度。每个任务之间让出事件循环。

**这是异步排队、提交后确认：HTTP 请求会等待数据库事务完成。** 当前 CLI/插件收到任意 2xx 就会清除本地待投递数据，因此不能在内存入队后就返回 202。服务器崩溃或网络断开而客户端未收到成功响应时，客户端保留并重试；已经提交的重复事件由 `event_id` 主键去重，先到的身份归属不变。

队列在读取正文之前限流，等待项只持有请求，不提前 JSON 解析、校验或打开数据库连接。Node 适配器也改为流式输入，避免在进入队列之前就把所有并发正文拼进 Buffer。此限制约束应用消费和解析，并不宣称能限制操作系统、反向代理或运行时的全部网络缓冲。

| 行为 | 默认值或结果 |
|---|---|
| 容量（执行中 + 等待中） | 64 个请求 |
| 最长等待 | 5 秒；只移除尚未开始的任务 |
| 正文上限 | 32 MiB，含无 Content-Length 的分块上传 |
| 正文读取总时限 | 10 秒；慢上传不能无限占住消费者 |
| 队列满 / 等待超时 / 停止接入 | 503 + `Retry-After: 1` |
| 正文读取超时 | 408；尚未进入鉴权及写事务 |
| 成功响应 | 提交后 200，精确返回 accepted / duplicates / rejected |
| 优雅停机 | 停止接入，等待已入队任务完成或等待超时，再关闭 HTTP |

排队超时不取消已经开始的事务，避免“实际上已提交却声称没写入”。客户端默认 HTTP 超时是 15 秒；若修改服务端等待时间，应一并检查上传、鉴权、数据库提交与客户端超时预算。当前客户端对非 2xx 会保留数据重试，尚未专门解析 Retry-After。

## 3. 实际消除的开销

### 数据库闸门不再扫描整段历史

原来的 `openPortalStore()` 每次都执行事件全表 COUNT，SQLite 还执行全历史外键检查；一次上报的多次鉴权会重复这些工作。

现在普通业务连接仍逐次检查版本、迁移状态、实际表结构及约束，不缓存权限或假定结构永久不变，但不扫描历史行。启动、显式 inspect/迁移仍做完整检查；启动发现历史外键损坏会拒绝。业务写入仍由数据库外键和 CHECK 约束保护。

### SQL 分块批量写入

- MySQL 每块最多 200 行，SQLite 每块最多 40 行，同时按约 512 KiB 的绑定数据目标拆块；单条合法的大记录独立写入。
- 使用位置参数与普通多行 INSERT，保留四个独立 token 列。
- 每块用保存点保护。只有事件主键重复才回退该块逐行处理，精确计算 duplicates。
- 其他 UNIQUE、FK、CHECK、MySQL 非严格模式及截断错误均拒绝确认，整批事务回滚；不使用 INSERT IGNORE。
- 大批次内可以分多条 SQL，但仍然是同一个请求事务；不会在块之间提交半批。

## 4. 数据实时性

上报成功响应之后，统计接口即可读取已提交的数据，没有额外的后台消费延迟或结果缓存。

部门看板每 5 秒刷新，切回浏览器页面立即刷新，隐藏时暂停。全员排行与人员候选共用请求，首页每轮从 4 个请求减为 3 个；人员详情抽屉也跟随刷新，失败时保留旧数据并显示错误。

“页面每 5 秒刷新”不等于事件发生后 5 秒必达。端到端延迟还包括客户端发批间隔、网络及队列：插件默认发批间隔是 10 秒，CLI 由实际运行频率决定。正常插件链路通常还要叠加这段等待。

## 5. 配置与监控

默认配置无需新增环境变量，现有启动方式会自动启用队列。可显式设置：

```bash
ATR_INGEST_MAX_REQUESTS=64 ATR_INGEST_MAX_WAIT_MS=5000 \
  bun run --filter '@ai-token-report/server' start
```

程序嵌入时可用 `createServer({ ingestQueue: { maxRequests: 64, maxWaitMs: 5000 } })`。配置非法会在启动时明确报错。直接使用 `createHandlerFor()` 的嵌入程序退出时应调用并等待 `bundle.close()`；`createServer().stop()` 已接好这一流程。

`GET /api/v1/admin/ingest-status` 返回当前进程的队列容量、执行/等待数量、最老等待时长、上次等待与处理时长、完成/拒绝请求数。需要 `members:read`，Bearer 仍与 token scopes 取交集；普通 appKey 不能访问。响应不缓存，也不返回凭证、姓名或正文。

`scope: "process"` 表示多实例各自计数，重启归零；`completed_requests` 包含已执行完的业务拒绝，不是成功上报事件数。数据最后落库时间继续看现有 diagnostics.lastIngestAt。

观察重点：waiting_requests 是否持续增长、oldest_wait_ms 是否接近上限、rejected_requests 是否增加，以及 HTTP 确认/统计查询 p95。出现持续积压应先排查数据库和大批补报，不要只把队列上限无限调大。

## 6. 验证与复现

真实 HTTP 验证脚本会创建临时 SQLite 数据库，通过 HTTP 创建 20 名人员和独立 appKey，默认每人两批、每批 200 条，合计 8,000 条事件。夹具将这批事件设为 60 亿 token，仅用于验证大数与四列保真，并不表示实际每日只有 8,000 次调用。

```bash
bun run --filter '@ai-token-report/server' verify:ingest
ATR_PERF_HISTORY_RECORDS=20000 bun run --filter '@ai-token-report/server' verify:ingest
bun run packages/core/verify/benchmark-portal-ingest.ts
# 需要本机开发 MySQL 容器或 ATR_V4_TEST_MYSQL_URL；只创建/清理随机隔离库。
bun run packages/core/verify/benchmark-portal-ingest.ts --mysql
```

HTTP 脚本验证每次 ACK 后立即查询同一人员的 calls、四列及 total，重投精确去重、人员稳定归属，以及写入期间统计查询仍能响应。支持 `ATR_PERF_CONCURRENCY`、`ATR_PERF_RECORDS`、`ATR_PERF_ROUNDS`、`ATR_PERF_HISTORY_RECORDS` 调整压力；只使用本次创建的临时库。

本机 HTTP 测试（Windows / Bun / SQLite，包含鉴权、排队与并发统计查询）：

| 场景 | 新增事件/秒 | 上报 ACK p95 | 并发查询 p95 |
|---|---:|---:|---:|
| 最终实现，空库 | 3,086 | 1,257 ms | 140 ms |
| 初轮实现，预填 20,000 条历史 | 2,716 | 1,429 ms | 105 ms |

原始写入微基准（每轮 2,000 条，3 轮中位数；**不包含 HTTP/鉴权/排队**）：

| 运行时与后端 | 原逐行写入 | 批量写入 | 比值 |
|---|---:|---:|---:|
| Bun / SQLite | 30.20 ms | 24.43 ms | 1.24 倍 |
| Bun / MySQL | 1,011.54 ms | 148.84 ms | 6.80 倍 |
| Node / SQLite | 216.62 ms | 39.58 ms | 5.47 倍 |
| Node / mysql2 | 1,094.69 ms | 173.05 ms | 6.33 倍 |

这些是隔离环境的实测，不是生产 SLA，也不能推算多年历史、大正文或全重复重投的最坏延迟。磁盘、数据库网络时延、后台查询并发和时间窗口都会影响结果。

最终回归：`bun test` 891 通过、0 失败、12 个依赖额外 MySQL 配置的测试跳过；全仓及发布脚本类型检查通过。另行运行的真实 MySQL 批量写入检查、SQLite/MySQL HTTP 看板逐位对账（60 项）、Node/mysql2 验证均通过；上报 E2E 35 项、CLI 上报链路 28 项、人员管理 E2E 69 项通过。两个 Web 构建、Portal SSR/图表检查及前端无 zod 产物检查通过。新增正文/队列/Node 流式测试覆盖满队列、超时、停机排空、撤权、UTF-8 分块和真实 HTTP 提前响应。

浏览器在隔离 SQLite 与实际构建产物上完成登录、首页、详情和整页重载验证：新上报后首页及已打开的人员抽屉自动从 1,000/1 次更新为 3,000/2 次；重载恢复会话后再次上报，约 4.1 秒自动显示 7,000/3 次。未手动刷新数据，页面无错误提示。

## 7. 后续扩展边界

当前没有新增表、自动迁移或更换业务库。单消费者限制的是本实例的上报；多实例仍依靠数据库身份锁与主键维持撤权顺序和幂等。

较大风险仍是长时间窗口趋势查询：时间分桶在 JS 中执行，会读取窗口内的事件。数百万事件长期积累后，应基于实测另做可验证的派生汇总、分页或查询计划优化；不能在前端或 SQL 中重写 token 口径，也不能直接用 SQL localtime 替代进程时区规则。单个大事务内的 SQLite 查询延迟也需要单独压测。

只有在确认需要“收到请求后立即 ACK，稍后入库”的独立消费能力时，再考虑持久化 inbox/消息队列：必须先持久化再确认、定义已接收身份与撤权语义、故障重放、队列容量、消费者恢复及看板延迟。这属于另一种交付语义，需要显式数据库迁移和客户端协议设计，不能把当前内存队列直接改成入队即成功。
