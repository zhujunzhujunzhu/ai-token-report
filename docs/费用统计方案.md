## 0. 已定决策

| # | 问题 | 决定 |
|---|---|---|
| 1 | 目标 | **两者都要**：token × 单价估算用于明细下钻；外部账单用于月度对账 |
| 2 | 单价来源 | **入库 + 管理页可维护**，内置表作初始化种子价 |

## 1. 结论：缺的只有单价

费用 = f(token, 单价)。token 一侧**已经就绪**：

- 铁律 3「落库必须存 4 个独立列」恰好是计价的前提。`cacheRead` 与 `input` 单价差约一个数量级，
  当年若合并成一列，今天无法计费。
- `provider` / `model` / `ts` / `member_id` 全部在 `usage_event` 里，维度齐全。

所以本方案的工程重心不在「算」，而在三件事：**单价从哪来、单价表往哪存、未定价怎么暴露**。

> ⚠️ **费用 ≠ 账单。** 本方案算的是 `token × 单价` 的**理论成本**，
> 不是**实际付款**。真实账单含折扣、预付、赠送额度、阶梯价。
> 自建计价**永远不会等于**财务账单 —— 这不是 bug，是定义。
> 因此账单只用于 §7 的月度对账，**绝不参与页面计算**。

## 2. 核心口径设计

### 2.1 计价公式：必须四类分价

```ts
cost = input × p_input + output × p_output
     + cacheRead × p_cacheRead + cacheWrite × p_cacheWrite
```

`cacheRead` 单价通常比 `input` 低约一个数量级，`cacheWrite` 可能更高。
**不存在「一个模型的单价」这种东西** —— 单价是按 token 类型分的四元组。

### 2.2 三条硬约束

**① 绝不落 `cost` 列，查询时按「事件时间 + 单价生效区间」重算。**

与「本地库只定义存储，不定义口径」同一条精神：落库 cost 等于把口径固化进事实表，
且单价一错就**永久错**。单价表带 `effective_from` / `effective_to`，
查询时按事件 `ts` 挑当时生效的单价 —— 这样既不动事实表，历史账单又不会因今天调价而变动。

**② overview 的费用必须逐模型计价后求和，不能用总额算。**

看板的 `overview` 现在是单条 `queryTotals()`（对全表 `SUM`）。
但不同模型单价不同，**「总额 × 平均单价」是一个会静默出错的第二个口径** ——
世上没有「平均单价」。正确做法：服务端内部先按 `provider-model` 分组，
逐组计价后求和。`queryGroups(by: 'provider-model')` 就是这项基础设施。

**③ 未定价必须显式暴露，绝不当 0。**

实测数据里就有现实案例：`dashscope/qwen3.6-plus` 仅 4 次调用，
自有网关或未收录模型更常见。新增与 `unattributedRate` 同构的指标：

```
unpricedRate = 无单价事件的 token 数 / 总 token 数
```

> 🚨 **把未定价当 0，会让「费用偏低」看起来像「省钱了」。**
> 这与「不能把待确认历史当匿名」是同一类错误，是本方案最危险的坑。

### 2.3 附带产出：缓存省了多少钱

```
cacheSaving = cacheRead × (p_input − p_cacheRead)
```

比现有「19.3 倍杠杆」更有说服力，且**不引入新口径**（同属 `cost` 族）。

### 2.4 币种：多币种各自累加，绝不换算、绝不相加

> 🚨 **本节已于 S1 按真实报价修正，并在 v7 补上人民币报价。** 初稿写的是「首版只支持 CNY」，
> 但 S1 拉取 DeepSeek 官方价目（英文页）发现**那里标的是 USD**（见 §2.6），
> 按初稿会把功能对真实数据完全废掉。修正后的做法如下。
> 其后官方**中文页同时给出人民币报价**（单位就是「元 / 百万 tokens」），
> 本仓的页面与录入因此统一按「货币单位 / 百万 token」呈现，内置种子价取**人民币高峰价**。

单价表带 `currency`（ISO 4217 三位大写）。费用**按币种分别累加**：

- `CostSummary.costs` 是 `CostByCurrency[]`，通常只有一项；
- 多币种时用 ` + ` 连接展示（如 `¥2.00 + $6.98`），**不相加、不换算**；
- `unpricedRate` 仍然可跨币种计算 —— **token 数与币种无关**，这是它成立的原因；
- **绝不引入汇率**：汇率是「第二个口径」的典型来源（谁定的汇率、哪天生效、按什么价），
  确需合并币种时单独立项。

若某部署只想看到一个数，做法是**录入单价时统一换算成同一个报告币种**
（一次性的人工决策，留审计），而不是在运行时做两次换算。

### 2.5 数值表示：整数微元

| 环节 | 表示 |
|---|---|
| 单价（库内） | 整数「**微元 / 千 token**」（1 微元 = 1e-6 元） |
| 单价（页面 / 录入） | 「**货币单位 / 百万 token**」—— 与各家价目表同一单位（DeepSeek 官方页写「元 / 百万 tokens」），两者差 1000：`2 元/百万 = 2000 微元/千` |
| 费用累加 | 整数微元：`cost_微元 = Σ(tokens × p_微元) / 1000` |
| 展示 | 只在格式化时除到元 |

> 录入与呈现一律按百万，是因为人能拿着供应商价目表逐字核对（店里写 `¥2 / 百万`，框里就填 `2`）。
> 库里保持「微元 / 千 token」不变 —— 那只是同一笔价的存储写法，换算在
> `packages/web-portal/src/utils/unitPrice.ts` 一处完成（`× 1000` / `÷ 1000`，整数倍无误差），
> 格式化为 `formatUnitPriceMicro()`。

理由：几十万条 × 小数累加，浮点必然出现分位误差。整数域累加在
`MAX_SAFE_INTEGER` 内安全 —— 单价上限 `MAX_MICRO_PER_KTOK = 1e7`（= 10,000 货币单位/百万 token，
是现实最贵模型 `$15/1M` 的约 600 倍余量），对应
`MAX_SAFE_BILLABLE_TOKENS ≈ 9,007 亿`，而本部门实测全体用量是 **23.9 亿**，余量约 380 倍。
超出时 `costMicroForTokens()` **抛 `RangeError` 而不是返回一个已经丢精度的钱数**。

### 2.6 ✅ 高峰 / 低谷两档（v10 已落地；本节由「已知识简化」改写为「已实现」）

DeepSeek 官方价目分**高峰 / 低谷两档，差 2 倍**：

| 档 | 时段（北京时间） |
|---|---|
| 高峰 | 周一至周五（不含法定节假日）**09:00–12:00、14:00–18:00** |
| 低谷 | 其余全部时间，**含周末与法定节假日全天** |

（英文页把同一时段写成 UTC 的 `01:00-04:00` 与 `06:00-10:00`，周一至周五 —— 两者等价。）

**v10 起按真实两档计价**，落点：

| 环节 | 做法 |
|---|---|
| 时段定义 | `shared/price.ts` 的 `PRICE_SCHEDULES`（`deepseek-cn`）：固定 UTC 偏移 + 星期几 + 分钟区间 + 节假日表；**只有这一份定义** |
| 价行 | `model_price` 多五列：`offpeak_schedule` + 四类闲时单价（v10 只加列、不重建表）；**五个字段同生共死**（`offpeakConfigError()` 拒掉半套配置 —— 缺的那档会按 0 元算） |
| 逐事件路径 | `priceRatesAt(price, ts)`（趋势 / 明细 / 离线折叠 / 插件宿主） |
| 聚合路径 | SQL 里由时段表**生成**的 `CASE` 判出 `price_slot`，跟着 `GROUP BY` 一起分组；JS 侧 `priceRatesForSlot()` 取那一档 |
| 一致性 | `core/test/portal-offpeak.test.ts` 用**手算的具体数字**把两侧对上（周一高峰 2000 / 周一闲时 1000 / 周六 1000 / 春节假期里的工作日 1000），并刻意让「用错做法」得出**不同**的数 |

为什么不再走初稿那条「把分类压进 SQL 会和『时间分桶在 JS 侧』的铁律冲突」的推理：
**冲突的是 `strftime(..., 'localtime')` 那类按 OS / SQL 会话时区取值的函数**，而这里用固定偏移的
纯整数算术（`(ts + 28800000) / 60000 % 1440`），两个后端与 JS 逐位一致；
`SELECT` / `GROUP BY` 里的表达式**由同一份时段表生成**，不是手抄一份。

⚠️ 两处**必须知道**的边界：

1. **节假日表要逐年维护**（`PriceSchedule.holidaysThrough` 写明覆盖到哪天）。表过期之后，
   落在工作日高峰窗里的节假日会按**高峰**计 —— 费用偏高；页面在时段说明里写明覆盖日期。
2. **MySQL 的 `/` 是浮点除法**：取整必须走 `dialect.intDiv()`（`DIV`），否则「一天里的第几分钟」
   整体错位、费用按错误的档算，而**不会报错**（`dialect.ts` 差异 5）。

### 2.6.1 基础价（不限供应商）—— 同一期落地

同一个模型常常被多个网关转售（本部门实测：`deepseek-v4.1-flash` 同时来自 `dashscope` 与
`bailian-tpp`），逐个网关抄一遍价既啰嗦又容易漏。v10 起价行的 `provider` 可以是保留值
**`ANY_PROVIDER = '*'`**（**不是**供应商名）：

- **解析**：`resolvePrice()` 先按 `(provider, model)` 精确匹配，命不中才落到 `('*', model)`；
- **取数 SQL join 两次**（`mp_e` 专属 + 在 `mp_e.price_id IS NULL` 前提下 join 一次 `mp_b`）——
  🚨 **绝不能写成 `ON (provider = ? OR provider = '*')`**：那样一条事件会同时命中两行，
  token 与金额一起翻倍，而页面上只是数字变大；
- **两条基础价覆盖同一时刻仍然是冲突**（`findPriceConflicts()` 回 409）；
  基础价与某个供应商的专属价**可以共存**（专属优先）；
- 页面把它渲染成「不限供应商（基础价）」，**绝不把 `*` 直接显示给人看**。

### 2.6.2 🚨 上线顺序：**先部署新服务端，再写价目**

基础价与闲时价都是**新代码才认识**的东西，所以：

| 先做什么 | 后果 |
|---|---|
| 先写 `'*'` 的基础价、后部署 | 老服务端的取数 SQL 只有 `mp.provider = 事件.provider` —— `'*'` 那一行**匹配不上**，于是这批用量从「按 USD 高峰价算」变成**一条都没配上（未计价）**，看板比改之前更差 |
| 先迁移 schema、后部署 | 老进程的 `openPortalStore()` 每次打开都过版本闸门：库一迁完，**还在跑的旧服务会对所有统计请求报错**；它一旦重启还会**拒绝启动** |
| 正确顺序 | 上传 staging → 停 PM2 → 用**新产物**跑 `migrate-db.mjs migrate --confirm-offline` → `deploy:server:apply`（切换 + 起服务 + 健检）→ 最后写价目（`/pricing` 页面或 `POST /api/v1/admin/pricing`） |

实操命令、`CHECKSUM TABLE usage_event` 前后核验与线上现状见
`docs/数据库部署与迁移.md` 的「线上实操顺序」一节。

### 2.7 内置种子价的来源与一处刻意简化

`BUILTIN_PRICES` 取自 DeepSeek 官方定价页中文版
（<https://api-docs.deepseek.com/zh-cn/quick_start/pricing>）的人民币报价
（官方页单位就是「元 / 百万 tokens」），
覆盖 `deepseek-official` 的 `deepseek-v4.1-flash` / `deepseek-flash` / `deepseek-v4-pro`，
**高峰与空闲两档都收**：

| 模型 | 档 | 缓存命中 | 缓存未命中 | 输出 |
|---|---|---|---|---|
| `deepseek-flash` / `deepseek-v4.1-flash` | 高峰 | ¥0.04 | ¥2 | ¥8 |
| 同上 | 空闲 | ¥0.02 | ¥1 | ¥4 |
| `deepseek-v4-pro` | 高峰 | ¥0.30 | ¥9 | ¥27 |
| 同上 | 空闲 | ¥0.15 | ¥4.5 | ¥13.5 |

官方原价目就是「cache hit / cache miss / output」三档，**与四类分价同构**
（`cache_write` 官方不单列，写入按 cache miss 输入计价，故种子价里是 `0`）。

一处刻意简化（管理员必须知道）：**`effectiveFromMs = 0`（视作自始生效）** ——
种子只是让首次部署立刻有数，**管理员应在单价管理页按真实生效日修正**，
否则历史费用会按今天的价重算。

**刻意不收录 `dashscope`（数字集团网关）**：它是转售 / 汇总账单口径，
拿官方零售价套上去会给出一个「看起来像官方价、其实不是自己付的钱」的数字 ——
留空会进 `unpricedTokens`，由页面显式告诉使用者「这部分没算钱」；编数字会让错误藏起来。
⇒ 需要给这类网关定价时，由管理员显式配一条**基础价**（那是人的决定，不是内置默认）。

## 3. 单价表设计

### 3.1 字段

| 字段 | 说明 |
|---|---|
| `price_id` | UUID 主键 |
| `provider` | 与 `usage_event.provider` 同域 |
| `model` | 与 `usage_event.model` 同域 |
| `currency` | ISO 4217 三位大写（实测 DeepSeek 官方中文页给人民币报价、英文页给 USD；多币种各自累加，见 §2.4） |
| `input_micro_per_ktok` | 未命中缓存输入的单价 |
| `output_micro_per_ktok` | 输出单价 |
| `cache_read_micro_per_ktok` | 缓存读单价 |
| `cache_write_micro_per_ktok` | 缓存写单价 |
| `effective_from_ms` / `effective_to_ms` | 生效区间；`to` 为 `null` 表示至今 |
| `created_at_ms` / `updated_at_ms` / `updated_by` | 审计（变更走既有审计表） |

**匹配规则**：`provider` + `model` **精确匹配**，不做子串。
（与「人员筛选是精确匹配」同理：子串会把 `deepseek-v4.1-flash` 和
`deepseek-v4.1-flash-preview` 串成同一个价 —— 那是数据错误，不是便利。）

同一 `(provider, model)` 的生效区间**不得重叠**；重叠由写入时校验拒绝（`409`）。

### 3.2 三级来源与解析优先级

| 场景 | 单价来源 | 解析顺序 |
|---|---|---|
| 服务端（看板 / 上报库查询） | portal 库 `model_price` 表 | 表 → 内置种子 |
| CLI / 本地页 / 插件宿主（离线） | 本地快照文件 | 本地快照 → 内置种子 |

- **内置种子**：`packages/shared/src/price.ts` 的 `BUILTIN_PRICES`。
  **同一份数据同时用于初始化服务端表** —— 单价数字只定义一次，不重复维护两套。
- **本地快照**：`pricing.json`，与 `identity.json` 同思路的**配置文件**，
  **不进 `usage.sqlite`**（本地库是 v3 且「坏了就重建」，而单价无法从日志重扫 ——
  放进去等于重建即丢）。
- **同步命令**：`ai-token-report pricing sync` → `GET /api/v1/pricing`（需 `cost:read`）。

### 3.3 🚨 费用数字必须携带「单价来源」元信息

离线端用快照、服务端用表，**两者一旦不同就会给出两个不同的费用** ——
正是本仓最痛恨的那类不报错的漂移。因此：

> **任何展示费用的地方，都必须能回答「这份费用是按哪份单价、什么时候算的」。**

响应体与页面/终端输出里带上：

```ts
pricingSource: 'db' | 'snapshot' | 'builtin'
pricingSyncedAt: number | null   // 快照同步时刻；db/builtin 为 null
unpricedRate: number             // 未定价占比，见 §2.2③
```

**缺这些字段时不得渲染金额**（与「缺字段必须按 `member` 处理」同一条安全逻辑）。

## 4. 存储与迁移

> 🚨 **本节已于实现期间按仓库真实状态修正。** 动工前发现工作区里另一条工作线
> （`provider_alias` 供应商归一化）**已经占用了 schema v6**，并且它确立的约定与本
> 方案的初稿不同。下面是修正后的做法，**以本节为准**。

### 4.0 仓库实际约定：追加常量留在同一文件，不新开版本文件

`provider_alias` 的做法是把当前版本终态留在 `portal-schema-v5.ts` 里，用
`PORTAL_SQLITE_V6_ADDITIONS` / `PORTAL_MYSQL_V6_ADDITIONS` / `PORTAL_V6_PERMISSION_SQL`
承载，并导出 `portalV6Statements()` / `portalV6TableStatement()` 供**建库与迁移两处**共用。

它**刻意不新建 `portal-schema-v6.ts`**，理由写在文件头：分成两个文件会让
「哪些表属于当前版本」变成两处各自维护，而它们必然漂移。

⇒ 费用统计照此办理：**在 `portal-schema-v5.ts` 里追加 `_V7_ADDITIONS`**，
不新建 `portal-schema-v7.ts`。

### 4.1 🚨 必须升 **v7**，绝不能改动 v6 的 DDL 文本

`readPortalState()` 判定 `current` 的条件是**账本 checksum 与当前受控 DDL 文本一致**。
而 `portalSchemaChecksum()` 是对 `PORTAL_*_V5_SQL + PORTAL_*_V6_ADDITIONS` 求 sha256。

> **往 v6 的追加常量里塞一张表 → checksum 变化 → 现网每一个 v6 库全部落到
> `unsupported` → 服务端拒绝启动。**
>
> 这正是 v4 被定为**冻结基线**的原因，也是 v6 追加被写成独立常量的原因。
> **任何 schema 改动，哪怕只是加一张表，也必须走新版本号。**

⇒ 新建 `PORTAL_SQLITE_V7_ADDITIONS` / `PORTAL_MYSQL_V7_ADDITIONS`（`model_price` + 索引）、
`PORTAL_V7_PERMISSION_SQL`、`portalV7Statements()` / `portalV7TableStatement()`，
并把 `PORTAL_SCHEMA_VERSION` 由 **6 改为 7**。v5/v6 的文本**一字不动**。

⚠️ **同时必须冻结一份 `portalSchemaChecksumV6()`**（= v5 文本 + v6 追加，
即改版前 `portalSchemaChecksum()` 的公式）。否则一个已经迁到 v6 的库，
其账本里记的是「v6 摘要」而函数现在返回「v7 摘要」，永远对不上 ——
它会从「可迁移的起点」退化成 `unsupported`。这与 `portalSchemaChecksumV4` 被冻结是同一件事。

### 4.2 v7 是纯加表，规避了 v5 的三个 MySQL 坑

v7 只做 `CREATE TABLE` + `CREATE INDEX` + 权限行，**不碰 `usage_event`**：

| v5 踩过的坑 | v7 是否受影响 |
|---|---|
| `DROP/RENAME COLUMN` 被 CHECK 约束挡住（errno 3959） | ❌ 不涉及 |
| `RENAME COLUMN` 不改类型 → `verifyCurrent` 最后一步拒绝 | ❌ 不涉及 |
| `CHECK_CLAUSE` 反斜线转义 | ❌ 不涉及 |

连带好处：**不需要逐位校验事件指纹**（不改写任何事件行），
迁移是幂等的（先看目标状态再动手）。备份仍建议执行，但风险等级远低于 v5。

> ⚠️ 唯一要照抄 `provider_alias` 的一处教训：`model_price` **不要用生成列**
> （`verifyTable` 的 `expectedColumns` 只认 DDL 文本里的列，引擎维护的列会让校验报「列数不符」），
> 也**不要用 SQLite 部分索引**（MySQL 没有 `CREATE UNIQUE INDEX ... WHERE`，
> 受控定义必须在两种后端上逐字相同）。

### 4.3 迁移步骤折进「当前版本」这一条账本，而不是各版本一条

仓库的实际结构：**只有一条 `PORTAL_SCHEMA_VERSION` 账本行**，
`upgradeV4ToV5()`（名字已过时，实际做到 v6）按起点状态依次调用
`runV5Sqlite/runV5Mysql` → `upgradeV5ToV6`，**每一步都自检目标状态**，
所以 resume 直接重跑即可，不靠 `last_completed_step`。

⇒ v7 照此办理：新增 `upgradeV6ToV7(store)`，并在 `upgradeV4ToV5` 的
两个分支里都排到 `upgradeV5ToV6` 之后。同时：

- `type SchemaVersion = 4 | 5` → 加 6 / 7
- `tableStatement()` 的 `version === 5 ?` 分支要跟着扩（它现在只区分 5 与「v4」）
- `readPortalState()` 新增一条：`version === 6 && v6 账本完整 && checksum === 冻结的 v6 摘要` → `legacy`
- 🚨 **「基线是否就绪」的判定依据要继续认「账本行/表是否存在」，不是版本号**
  —— 这条已经踩过两次（v5 那次让 MySQL 库 resume 永久卡死）

### 4.4 权限码随 v7 一起 seed

⚠️ **`...112` / `...113` 已被 `providers:read` / `providers:manage` 占用**
（v6 追加里）。费用统计必须用新的 UUID：

| 权限码 | UUID 尾号 | 用途 |
|---|---|---|
| `cost:read` | `...114` | **可见费用**。无此权限时**不返回 `cost` 字段**（不是返回 0） |
| `pricing:manage` | `...115` | 维护单价表 |

权限行**必须幂等**（`INSERT ... SELECT ... WHERE NOT EXISTS`）：
MySQL 的 DDL 会隐式提交，迁移中途崩过一次就会重跑，裸 `INSERT` 会撞主键。

同步改动点：
- `packages/server/src/identity/types.ts` 的 `PERMISSIONS` 数组
- `packages/web-portal/src/views/rolesModel.ts` 的中文标签（否则角色页显示不出名字）
- `packages/server/src/admin-route.ts` 的路由 → 权限映射

> ★ 注意 `cost:read` **不加进** `APP_KEY_SCOPES`。
> appKey 是插件/CLI 上报用的，范围固定为 `usage:write` + `stats:read`；
> 费用可见性不该由上报凭证携带。

## 7. 账单对账（决策 1 的 B 面）

### 7.1 🚨 账单与估算严格隔离

账单数字**只出现在对账报告里**，**绝不进入**页面、接口响应或 CLI 统计输出。
两者混用 = 页面上同时存在两个来源的费用 = 第二个口径。

### 7.2 `packages/server/scripts/reconcile-bill.ts`（✅ 已实现）

```bash
bun run reconcile:bill -- --portal-db <上报库路径 | mysql://…> --bill <账单.csv> \
  --period 2026-01 [--tolerance-percent 0.5] [--json]
```

估算侧**不自己算钱**：直接取 `openPortalStats(..., withCost)` 的 `costTotals()` 与
`costByGroup('provider-model')`，格式化只用 `formatCostMicro()`。全脚本**唯一**的减法
是 `sameCurrencyDiff()`（同一币种内「估算 − 账单」），注释点明「这是对账，不是计价」；
**从不跨币种**相减或相加。

| 输出项 | 状态 | 作用 |
|---|---|---|
| 币种 / 估算 / 账单 / 差额 / 差额占比 | ✅ | 判断单价表是否需要调整 |
| 未计价占比 + 未配价目标清单 | ✅ | 解释差异的**首要嫌疑**（先补价再对账） |
| 差额最大的前 5 个 `provider/model` | ✅ | 定位是调价未跟进还是折扣所致 |
| 账单文件自洽性（总额行 vs 逐目标行之和） | ✅ | 财务文件本身需要人处理时明说 |
| 只在单侧出现的币种 / 估算侧零用量 | ✅ | 防「比了个空」 |
| 按 key ↔ 人映射的对比 | ❌ 未做 | 账单 CSV 里没有本仓的人名，无法可靠对应 |

**约定**（都被测试钉住）：

- **CSV 表头**：前 3 列 `period,currency,amount` 逐字相符，后 3 列必须是
  `provider,model,note` 的**前缀**（顺序固定）。`period,currency,amount,note` 这种
  「跳过 provider/model」的表头**会被拒** —— 放宽成「子序列」就会出现「把备注列
  当成 provider 读」的静默错配，而它看起来只是「这个目标没对上」。
- 坏行**一律报错**（带物理行号）并回退出码 2，绝不跳过：跳一行会让「少比了一行」
  看起来像「完全一致」。
- **窗口**是本地自然月 `[1 号 00:00:00.000, 次月 1 号零点 − 1ms]`，两端都含
  （与 `query.ts` 的 `ts>=since / ts<=until` 一致），并**打印出来**（含 epoch ms）。
  刻意不用「本月最后一天 23:59:59.999」：闰年 / 大小月上会少比一天。
- **退出码**：`0` 一致或差额在阈值内、`1` 存在差额（**不是崩溃**，末行明写）、
  `2` 用法 / 输入 / 环境错误。所有异常都映射到 2，保证 1 只表示「有差额」。
- **未计价不影响退出码**：它不是差额，而是「差额可能来自这里」的线索。
  改成「有未计价即 1」会让脚本在有未配价模型的月份里永远失败。
- **只读**：运行前后上报库 SHA256 不变、不产生 `-wal/-shm`（有测试断言）。
- `--portal-db` 是不存在的路径时**立刻报错**：`openPortalStats()` 对不存在的
  SQLite 路径会**静默新建一个空的 v7 库**并回答「零用量」—— 那会把「路径写错」
  伪装成「这个月没有用量」。脚本用 `assertPortalTargetExists()` 兜住（见 §9 风险 15）。

对账**不自动回写**单价表；调整单价是人工决策，走管理页，留审计。

- **取数三条路径**（`core/src/db/query.ts` + `portal.ts`，`PRICE_TABLE = 'model_price'`）：
  1. SQL 可分组维度（provider / model / provider-model / user / group）走 JOIN 聚合；

  effective_from_ms, effective_to_ms FROM model_price) mp`，按 `(分组键, price_id, currency)` 分组，

### 12.3 实现期间顺带修掉的三个真缺陷

**① `CREATE UNIQUE INDEX` 语句此前没有任何迁移路径会执行它**（`ensureIndex` 的正则与两处
`startsWith('CREATE INDEX')` 过滤都跳过了它）。它不影响 SQLite（`verifyCurrent` 只比对
`sqlite_master.sql` 全文、**从不比对索引**），只在 MySQL 上表现为
「迁移明明做完了却不算成功」。影响 **v5 以来的所有迁移路径**，不只是 v7。
详见 `AGENTS.md` 的 MySQL 第 6 条坑。

**② 单价表与用量表有同名列（`provider` / `model`）**（S5 取数时被新测试抓到）：
直接 JOIN 会让维度表达式里的**裸列名变成歧义列**（实测 SQLite
`ambiguous column name: provider`、MySQL errno 1052），于是「按供应商 / 按模型看金额」
整条路径直接不可用。修法是给单价表起**别名列**的子查询（`provider AS mp_provider`…）。
注意**两个后端都会报，它不是方言差异**，所以没有归进 `AGENTS.md` 那份
「只有活体 MySQL 才会暴露」的清单，而是单独记进「非显而易见的约束」。

**③ `packages/server/tsconfig.json` 的 `include` 只覆盖 `src/**/*.ts`**（S8 落地时发现）：
`scripts/**` 与 `test/**` 里的类型错误**根本不会进 `bun run typecheck`** ——
也就是说 `reconcile-bill.ts`、`migrate-db.ts`、`import-credentials.ts` 这些**会真跑**的脚本
一直处在「只有运行时才会发现问题」的状态。已把 `scripts/**/*.ts` 纳入（实测 0 错误），
`test/**` 暂时不纳入：那批端到端脚本有一片既有的 `unknown` 类型错误
（响应体解析处），顺手加进来会让「7 包全绿」变成一片红，那是独立的一轮清理。

> 这三条都不是本方案的需求，而是**做需求时被新测试与真跑抓出来的**：
> ① 是 MySQL 迁移路径的问题、② 是金额取数路径的问题、③ 是验收链路本身的问题。
> 共同点是**它们在 SQLite + 单测下全是绿的**。

| 9 | 模型 ID 改名 → 单价失配 | 失配即计入未定价并告警，**绝不回退到模糊匹配** |
| 10 | 改 v6 DDL 让现网库全变 `unsupported` | 只走 v7；v5/v6 文本冻结；冻结 `portalSchemaChecksumV6()` |
| 11 | 高峰/低谷未区分 → 低谷时段费用虚高约 2 倍 | ✅ **v10 已解决**：时段表 + 四类闲时单价按行配置（§2.6）；SQL 侧时段表达式与 JS 侧 `isPeakAt()` 由同一份时段表生成，`portal-offpeak.test.ts` 用手算数字对上。**残余**：节假日表要逐年补（`holidaysThrough` 写清覆盖到哪天，过期会把节假日按高峰计） |
| 12 | 整数溢出算出一个不准的钱数 | `MAX_SAFE_BILLABLE_TOKENS` + `RangeError`，绝不静默 |
| 13 | **金额取数是区间连接，代价约 O(事件数 × 单价行数)** | 单价只有几十行，实测可接受，**刻意接受**；真优化要给 `usage_event(provider, model)` 加索引，那是 schema 变更，不在这一期做 |
| 14 | **单价区间重叠时一条事件被算两次** | 写入路径由 `findPriceConflicts()` 回 409 挡住，所以只可能来自**直接改库**；不为此加运行时去重 —— 那会把「有人改了库」这件事掩盖掉 |
| 15 | **只读入口会写盘**：`openPortalStats()` 拿到**不存在的 SQLite 路径**时会静默新建空 v7 库，把「路径写错」伪装成「这个月没有用量」 | 对账脚本用 `assertPortalTargetExists()` 提前报错；MySQL 侧无法预检，改为打印「估算侧零用量」告警。**未改 core**（那会动到服务端启动路径，服务端本来就需要初始化空库）—— 后续若要给只读消费者一个「不许建库」开关，应加在 `openPortalStats` 这一层 |
| 16 | **离线端与看板读的不是同一份价**（快照 vs `model_price` 表） | 金额永远与 `pricingSource` / `pricingSyncedAt` 一起出现；退回内置种子价时**显式告警**。本机实测：内置种子价只覆盖 `deepseek-official`，真实数据是 `dashscope` ⇒ 退回时命中率 0%、`unpricedRate` 必然是 100% |
| 17 | **金额让本地取数变慢**（本地页每次请求多一次全量记录折叠，实测 2.37 万条 +56ms） | **刻意接受**：按 `(provider, model)` 分组后乘以「一个价」正是被禁止的算法，而它恰好是「不取记录」的那条路。真嫌慢要给 `usage_event` 加索引，那是 schema 变更 |
| 18 | **没配置上报的机器上，内置种子价被当成真金额** —— 它的价只覆盖 `deepseek-official` 那几个模型，而以 Claude Code / Codex / Trae / WorkBuddy 为主的机器上，算出来的数既不是这些模型的价、也不是这个部门谈的价，却会以一个「看起来正常」的金额出现在第一屏 | 本地页（`/api/local/stats/*`）加一条**配置门禁**：未署名（`<dataDir>/identity.json` 不存在）= 没配置上报 ⇒ `cost` 三个接口**整块不下发**（缺席，不是 `0`），且**连单价文件都不读、连记录都不物化**。页面/CSV 靠既有的「字段在不在」三态自动收掉四处费用 UI，前端零改动。⚠️ 这是**产品口径开关，不是权限**（`/api/local/*` 只监听回环、无鉴权）；部门看板与 CLI / 插件面板不受影响（它们的价来自库里的 `model_price` / 各自的数据目录快照） |
| 19 | **基础价被写成 `OR` 匹配**（`ON (provider = ? OR provider = '*')`）→ 一条事件同时命中专属价与基础价，token 与金额**一起翻倍**，而页面上只是数字变大 | 取数 SQL **join 两次**，基础价那一侧带 `mp_e.price_id IS NULL`；`portal-offpeak.test.ts` 断言「有专属价时基础价不参与」且总 token 恰好等于事件数 × 每条 token。**绝不许改回 `OR` 写法** |
| 20 | **闲时半套配置**（只有时段表、或只填了两类闲时价）→ 缺的那几档按 **0 元**算，费用静默偏低（0 是合法单价，计价函数不报错） | 写入路径与页面共用 `offpeakConfigError()`：五列必须同进同出，服务端回 `400`；快照解析遇到半套配置**整份拒绝**；`unitPrice.ts` 的 `hasOffpeak()` 也只认「五个都齐」 |
