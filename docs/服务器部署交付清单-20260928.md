## 零、子路径部署的两个坑（本次踩过并已修复）

页面挂在反向代理**子路径** `/ai-token/` 下，与根路径部署有两处必须改的地方。
两处都已修好并固化进代码，此处记录以免将来重蹈覆辙。

### 0.1 前端产物必须是相对子路径的（`vite.config.ts` 的 `base`）

Vite 默认 `base: '/'`，产物里写的是**绝对路径**：

```html
<script src="/assets/index-xxx.js">   <!-- 浏览器去站点根取 -->
```

浏览器在 `/ai-token/` 页面下会请求 `http://117.72.173.21/assets/...`，
而站点根属于同实例上**别的应用**（实测拿到若依的 `index.html`，
`Content-Type: text/html`）⇒ 模块脚本 MIME 校验失败 ⇒ **页面一片空白**。

修复：`base` 由 `DSH_PORTAL_BASE` 注入，构建时传 `/ai-token/`：

```bash
DSH_PORTAL_BASE=/ai-token/ bun run build:portal
```

根路径部署不传即可，行为与原来逐字相同。

### 0.2 前端 API 路径也必须带前缀（`src/api/request.ts`）

`base` **只管静态资源**，不会改 `fetch('/api/v1/...')`。这些请求同样会打到站点根，
被别的应用接走 —— 现象是「服务端返回了非 JSON 响应」，看起来像后端坏了。

修复：在 `send()` 里用 `import.meta.env.BASE_URL` 拼前缀（与静态资源同源，
不可能漂移）。各 api 模块继续写根相对路径，无需知道自己在哪个子路径下。

### 0.3 nginx：正则 location 不能用带 URI 的 `proxy_pass`

```nginx
# ❌ 语法错误：nginx 报 "proxy_pass cannot have URI part in location given by regular expression"
location ~* ^/ai-token/assets/ { proxy_pass http://127.0.0.1:8790/assets/; }

# ✅ 改用前缀 location（前缀 location 允许带 URI）
location /ai-token/assets/ { proxy_pass http://127.0.0.1:8790/assets/; }
```

`proxy_pass` 末尾的 `/` 决定是否**剥离**匹配到的前缀：

| 写法 | 服务端收到的路径 |
|---|---|
| `proxy_pass http://127.0.0.1:8790;` | `/ai-token/assets/...`（**不剥离**，服务端找不到文件 → 回落到 index.html） |
| `proxy_pass http://127.0.0.1:8790/;` | `/assets/...`（**剥离**，正确） |

实测症状：直连 8790 返回 `text/javascript` 158356 字节，
经 nginx 却返回 `text/html` 887 字节（index.html）—— 就是这个尾斜杠导致的。

### 0.4 认证 Cookie 的 `Path` 必须带上子路径前缀（最隐蔽的一个）

**症状**：页面能打开、验证码图片正常显示，但**登录永远失败**，
提示「验证码错误或已过期」——即使验证码填对了也一样。

**根因**：服务端原先把认证 Cookie 的 `Path` 写死为 `/api/v1`：

```js
setCookie(c, captchaCookie, binding, { path: '/api/v1' })
```

子路径部署时，浏览器发出的请求是 **`/ai-token/api/v1/auth/login`**，
它**不以 `/api/v1` 开头** ⇒ 浏览器**根本不发送这个 Cookie** ⇒
服务端拿不到 `binding` ⇒ 验证码校验必然失败。

**为什么极难发现**：

| 观察点 | 表现 |
|---|---|
| 浏览器控制台 | **没有任何报错** |
| 服务端日志 | 请求收到、返回 400，一切"正常" |
| Cookie 存储 | **Cookie 确实存在**，`path=/api/v1` 看起来完全合理 |
| 只有抓请求头 | 才看到 `cookie=(无)` |

**修复**：`Path` 由 `ATR_PORTAL_ORIGIN` 的**路径段**推导
（该变量是部署方已配好的公开地址 `http://host/ai-token`），
所以前缀只有一个真源，不会出现「改了环境变量却忘了改 Cookie」的漂移：

```js
const cookiePath = deps.cookiePath ?? (() => {
  if (!deps.portalOrigin) return '/api/v1'
  const prefix = new URL(deps.portalOrigin).pathname.replace(/\/+$/, '')
  return prefix ? `${prefix}/api/v1` : '/api/v1'
})()
```

根路径部署时结果仍是 `/api/v1`，**行为逐字不变**。

⚠️ 同一个 `path` 必须同时用于 `setCookie` 和 **`deleteCookie`** ——
两者不一致时浏览器不认删除指令，Cookie 会一直残留。

**实测证据**（修复后）：

```
set-cookie: atr_portal_captcha=...; Path=/ai-token/api/v1; HttpOnly; SameSite=Strict
```

Playwright 抓到的实际请求头：

```
POST /ai-token/api/v1/auth/login  cookie=★atr_portal_captcha=Wsb89EkdZyXJw2SsH8hxq81VGfzAiyL
```

### 为什么服务端必须用 Node 22

`packages/core/src/decode.ts` 使用了 `node:zlib` 的 `zstdDecompressSync`，
该 API **Node 22.15+ 才有**。Node 20 加载产物会直接崩：

```
SyntaxError: The requested module 'node:zlib' does not provide an export named 'zstdDecompress'
```

### 为什么必须用 MySQL 8.0

v4 表结构（`portal-schema-v4.ts`）使用 `utf8mb4_0900_bin` 与 145 个 `CHECK` 约束。
MySQL 5.7 **两者都不支持**——实测 `ERROR 1273: Unknown collation`，
且 CHECK 约束被**静默忽略**（非法 UUID 能直接写进去）。
