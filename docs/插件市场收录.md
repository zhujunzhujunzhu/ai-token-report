> 目标：让 `dsh-plugin-token-report` 出现在 DSH「设置 → 插件市场」的**发现**页，
> 用户能一键安装。本文是这次收录的**提交物 + 操作手册 + 验收清单**，
> 事实依据来自 2026-10-04 实测（市场 `dshmarket@1.66.8`、精选列表仓库源码）。

## 1. 先看清链路：市场没有「官方审核」

| 环节 | 是什么 | 谁决定 |

市场 README 原话：「这个仓库是市场应用本身，不是插件目录……请去 awesome-dsh-plugin 提 PR」。
所以**唯一要做的投稿动作就是那一个 YAML**。

放进 awesome-dsh-plugin 的 **`data/plugins/`** 目录：

```yaml

category: usage

With a self-hosted portal URL and an app key it also reports usage events to that portal; with neither configured it collects nothing.   zh: 'DSH 的 token 用量面板：输入框上方一条用量条，点开是计费总量、趋势图、按模型/项目/来源的分组明细与自定义日期范围，数据来自本机 DSH / Codex / Claude Code / Trae / WorkBuddy 的会话日志；填了自建服务端地址与 appKey 后，用量事件会实时上报到那个服务端，两者都没配时一个字节都不采集；另提供 token_usage 工具与 ctx.tokenReport 服务。不采集对话内容。'

**注意**：

- `description` 里含 `: `（冒号加空格）必须加引号 —— 上面已经加了。
- **不要**写 `npm:` 字段：映射由站点自动探测，手写会被校验拒绝。
- 一个 PR 最多 3 条；只加自己这一条，不要动别人的条目。
- 分类取值表里有 `usage`（站点上显示为 Usage & Billing），正是本插件的位置。

## 3. 站点怎么认到 npm 包（决定了包名不能解耦）

站点脚本 `scripts/probe-npm.mjs` 对每条目的 `url` 做这件事：

```js
const sub = repoPath.includes('/tree/') ? repoPath.split('/tree/')[1].replace(/^[^/]+\//, '') : null
const pkg = await fetchJson(`https://raw.githubusercontent.com/${repo}/HEAD/${sub ? sub + '/' : ''}package.json`)
const name = pkg.name                       // ← 直接读**被收录子目录**里的包名
// 要求 registry 上存在该包，且它的 repository 指回本仓
```

⇒ **`packages/dsh-plugin/package.json` 的 `name` 必须等于已发布的 npm 包名**
（这就是 0.9.0 把仓内包名从 `@ai-token-report/dsh-plugin` 改成 `dsh-plugin-token-report` 的原因）。
不一致时映射为空，市场会把「一键安装」退化成源码安装
（`github:…#path:/packages/dsh-plugin`）—— 而本仓源码包依赖 `workspace:*`，那条路**装不上**。

## 5. 发布新版 + 提 PR 的顺序（不能反）

站点与市场读的是**仓库 HEAD** 与 **npm registry**，所以：

```bash
# ① 全量验收（发布前必跑；先构建再跑 verify，verify 装的是 dist）
bun run typecheck && bun test
bun run --filter 'dsh-plugin-token-report' build
bun run packages/dsh-plugin/verify/verify-plugin.ts          # 79 项
bun run packages/dsh-plugin/verify/verify-cordis-load.ts     # 11 项 ★ 与官方 OTel 共存
bun run packages/dsh-plugin/verify/verify-resolution.ts      # 7 项
bun run packages/dsh-plugin/verify/verify-client-bundle.ts   # 40 项
bun run build:npm:plugin && bun run verify:npm:plugin        # 真 Node 装载
bun run publish:plugin:dry                                   # 只断言 tarball，不发布

# ② 真发布：先 next 再 latest（凭证走 ~/.npmrc）
bun run publish:plugin:next
bun run publish:plugin

# ③ 推仓库（含改名、去互斥、0.9.0 版本号、截图声明），**并进 main**，然后去 awesome-dsh-plugin 提 PR

# ④ 收录预检：提 PR 前后各跑一次（会分别对 origin/main 与当前 HEAD 各算一遍 npm 映射）
bun run packages/dsh-plugin/verify/verify-market-entry.ts
```

### 5.1 顺序为什么不能反（2026-10-04 实测）

预检脚本对两个版本各算一次 npm 映射，结果如下 —— 这就是「必须先并进 main」的硬证据：

| 站点读到的版本 | 子目录包名 | 站点结论 |
|---|---|---|
| `origin/main`（**今天**） | `@ai-token-report/dsh-plugin@0.8.0` | ❌ registry 404（这个包名从没发布过）→ 市场只能给源码安装 `github:…#path:/packages/dsh-plugin`，而本仓源码包依赖 `workspace:*`，**装不上** |
| 本分支 HEAD（并进 main 之后） | `dsh-plugin-token-report@0.9.0` | ✅ 映射成立 → `dsh plugin --profile web add dsh-plugin-token-report` |

原因是站点脚本读的是
`https://raw.githubusercontent.com/<repo>/HEAD/<sub>/package.json` —— **`HEAD` 就是默认分支**：
只推特性分支时，站点眼里什么都没变。

还有第二条同样致命的时序：市场卡片与一键安装用的是 npm 上的 **`latest`**。
预检显示，即使 main 已经改名，只要 **0.9.0 还没发布**，市场会装到的仍是 **`0.8.0`**
—— 那一版正是「必须手工禁用官方 OTel 才能用」的互斥版。

⇒ **正确顺序：先发 0.9.0 → 再把分支并进 main → 最后提 PR**（并完再跑一次预检，`origin/main`
那条应从 ❌ 转 ✅）。

> ⚠️ `verify:npm:plugin` 需要一棵含 `@deepseek-ai/*` 的宿主模块树。
> 桌面端把宿主装在 `app.asar` 里，`~/.bun/install/global` 那份联接可能是悬空的。
> **实测结论：从 `app.asar` 解出来的树不够用** —— asar 里有 126 个 0 字节的
> `package.json`，`dsh-app-boot` 扫描安装范围时会 `JSON.parse` 失败
> （`Unexpected end of JSON input`），真宿主起不来。只有 `verify:npm:plugin`
> 这种「按名解析几个包」的用例能靠它跑通。
>
> **能用的做法**（实测通过，`verify-startup.ts` 也是这么跑绿的）：
>
> ```bash
> mkdir /tmp/dsh-host && cd /tmp/dsh-host
> echo '{"name":"dsh-host","private":true}' > package.json
> bun add @deepseek-ai/dsh@0.2.0-rc.2        # 529 个包，约 66s
> export ATR_DSH_MODULES=/tmp/dsh-host/node_modules
> ```
>
> 用这棵树跑 `verify-startup.ts` 的实测结果：真实 `dsh web` 2.8s 启动，
> profile 里**官方 OTel 保持启用**，面板三条查询 cold 383ms / hot 43ms / detail 30ms
> 全部返回 `calls=5000`、`total=475000`，日志无 `duplicate loader entry` /
> `plugin tree failed` / `ClientPackageCompositionError` ——
> 即「官方 OTel 与插件同时在组装里，宿主照常启动」。
>
> `verify-live-dsh-report.ts`（真模型 + 真部门服务端）还需要
> `ATR_VERIFY_PORTAL_URL` / `ATR_VERIFY_TOKEN` / `ATR_VERIFY_NAME` 才能实跑；
> 它已改成**不再禁用 OTel**，并在起宿主前用 `--dump-config` 断言
> 「官方后端在组装里且没被禁用」——否则「上报成功」既可能是共存，也可能是它根本没装进来。

**PR 标题**：`submission: dsh-plugin-token-report`

**PR 正文模板**：

```markdown
Adds `dsh-plugin-token-report` (Usage & Billing).

- Monorepo subpackage: https://github.com/zhujunzhunzhu/ai-token-report/tree/main/packages/dsh-plugin
  (declares `dsh.bundle` in its package.json; `cordis.patch.yml` ships with the bundle)
- npm: `dsh-plugin-token-report` (repository points back at this repo)
- Installs with: `dsh plugin --profile web add dsh-plugin-token-report`
- It does not register the `sessionTelemetry` service, so it coexists with the built-in
  `dsh-session-telemetry-otel` backend — no profile patch needed.
- Screenshots declared in `packages/dsh-plugin/screenshots.json`.
```

### 5.3 提 PR 时要避开的三个「静默跳过」陷阱（他们 CI 注释里点名的）

1. **只提交 `data/plugins/<owner>__<repo>.yml`，别手工改 README**：README 是生成物，合并后由
   `sync-readme.yml` 在 main 上重生成；改了反而要求 `--check` 严格一致。
2. **文件名必须以 `.yml` 结尾、且只能放在 `data/plugins/` 下一层**：`readEntries()` 只 glob
   `data/plugins/*.yml`，扩展名不对或多一层目录都会**不报错地**被跳过（他们的注释记录了两次真实事故）。
3. **提交前先把 fork 与上游 main 同步**：落后太多的 fork 会连带「删掉」别人的条目，触发
   stale-fork 守卫（删 >2 条且多于新增即失败）。

### 5.5 一个意外收获：0.9.0 的产物不再 import 任何 `@deepseek-ai/*`

P1-a（不再注册 `sessionTelemetry`、改订阅宿主事件流）的直接后果，实测：
`dist/index.js` 里 **0 条** `from "@deepseek-ai/…"`；而已安装的 0.8.0 必须解析
`@deepseek-ai/dsh-session-telemetry`。

第五层验证 `diagnose-boot.ts desktop` 把这件事照了出来：这台机器的 desktop profile 里
**`@deepseek-ai/*` 联接已全部悬空**（DSH Desktop 自己从 `app.asar` 加载，所以照常工作；
但任何**独立 Node 进程**按那个 profile 解析都会失败 —— `dsh-base` / `dsh-web-app` /
`dsh-better-sidebar` 与 0.8.0 的 token-report 全都报 `Cannot find module`）。
⇒ 升级到 0.9.0 之后，插件在这种破损布局里反而**能 import 成功**；peer 声明从此只剩
「兼容闸门」的作用（由 `dsh-app-boot` 在装载期判定），不再是 import 期的硬依赖。

同一天还补跑了「tarball 真启动」：

```bash

ATR_DSH_MODULES=<真宿主树> bun run packages/dsh-plugin/verify/verify-profile-boot.ts <tgz>

### 5.6 用户的真实路径：从市场装到的 0.8.0 → 升到 0.9.0（A/B 实测）

用**真 DSH CLI**（`dsh plugin add`）+ npm 上的真 0.8.0 + 本地 0.9.0 tarball，
在同一台机器、同一个临时 profile 上做 A/B；环境里**官方 OTel 全程启用**，
并刻意写 identity + `DSH_TOKEN_REPORT_APP_KEY`（这正是「部署配置里带了凭证」的形态）：

| | 装的是 | 宿主日志 | 结论 |
|---|---|---|---|
| A | npm 上的 **0.8.0** | `session-telemetry-otel (…): Error: service "sessionTelemetry" has been registered at <token-report>` | 两个 telemetry 后端抢同一个服务名 —— **官方 OTel 这条入口加载失败**（这台宿主的版本会记下错误并继续跑；团队机器上出现过整个 DSH 起不来的那种表现，取决于哪个后端先注册） |
| B | 升级到本地 **0.9.0** | **一行冲突都没有** | 不抢名字 ⇒ 两边各自工作 |

升级本身：`dsh plugin --profile web add file:<0.9.0.tgz>` → `+ dsh-plugin-token-report 0.9.0`，
`dsh.profile.bundles` 里**只登记一次**；0.9.0 的发布清单里**已经没有**
`@deepseek-ai/dsh-session-telemetry` 这条 peer（0.8.0 有）。

⚠️ 本轮探针没在日志里抓到面板数据通道那行（`/api/tokenReport.stats`）——
面板取数由 `verify-startup.ts`（真宿主、面板三条查询各 5000 条）与
`verify-profile-boot.ts`（tarball → 临时 profile → HTTP 200）覆盖，这里不重复断言。

3. 在一台干净机器/干净 profile 上 `dsh plugin --profile web add dsh-plugin-token-report`：
   **宿主能起来**（官方 OTel 保持开启）、面板出数、填服务端地址 + appKey 后开始上报；
4. 卡片上的「能力清单」出现 `network` / `fs-read` / `fs-write` / `env` 属预期（静态扫描的披露，不是判决）。

## 7. 上架之后

- **发版即更新**：市场按 npm 版本对比检测更新，改完发新版即可，不必再动列表。
- **截图**：改自己仓库的 `screenshots.json` 即可，下一次站点构建自动生效（不用提 PR）。
- **收录不是永久的**：仓库消失、归档或长期停更会被定期扫描清理下架。
- **下架/回滚**：把那条 YAML 删掉再提一个 PR 即可；npm 包**不要删** —— 它是唯一可用的安装面。
