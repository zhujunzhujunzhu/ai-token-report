# 汇总表设计规格（Portal v8）

> **状态：已实现**。DDL 在 `packages/core/src/db/portal-schema-v8.ts`，
> 构建与增量补齐在 `rollup.ts`，查询路由在 `portal.ts`（`#rollupUsable()` /
> `#rollupSeries()` / `hourOfDay()`），接口在 `stats-route.ts` 的
> `GET /api/v1/stats/hour-of-day`。
> 测试：`packages/core/test/rollup.test.ts`（14 项）+ `packages/server/verify/verify-rollup.ts`（16 项活体）
> + `packages/server/verify/verify-v8-migration.ts`（15 项迁移/回滚）。
>
> 性能依据与实测数字见 `docs/性能：MySQL上报库摸底与优化方案.md`
> （§6 线上盘点、§7 两需求、§8.2 汇总表的行数与收益）。
>
> ## 已定稿的决定（2026-10-01）
>
> | 项 | 决定 | 影响 |
> |---|---|---|
> | T2（小时粒度）保留窗口 | **30 天** | 单日曲线与近 30 天的时段分布都由汇总表服务 |
> | T3（时段折叠）是否带「工作日/周末」 | **带**（`day_kind` 两值，不是 7 个星期几） | 能过滤掉周末；行数 ×2 |
> | 时区 | **服务器进程本地时区**，与 `toDayKey()` 同源 | 不引入新配置；改时区需全量重建（版本键里带上时区） |
> | `sessions` 口径 | **走原始表**，绝不由汇总表相加 | 跨天会话不会被重复计数；慢的那一条路径保持精确 |
>
> ⚠️ 一处待确认：需求里既选了「T3 带工作日维度」又选了「只要一天中的第几小时」。
> 本规格按**带 `day_kind`（工作日/周末两档）**实现 —— 它让「工作时段」能排除周末，
> 代价只是行数 ×2（T3 本来就只有百 KB 量级）。若不需要，删掉这一列即可。

## 1. 三张汇总表

统一约定（照抄本仓既有规矩）：

- **只存原始列的和**：`calls`、四项 token、`reasoning_tokens`、`lo` / `hi`。
  **绝不存派生指标**（命中率、均价、金额一律查询期现算）。
- **归属只存 `member_id`**（稳定 ID）；分组（多对多）在**查询期** JOIN
  `member_group_assignments` 展开 —— 写进汇总行会让一个事件复制成多行、`SUM` 静默放大。
- **时间键在 JS 侧算**（`aggregate.ts` 的 `toDayKey()` / `toHourKey()`），
  入库时就用它算出 `day_key` / `hour_of_day` 落库；**绝不用 SQL 的
  `DATE(FROM_UNIXTIME())` / `HOUR()`** —— 那正是 `query.ts` 花大力气避开的时区分叉。
- 受控 DDL 变更 = 新 schema 版本（**v8**）+ 显式迁移 + checksum；
  **绝不自动重建**（这是本仓铁律）。

### 1.1 T1 `usage_rollup_day`

```sql
CREATE TABLE usage_rollup_day (
  day_key           DATE         NOT NULL,   -- 本地日（toDayKey()）
  member_id         CHAR(36)     NOT NULL,   -- 未归属用 '' 哨兵（主键列不能 NULL）
  provider          VARCHAR(255) NOT NULL,   -- 上报原值，不做归一化
  model             VARCHAR(255) NOT NULL,
  calls             BIGINT       NOT NULL,
  input_tokens      BIGINT       NOT NULL,
  output_tokens     BIGINT       NOT NULL,
  cache_read_tokens BIGINT       NOT NULL,
  cache_write_tokens BIGINT      NOT NULL,
  reasoning_tokens  BIGINT       NOT NULL,
  lo                BIGINT       NOT NULL,   -- 该格内 MIN(ts)
  hi                BIGINT       NOT NULL,   -- 该格内 MAX(ts)
  PRIMARY KEY (day_key, member_id, provider, model),
  KEY idx_rollup_day_member (member_id, day_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_bin;
```

服务：长窗口（≥3 天）的趋势 / 排行 / 分布 / 金额。
实测（300 万行 / 300 人 / 365 天）：**10 634 行 / 2.5 MB**，查询 **191~485×**。

### 1.2 T2 `usage_rollup_hour`

```sql
CREATE TABLE usage_rollup_hour (
  day_key           DATE         NOT NULL,   -- 本地日
  hour_of_day       TINYINT      NOT NULL,   -- 0~23（本地小时）
  member_id         CHAR(36)     NOT NULL,
  provider          VARCHAR(255) NOT NULL,
  model             VARCHAR(255) NOT NULL,
  calls             BIGINT       NOT NULL,
  input_tokens      BIGINT       NOT NULL,
  output_tokens     BIGINT       NOT NULL,
  cache_read_tokens BIGINT       NOT NULL,
  cache_write_tokens BIGINT      NOT NULL,
  reasoning_tokens  BIGINT       NOT NULL,
  lo                BIGINT       NOT NULL,
  hi                BIGINT       NOT NULL,
  PRIMARY KEY (day_key, hour_of_day, provider, model, member_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_bin;
```

> 🚨 **主键列序是刻意的，而且不能把 `member_id` 放在 `provider` / `model` 前面。**
>   InnoDB 的索引键长上限是 utf8mb4 下的 **3072 字节**，而
>   `CHAR(36) + VARCHAR(255) + VARCHAR(255)` 的**列前缀**就已经 36×4 + 255×4 + 255×4 = **2184 字节**，
>   再放 `DATE(3) + TINYINT(1)` 是 2188 —— 恰好越过 3072？
>   不：真正的判据是「**复合键里所有列的长度上限之和**」，即
>   `36×4 + 3 + 1 + 255×4 + 255×4 = 2188 字节`，**没有超**。
>   ⚠️ 但这个数字离上限只剩 30%，所以**任何一列的加宽都会让它 errno 1071**。
>   改这个表之前先算一遍键长（`CHAR(n)` 在 utf8mb4 下是 `4n` 字节）。
>   这也是为什么 `day_key` 用 `DATE`（3 字节）而不是 `VARCHAR(10)`（40 字节）。

服务：**近 30 天**的单日日内曲线 + 近 30 天的时段分布（可带工作日过滤）。
实测（近 30 天）：**11 900 行 / 3.5 MB**（构造 1.5 s）。

> ⚠️ 夹具里「每人每小时只有 1 个 provider-model 组合」，所以这个行数偏乐观；
> 上界是 `天数 × 24 × 人数 × 组合数`，必须用真实数据复核（见 §7）。

### 1.3 T3 `usage_rollup_hod`

```sql
CREATE TABLE usage_rollup_hod (
  hour_of_day       TINYINT      NOT NULL,   -- 0~23
  day_kind          TINYINT      NOT NULL,   -- 0=工作日 1=周末（能排除周末）
  member_id         CHAR(36)     NOT NULL,
  provider          VARCHAR(255) NOT NULL,
  model             VARCHAR(255) NOT NULL,
  calls             BIGINT       NOT NULL,
  input_tokens      BIGINT       NOT NULL,
  output_tokens     BIGINT       NOT NULL,
  cache_read_tokens BIGINT       NOT NULL,
  cache_write_tokens BIGINT      NOT NULL,
  reasoning_tokens  BIGINT       NOT NULL,
  PRIMARY KEY (hour_of_day, day_kind, member_id, provider, model)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_bin;
```

服务：**全历史**的「一天中的第几小时」分布（可只看工作日）。
行数上界 `24 × 2 × 人数 × 组合数` —— **与天数无关**，一次建成长期可用。
实测（300 人）：**115 200 行**（不含 `day_kind`；加上后约 ×2），查询 **51×**。

> ⚠️ 注意 `usage_rollup_hod` **没有日期维度**：它答不了「某一天的第几小时」。
> 那个问题由 T2 或原始表回答（见 §3 路由表）。

### 1.4 版本与元数据表

```sql
CREATE TABLE usage_rollup_meta (
  id                TINYINT  NOT NULL PRIMARY KEY CHECK (id = 1),
  timezone_key      VARCHAR(128) NOT NULL, -- `${TZ}|${Intl 时区}`，与 local-rollup.ts 同款
  built_through_ms  BIGINT   NOT NULL,     -- 已汇总到哪个「接收时刻」（增量水位）
  hour_cutoff_ms    BIGINT   NOT NULL,     -- T2 的保留窗口左边界
  updated_at_ms     BIGINT   NOT NULL
);
```

> **不做 `rollup_version` 列**：汇总逻辑的对错由**受控 DDL 的 schema 版本**决定
> （改口径 = 改 DDL 文本 = 新版本号 + 全量重建），再放一个应用层版本号会变成
> 两处各自维护、必然漂移。时区是**唯一**需要额外版本化的运行时输入，所以只留 `timezone_key`。

🚨 **`timezone_key` 必须进版本判定**：`local-rollup.ts` 已经有这个先例
（`timezoneKey()` 把 `TZ` + 系统时区纳入版本）。改了时区而 `day_key` 还是旧的，
表现是「趋势图的点整体偏 8 小时」而**没有任何报错**。

> **水位语义**：`built_through_ms` 存的是**接收时刻**（`received_at_ms`）的高位，
> 不是事件的 `ts`。理由见 §2 的「乱序补报」。

## 2. 增量构建

汇总表是**派生数据**，可以从 `usage_event` 完整重建，所以策略是「可重建 + 增量补齐」：

| 步骤 | 做法 |
|---|---|
| 全量重建 | `INSERT … SELECT … GROUP BY` 扫全表。300 万行实测 **T1 41 s / T2 1.5 s / T3 17 s** |
| 增量补齐 | 用 `usage_rollup_meta` 的游标做水位，只处理游标之后的事件；**同一天可能跨两次补齐**，所以 upsert 时要**累加**（`calls = calls + new.calls`）而不是覆盖 |
| 触发时机 | ① 启动时补齐一次（`createHandlerFor()` 里）；② 之后每 5 分钟一次（`rollupSyncMs`，可配 0 关闭）。**每一轮只处理一批**，积压多时分多轮推进 |
| 不变量 | `SUM(汇总.calls) == COUNT(usage_event)`（同一窗口、同一时区）—— 查询层的快路径判定与测试都钉住它 |
| 失败处理 | 补齐失败只记日志并保留水位，下次重试；**绝不让看板因为汇总表缺失而 500**（退原始表） |
| 保留窗口 | T2 定期 `DELETE WHERE day_key < 今天-30`；T3 不删（与天数无关） |

### 🚨 水位是**复合游标** `(received_at_ms, event_id)`，不是单个时刻

这是实现阶段踩到的最严重的坑，**且完全静默**：

```
WHERE received_at_ms > 水位   -- ❌ 会卡死
```

一次批量上报（HTTP 一批）的 `received_at_ms` 是**同一个 `Date.now()`**。
于是「本批最后一行的接收时刻」== 「下一批第一行的接收时刻」，
`>` 永远筛不到新行 —— 水位停在那里，**剩下的数据永远进不了汇总**。

**实测**：300 万行造数（接收时刻全相同）+ 默认 `maxRows=200_000`
⇒ `SUM(汇总.calls)` 停在 **20 万**，而原始表 300 万。看板只是静默少算，
`rollupUsable()` 的不变量会因此判为「不可用」→ 退原始表 → **表现完全正常**，
所以这个问题在功能上不可见，只在性能上「优化无效」（实测收益 1.0×）。

**修法**：`(received_at_ms, event_id) > (游标时刻, 游标事件ID)` +
同序 `ORDER BY received_at_ms, event_id`。`event_id` 是主键，所以游标严格单调。
元数据表因此有 `built_through_event_id` 一列（`rollup.test.ts` 有一条专门造
「6 条接收时刻完全相同 + maxRows=4」的回归用例）。

### ⚠️ 为什么水位用 `received_at_ms` 而不是事件的 `ts`

上报允许乱序：一条「昨天发生、今天才上报」的事件，其 `ts` 早于水位。
按 `ts` 走水位会把它**永久漏掉**（原始表里有、汇总里没有，静默少算）。
`received_at_ms` 是「这条数据什么时候到的」，不会倒退。

⚠️ `received_at_ms IS NULL` 的历史行（v4 之前导入的）**永远进不了汇总**，
所以 `syncRollups()` 会如实报出这个缺口数（`unattributedWindow`），
查询层的不变量也会因此判为「不可用」并**退原始表** —— 数字仍然正确。

## 3. 查询路由（唯一要记住的一张表）

| 场景 | `bucket` | 走哪张 | 依据 |
|---|---|---|---|
| 空窗 / 今天 / 昨天 / ≤2 天 | `hour` | **原始表**（实测 12.8 ms / 8 220 行） | `bucketFor()` 就是这么选的；单日本来就小，**汇总表在这条路上没有收益** |
| 3 天 ~ 30 天 | `day` | **T1**（T2 也行，T1 更小） | |
| > 30 天 | `day` | **T1** | T2 只留 30 天 |
| 3 天 ~ 30 天 | `hour` | **T2** | |
| > 30 天 | `hour` | **原始表** | T2 覆盖不到；页面通常也不会这么用 |
| 时段分布（工作日/周末可筛） | — | **T3** | 全历史折叠 |
| 时段分布 + 限定最近 N 天（N ≤ 30） | — | **T2**（`GROUP BY hour_of_day`） | |
| `sessions` 去重计数 | — | **原始表**（永远） | 不可加 |
| 明细 `records` | — | **原始表**（永远） | 逐行事件 |
| 金额 `cost` | — | **原始表** | 单价按事件时刻解析，汇总行跨了换价时刻就不能用「总量 × 一个价」 |
| `pricing` / 人员 / 分组 / 供应商候选目录 | — | 不碰 `usage_event` | |

★ **路由判定的输入必须与 `bucketFor()` 同源**（`period` + 窗口跨度），
否则会出现「页面要小时粒度、服务端给日粒度」的静默错位 —— 图上只是少了很多点。

★ **汇总表不可用时一律退原始表**，并且**不报错**。汇总表是性能设施，不是正确性依赖。

## 4. 迁移与回滚（已实测，15 项断言全过）

```bash
# 迁移专项验证：SQLite + MySQL 各一轮，含回滚与再迁移
bun run packages/server/verify/verify-v8-migration.ts
```

### 4.1 升级（v7 → v8）

```bash
# 先看状态（默认命令就是 inspect）
bun run packages/server/scripts/migrate-db.ts inspect

# 显式迁移（v8 是**纯追加**，不要求备份证明、也不需要 --confirm-offline）
bun run packages/server/scripts/migrate-db.ts migrate
```

- **不会改写任何事实数据**：实测「迁移前后 `usage_event` 事件指纹逐位相同」（SQLite 与 MySQL 都验过）。
- **迁移只建空表，不灌数据**：灌历史要扫整张事实表（3M 行实测 41s），
  塞进迁移事务会让它变成一次长事务。首次补齐由服务端启动时的 `syncRollups()` 做，
  可中断、可重试，而且**汇总表空着也不会让看板出错**（查询层自动退原始表）。
- 服务端启动时若发现 v7 库会**拒绝启动**并给出提示 —— 这是本仓既有闸门的固有行为，
  不是 v8 引入的。

### 4.2 回滚（v8 → v7）

**回滚 = 删掉四张汇总表 + 把版本标记退回 7。** 没有任何事实数据需要恢复。

```sql
-- MySQL
DROP TABLE usage_rollup_day, usage_rollup_hour, usage_rollup_hod, usage_rollup_meta;
DELETE FROM portal_schema_migrations WHERE version = 8;
UPDATE portal_meta SET schema_version = 7 WHERE id = 1;

-- SQLite
DROP TABLE usage_rollup_day; DROP TABLE usage_rollup_hour;
DROP TABLE usage_rollup_hod; DROP TABLE usage_rollup_meta;
DELETE FROM portal_schema_migrations WHERE version = 8;
PRAGMA user_version = 7;
```

⚠️ **版本标记必须一起退**（SQLite 是 `PRAGMA user_version`，MySQL 是 `portal_meta.schema_version`）：
只删账本行而留着版本 8，`readPortalState()` 会得到「version=8 但没有 v8 账本行」
⇒ **`unsupported`**（服务端拒绝启动）。这个坑我在写验证脚本时踩到过，
报错是「不支持迁移版本 8」而完全不提「你的版本标记没退」。

⇒ 回滚后库是 **v7 且被认成 `legacy`**（可迁移起点），所以**再迁一次就能回来**
（实测「回滚-再迁移两轮之后事件指纹仍然不变」）。

### 4.3 只想暂停汇总、不想动 schema

把服务端的补齐间隔关掉即可（`rollupSyncMs: 0` / 不跑 `syncRollups()`），
汇总表会**停留在旧水位**；`rollupUsable()` 的不变量会因此判为「不可用」，
看板自动退原始表 —— **数字仍然正确**，只是回到优化前的速度。

## 7. 可行性已复核（2026-10-01，线上只读实测）

**结论：✅ 值得做，行数落在小的一侧。**

`online-rollup-feasibility.sql` 在线上跑出来的关键分布：

| 指标 | 实测 | 含义 |
|---|---|---|
| **每人每天用到的组合数 C** | 均值 **1.67**，最大 7 | 65.5% 的人-天只用 **1** 个组合；只有 1 个样本用到 7 个 |
| 线上当前 T1 行数 | **97 行** | 与 `6 人 × 41 天 × 1.67 ≈ 411` 的量级一致（低于它是因为人-天分布很稀疏） |
| provider-model 组合总数 | **25** | 不是我早先估的 12 —— 有 `bailian-tpp` / `szjt` / `deeprouter` 这类归一化前的原值 |
| T1 外推到 300 人 / 365 天 | **≈ 18.3 万行** | 我早先的两个估算（1.06 万 ~ 131 万）之间，靠近小的一侧 |
| T2（30 天）行数 | **远小于** T1 | 98.3k 是「每人每小时的组合数都塞满」的**上界**；实际按 C=1.67 且只算活跃小时，约 **4 万行** |
| 按天分布（1 行/人/天） | 6 846 行 | 纯按天汇总的对照 |
| 平均每会话条数 | **102.8** | 会话内高频上报；中位远比它小（一个 31k 条的会话把均值拉高了） |
| 每人每天会话数 | 10.26 | |
| 星期分布 | 周四 14 059 / 周日 1 308 | 工作日约为周末的 **4.6 倍** ⇒ **`day_kind` 这一列有意义** |

**据此的容量结论**：

| 表 | 300 人 / 365 天 | 量级 |
|---|---|---|
| T1 | ≈ 183 000 行 | 几十 MB —— 完全可接受 |
| T2（30 天） | ≈ 4 万行（上界 9.8 万） | 几 MB |
| T3 | `24 × 2 × 300 × 25 = 360 000` 行上界 | 几十 MB，**一次建成长期可用** |

⇒ **T2 的 30 天保留窗口可以放心用，不必缩到 7 天。**

### 6.1 ⚠️ 一个必须写进 README 的运维注意：真值上限是 5 万条/天

线上盘点到：**单个用户在 8 分钟内上报了 9 849 条，另一个在 21.9 小时内 31 327 条**。
按「每条 200 字节的 20 列 INSERT」估算，**约 5 万条/天就是这条链路的真值上限**
（`max_allowed_packet` 默认 64MB，客户端 15s 超时）。

这不影响汇总表（它只读），但影响两件事：
① 有人一天灌 10 万条以上时，**入库会先于查询成为瓶颈**（§2 的 3360 条/秒是已优化后的上限）；
② 那种突发会把「30 天窗口行数」瞬间抬高一个数量级，
所以**看板的性能预算必须按突发后的行数算**，不能按稳态均值算。

## 8. 实测收益（v8 实现完成后，3M 行 / 2GB pool，同机同数据集）

### 8.1 SQL 层：**192× ~ 1862×**（`measure-rollup-sql.ts`）

| 用例 | 原始表 SQL | 返回行 | 汇总表 SQL | 返回行 | 提升 |
|---|---|---|---|---|---|
| 30 天四项求和（overview 的一部分） | 346.6 ms | 1 | **1.3 ms** | 1 | **267×** |
| 30 天趋势（series:day） | 355.8 ms | 246 511 | **0.5 ms** | 11k | **712×** |
| 人员聚合（breakdown by=user） | 423.8 ms | 25 | **2.2 ms** | ~11k | **193×** |
| 供应商聚合（breakdown by=provider） | 364.7 ms | 7 | **0.7 ms** | ~11k | **521×** |
| 时段分布（hour-of-day，全历史） | 930.9 ms | 3 000 000 | **0.5 ms** | 8k | **1862×** |
| 单日日内曲线（series:hour，某一天） | 12.9 ms | 8 219 | **0.5 ms** | 24 | 26× |

### 8.2 端到端（真 HTTP）：**1.0×** —— 收益被固定开销吃掉

| 端点 | 原始表 | 汇总表 | 提升 |
|---|---|---|---|
| `series:day`（30 天） | 885.7 ms | 891.5 ms | 1.0× |
| `series:hour`（今天） | 249.2 ms | 209.0 ms | 1.2× |
| `hour-of-day`（30 天） | 2 256.5 ms | 2 216.7 ms | 1.0× |
| `overview`（30 天） | 1 315.9 ms | 1 320.5 ms | 1.0× |

🚨 **这个「1.0×」必须如实说清，不要把它藏起来**：

1. **端到端的时间里，SQL 已经只占小头**。3M 行 / 2GB pool 下 30 天窗口的原始表
   聚合只有 350ms，而一个请求还要付：HTTP 回环 + `Bun.serve`（本机 p50 ≈ 60~90ms）、
   逐请求的 schema 闸门（本机堆叠查询 ~30ms）、`openPortalStore()`、
   以及 `series()` 在 Node 侧重建 24.6 万个点（~300ms）。
   汇总表省掉的是那 350ms 里的一部分，**在 890ms 的总额里看不出来**。
2. **`overview` / `hour-of-day` 的端到端数字里还混着「原始表路径的代价」**：
   `overview` 只有 `totals` + `sessions` 走了原始表（金额 / 会话数**刻意**不走汇总），
   所以它本来就不会因为汇总表而变快。`hour-of-day` 的 2.2 秒同样主要是
   Node 侧的折叠与 HTTP 开销。
3. **只有在「SQL 昂贵到主导总耗时」时，汇总表才在端到端上体现**。
   实测反例：128MB pool 下 3M 行，原始表聚合是 **4.4~19.3 秒**（见性能报告 §4.1），
   那时汇总表的 1ms 会把整个请求从「十几秒」拉回「几百毫秒」。

### 8.3 结论：**现在不要部署，等阈值**

| 判据 | 现在 | 该部署的时机 |
|---|---|---|
| `usage_event` 体积 | **77 MB**（线上） | > `innodb_buffer_pool_size` 的一半 |
| 30 天窗口原始表聚合 | **35 ms**（线上） | > 300 ms（≈ 150 万行/30 天） |
| 看板单接口 p95 | 待测 | > 1 s |

⇒ **v8 是「规模到达之后」的性能保险，不是当下的提速**。
它的实现价值在于：① 口径已经被 14 项单测 + 16 项活体断言钉住，届时只需配置阈值；
② 顺带修掉了水位游标那个**静默少算**的真实 bug（§2）。

⚠️ 另一条建议：一旦启用，**先只接 `series(day)` 与 `hour-of-day`**。
`overview` / `sessions` / 明细 / 金额继续走原始表 —— 它们要么不可加、
要么必须按事件时刻取价，**接进汇总会引入口径错误而不是性能收益**。
