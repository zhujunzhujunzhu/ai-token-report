# 发布检查与事故恢复

发布包为 `dsh-token-report`（CLI）与 `dsh-plugin-token-report`（DSH 插件）。

## 发布入口

```bash
bun run publish:plugin:dry    # 全部验证 + 打包 + 真启动 + dry-run，不上传
bun run publish:plugin:next   # 全部验证通过后发布 next
bun run publish:plugin        # 全部验证通过后发布 latest
bun run publish:cli:dry
bun run publish:cli:next
bun run publish:cli
bun run publish:dry           # 两个包共同验证、dry-run

# 快速通道（迭代期用；边界见下节）
bun run publish:plugin:quick  # 只验插件这个产物：typecheck → build → 产物体检 → 打包 → tarball 真启动 → 发布 latest
bun run publish:cli:quick     # CLI 同款
```

以上全部进入 `scripts/release.ts`。**完整通道没有任何跳过验证的参数**；唯一的例外是显式的
`--quick`（即 `:quick` 那两个脚本，也可写 `bun run scripts/release.ts plugin --quick --dry-run` 先自检）。
它把范围收窄到「本次要发的那个产物」，**跳过的步骤逐条打印**并写进 `report.json`
（`mode: "quick"` + `skipped: [...]`），所以「快」不会变成「不知道漏了什么」。
脚本默认 dry-run，只有显式 `--publish` 才上传；未知参数及 `--publish --dry-run` 都报错。
任一步失败或超时，后续发布不会执行。不要直接在 dist 执行 `bun publish`，那会绕过仓库检查。

每次生成 `.artifacts/releases/<时间>/report.json`、逐步日志和 tarball，记录 SHA-256。
解包验证后发布同一个 tarball，不再重新构建。next 已发布的同版本不能再次上传 latest；应通过 registry dist-tag 提升版本，或增加版本号重新验证。

## 快速通道（`--quick`）

改文案、改样式这类小修小补不必每次等 5~7 分钟的全仓验证。本机实测（2026-09-30）：

| 通道 | 步数 | 验证耗时 | 明细 |
|---|---|---|---|
| 完整 `publish:plugin:dry` | 31 | 约 412 秒 | 单测 68.5 / 双轨对账 86 / MySQL 30 / 两种 Web 6 / 插件分层 14 … |
| 快速 `publish:plugin:quick` | 6 | **约 22 秒** | typecheck 8.3 + 构建 1.0 + 产物体检 2.8 + 打包 0.1 + tarball 真启动 9.5 + dry-run 0.0 |
| 快速 `publish:cli:quick` | 6 | **约 71 秒** | 大头是 `verify:npm:cli` 31.8 与 CLI tarball 27.2 |

真正上传 npm 的那一步两条通道**一样贵**（实测 `plugin 发布 (latest)` 单独就 66 秒），
所以快速通道省下的是验证时间，不是上传时间。

**每次都跑（不可省）**：

| 环节 | 为什么不能省 |
|---|---|
| `typecheck`（全仓 7 个包） | 契约漂移的主要拦截点，只花约 8 秒 |
| `build:npm:<目标包>` | 发布物就是它产出的（CLI 那条还包含 web-local 构建，插件那条包含浏览器半信封改名） |
| `verify:npm:<目标包>` | 发布清单 / Node 真实加载 / 浏览器半产物 |
| `pm pack` + **tarball 真启动**（`verify-profile-boot.ts` / `verify-tarball.ts`） | **唯一**能挡住「发出去的包装不上、DSH 起不来」（0.3.0 事故）的检查 |

**跳过**：全仓单测与 e2e、双轨与驱动对账、MySQL 三条、两种 Web 的 SSR / 布局 / 图表、
插件分层验证、bundles 检查 —— 完整通道里除 `typecheck` 与目标包那两条以外的全部步骤。
另一个包**不构建、不打包、不发布**（完整通道恒为两个包：共享内核的改动会让另一种分发形态一起坏）。

**不许走快速通道**（这几种情况用完整通道）：

- 改动落在 `packages/shared`（口径 / 契约）、`packages/core`（日志解析 / 本地库 / 查询）、上报链路或数据库结构；
- 插件装载、发布清单、peer 兼容窗口、`cordis.patch.yml` 有改动；
- 对外首发、升 minor 版本，或同版本已发过 `next` 现在要发 `latest`；
- 你**说不清**自己改了哪一面 —— 那时 5 分钟的完整验证比事后回滚便宜。

## 必备环境

Bun、真实 Node ≥22.15、已安装的兼容 DSH、tar、真实会话日志、开发 MySQL。
`ATR_NODE_BIN` 可指定 Node，`ATR_DSH_MODULES` 可指定 DSH 宿主 node_modules，
`ATR_MYSQL_URL` 可指定测试库，`DSH_HOME` 指定日志来源。默认 MySQL 为本机开发实例 3335 / ai-token。
缺少环境会中止，不能把没有执行的检查当成通过。

## 自动验证范围

下表是**完整通道**的范围。快速通道（`--quick`）只保留三样：
全仓 `typecheck`、**目标包**的构建与 `verify:npm`、**目标包**的 tarball 真启动
（对照上节「每次都跑」那张表）。

| 环节 | 验证内容 |
|---|---|
| 全仓测试、typecheck、两个 Web 构建 | 单元、HTTP 契约、权限、查询、实际资源 |
| identity / ingest / admin / report-ingest E2E | 真 HTTP 与投递全链路 |
| DB parity / driver parity | 固定真实日志副本的 SQL 与直扫；Bun 与 Node；不改正在使用的本地库 |
| MySQL dialect / portal parity / Node mysql2 | 方言活体、双后端逐字段对账、真实 Node 驱动 |
| 本地与部门 Web 验证 | SSR、SVG 布局几何、图表（不依赖运行中的预览页或硬编码 Chrome 路径） |
| 两个 npm verify | 清单、Node 真实加载、CLI 双运行时 HTTP |
| 插件 peer 兼容窗口 | 用**宿主自己的** `evaluatePluginCompatibility` 给发布清单打分：已实测的代际必须被接受、未验证的代际（0.1.6 / 0.3）必须被拒；源码清单与发布清单的两份 peer 必须一致 |
| 插件分层验证与 SQL | HTTP、Cordis 代理、解析、浏览器产物、SQL/降级 |
| bundles 检查 | zod 不进入前端产物 |
| 插件实际 tarball | 真 Loader 干净安装、重复 ID 复现、升级修复、备份/幂等/配置保留、浏览器信封执行、完整 DSH Web HTTP |
| CLI 实际 tarball | 解包后重新跑双运行时验证，禁止重建掩盖漏文件 |
| 发布 | 校验 SHA-256，上传已验证文件 |

`diagnose-boot`、`probe-activation`、`repro-boot-failure` 是针对用户环境的排障工具；
发布时使用临时 profile 的 `verify-profile-boot.ts`，不对真实用户 profile 启动或修改。
需要真实模型凭证的付费会话不在自动发布中运行。

## 0.3.0 事故与恢复

症状是 `duplicate loader entry id: token-report`，整个 DSH 启动失败。
`dsh plugin add` 会自动登记 bundle，bundle 会插入 `token-report`。
旧的手动 insert、重复 bundle、源码包与发布包并存都会导致重复挂载。
此前验证覆盖 import 和单插件 Context，遗漏 profile 合并与完整宿主启动，发布入口也未强制串联检查。

0.3.1 的离线 `repair-profile.mjs` 默认只检查，`--apply` 才写入，先备份再把旧 insert 转成 ID 覆盖，去掉源码包依赖及 bundle。冲突不猜测、不落盘；不访问身份、数据库、日志或 outbox。具体恢复命令见插件 README。

修复后的约束：bundle 是插件 insert 的唯一来源；用户配置只使用 `- id: token-report` 覆盖。
`config` 是整体替换，人工合并时必须保留原有上报设置。

## DSH 升代时的兼容复验

插件不把 `peerDependencies` 钉在某个精确版本上，而是声明一个**兼容窗口**
（`@deepseek-ai/dsh-{session,session-telemetry,agent}` = `>=0.1.7-rc.2 <0.3.0-0`）。
宿主启动时由 `dsh-app-boot` 的 `evaluatePluginCompatibility` 用
`semver.satisfies(runtime, range, { includePrerelease: true })` 判定；**任一 peer 不满足，
整个 bundle 被跳过** —— 现象是「面板不见了、一条也不上报」，启动日志只有一行
`skipping profile bundle …`，不是报错。所以放开窗口前必须先实测新宿主。

复验步骤（不碰本机的宿主安装，只多一份临时副本）：

```bash
# ① 把要复验的宿主装到临时目录（不是升级本机的 DSH）
mkdir /tmp/dsh-next && cd /tmp/dsh-next
printf '{"private":true,"dependencies":{"@deepseek-ai/dsh":"<新版本>"}}' > package.json
npm install --no-audit --no-fund

# ② 用它当宿主，跑发布产物验证与真实 tarball 启动（两条都认 ATR_DSH_MODULES）
export ATR_DSH_MODULES=/tmp/dsh-next/node_modules
bun run --filter '@ai-token-report/dsh-plugin' verify:npm
bun run packages/dsh-plugin/verify/verify-profile-boot.ts <packed.tgz>
```

两条都要过；`verify-profile-boot.ts` 会真的起一个完整 DSH Web 并访问它的 HTTP 端口，
所以「能被 import」不算通过。改窗口时同步改三处并说明依据：
`packages/dsh-plugin/package.json`、`scripts/build-npm.ts`（两份 peer 由验证脚本钉成一致）、
以及声称支持的代际清单（`verify-npm-package.ts` 里的 `compatClaimed` / `compatRejected`）。

支撑「0.1.7-rc.2 → 0.2.0-rc.2 可以共用同一个窗口」的两条实测证据（放开范围前自己复跑一遍）：

1. `@deepseek-ai/dsh-session-telemetry` 的导出与 `SessionTelemetryCoordinator` 签名
   **只是纯增量**（多一个可选 `sourceEvent`），`body` 的形状没变；
2. `dsh-session-format*` 全树的实现文件**逐字节相同**（只有 `package.json` 的版本字段不同），
   即落盘会话日志格式没变，`packages/core` 的 scanner 口径不受影响；
   `dsh-llm` 的 usage 类型文件同样逐字节相同。
