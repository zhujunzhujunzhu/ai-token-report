# 部门服务端部署

把本仓的服务端与看板产物送到 `117.72.173.21` 的 `/ai-token/` 下。
入口是 `scripts/deploy-server.mjs`（**Node 脚本**，`node` 直接跑，不需要 bun 做入口）。

> ⚠️ 这与 [`scripts/release.ts`](发布检查与事故恢复.md)（npm 公开发布）是**两件事**：
> 前者把产物送上网关机器，后者把 tarball 发到 registry.npmjs.org。
> 两者的验证范围没有交集，**不要互相替代**。

---

## 一、三个档位（默认零副作用）

```bash
bun run deploy:server              # dry-run：只本地构建 + 打包 + 打印计划，不连服务器
bun run deploy:server:preflight    # 真上传到服务器 /tmp 并校验产物，不切换、不重启
bun run deploy:server:apply        # 真部署：备份 → 切换 → 重启 → 健检，失败自动回滚
```

也可以直接跑脚本本体（便于加参数）：

```bash
node scripts/deploy-server.mjs --apply --skip-verify      # 跳过本地测试（构建仍会跑）
node scripts/deploy-server.mjs --apply --full-verify      # 额外跑全仓 bun test + typecheck
node scripts/deploy-server.mjs --apply --keep-old-assets  # 不清理历史 assets
node scripts/deploy-server.mjs --apply --runtime node     # 临时退回 Node22 跑（见 §11）
```

| 参数 | 作用 |
|---|---|
| `--apply` / `--preflight` / `--dry-run` | 三档互斥；**不带参数 = dry-run** |
| `--skip-verify` | 跳过本地 typecheck 与 server 测试 |
| `--full-verify` | 改用全仓 `bun test` + `bun run typecheck` |
| `--keep-old-assets` | 保留看板历史 assets（默认清理） |
| `--runtime bun\|node` | **线上进程 exec 哪一个运行时**，缺省 `bun`。见 §11 |
| `--server` / `--user` / `--hostkey` / `--portal-base` / `--remote-root` | 覆盖默认值 |

> ★ `--runtime` 不是「换个参数」那么轻：它会改写并安装 `deploy/atr-server-start.sh`，
> 并在重启后**断言进程真的 exec 在指定的二进制上**（对不上就回滚并回 `runtime-mismatch`）。
> 切 Bun 之前还要求产物里已经有长口令 TLS 修复，否则本地就拒绝上传 —— 见 §11.2。

默认档位下脚本**不产生任何远程影响**；`--preflight` 只写 `/tmp`；只有 `--apply` 会动现网。
每次运行在 `.artifacts/deploys/<时间戳>/` 留 `report.json`、逐步日志、两个 tarball、
生成的远端脚本 `remote.sh` 与远端输出 `remote.log`。

## 二、它到底做了什么

| 阶段 | 动作 |
|---|---|
| 本地验证 | 默认：server typecheck + `bun test packages/server`（含 67 项 HTTP 契约）+ web-portal typecheck |
| 本地构建 | `build:node` → `packages/server/dist/*.mjs`；`DSH_PORTAL_BASE=/ai-token/ bun run build:portal` |
| 产物断言 | 三个 `.mjs` 都在；`index.html` 必须含 `/ai-token/assets/`；**Bun 运行时还要求产物含 `planBunMysqlAuth`** |
| 渲染启动包装 | 取仓库里的 `deploy/atr-server-start.sh`，只改写 `ATR_RUNTIME_BIN=` 那一行 |
| 打包 | `tar -czf` 两份，记录 sha256（传的与解的是同一份字节） |
| 上传 | 传到服务器 `/tmp/atr-deploy-<stamp>-{server,portal}.tgz` 与 `-start.sh` |
| 远端校验 | 解包到 staging，断言文件齐全 + **index.html 前缀正确** + **启动包装过 `bash -n`**，否则拒绝切换 |
| 切换 | 先备份到 `.deploy-backup-<stamp>`（**两个 `dist` + 启动包装**），再替换 |
| 重启 | 加载 `/root/.atr/portal.env`，`pm2 restart ai-token-server` |
| 健检 | 30 秒内轮询 `127.0.0.1:$ATR_PORT/api/health`；失败**自动回滚**并打印 PM2 日志 |
| **运行时断言** | 读 `/proc/<pid>/exe`，确认进程**真的** exec 在 `--runtime` 指定的二进制上；对不上同样回滚 |
| 公网校验 | 抓 `http://<host>/ai-token/health`、首页、入口 JS，断言 MIME 是 `javascript` |

> 最后一条是**唯一能抓住「白屏」的环节**：子路径配错时资源被站点根的其他应用接走，
> 回 `text/html`，浏览器按模块 MIME 校验拒绝执行 —— 页面全白，而服务端日志里一句错都没有。
>
> **运行时断言**那条是 2026-10-01 补的：在此之前「线上跑 Node 还是 Bun」没有任何环节会验，
> 而它的失败形态恰好是「服务健康、数字正常、只是跑错了二进制」。

## 三、只碰这三样（★ 硬边界）

```
/data/ai-token-report/packages/server/dist/         ← 覆盖
/data/ai-token-report/packages/web-portal/dist/     ← 覆盖（含清理历史 assets）
/data/ai-token-report/deploy/atr-server-start.sh    ← 覆盖（安装前备份，回滚时还原）
```

**绝不触碰**：

| 路径 | 为什么 |
|---|---|
| `packages/server/node_modules/` | 产物 `external: ['mysql2/promise']`，靠它解析（实测 `MYSQL2_OK`）；`node_modules` 顶层没有 `mysql2`，只有 `packages/server/node_modules` 里有 |
| `/root/.atr/portal.env` | 凭证与监听配置，脚本只读取 `ATR_PORT` |
| 上报库 | schema 迁移**不在部署脚本内**，见 §五 |

> ### ★ 启动包装为什么从「绝不触碰」变成了「由脚本安装」
>
> 它以前**不在仓库里** —— 于是「线上跑 Node 还是 Bun」是一条**只存在于一台机器磁盘上的事实**。
> 两种失败都是静默的：谁重建机器 / 谁手工重写一遍这个文件，就退回 Node22；
> 而「先切 Bun、产物里却还没有长口令 TLS 修复」会让服务直接 `errno 1045` 起不来。
>
> 现在真源是仓库里的 `deploy/atr-server-start.sh`，由 `--runtime` 渲染后安装：
> 改动可评审、可 diff、可回滚（备份进 `.deploy-backup-<stamp>/`），
> 并且每次部署都会断言进程真的 exec 在指定的那个二进制上。
> 🚨 **因此不要再手工编辑服务器上那一份** —— 下次部署会覆盖它。

## 四、子路径部署（`DSH_PORTAL_BASE`）

页面挂在反代子路径 `/ai-token/` 下，构建时**必须**带前缀。脚本默认值就是 `/ai-token/`，
且在构建后立刻断言 `index.html` 里有它 —— 忘了带会构建出绝对路径产物，
**页面立即变白且服务端不报任何错**，所以这条不再依赖人的记忆。

根路径部署用 `--portal-base /` 覆盖。

## 五、数据库迁移是另一件事

上报库（MySQL 8 @3308）是全员数据的**唯一副本**，schema 变更**绝不自动执行**：
版本不符时服务端拒绝普通业务写入，只能显式跑 `dist/migrate-db.mjs`（`inspect` / `migrate` / `resume`）。

部署成功后脚本会比对「服务器 health 里的 `schema_version`」与「本地版本常量」，不一致时**告警**
（当前常量 = **7**，真源是 `packages/core/src/db/portal-schema-v5.ts` 的 `PORTAL_SCHEMA_VERSION`）。
**v4 是冻结基线**：v3 库先迁 v4，再走 v4→v5；v4→v5 会去掉事实表的分组 ID 列
并把 `dept` 改名 `group_name`，SQLite 分支因此必须重建事实表 —— **先按备份流程执行**。
v6 / v7 都**只增表**（`provider_alias`、`model_price` 与各自的权限码），不改既有列。
改了 schema 就必须先迁移再部署，见 [数据库部署与迁移](数据库部署与迁移.md)。

> ✅ **已修**：`scripts/deploy-server.mjs` 现在**不再写死某个版本的文件名** ——
> 它扫描 `packages/core/src/db/portal-schema-v*.ts`，取真正导出 `PORTAL_SCHEMA_VERSION`
> 的那一个（改名前它写死 `portal-schema-v4.ts`，常量搬到 v5 后静默取不到值，
> 而调用点的 `expected !== null` 判断会把「读不到」当成「跳过比对」，
> 这条唯一的版本护栏就消失了）。同时「读不到期望版本」现在会**显式告警**，
> 不再静默跳过。

## 六、连接方式与前置条件

脚本按顺序二选一，**优先免密**：

1. **OpenSSH 免密**（`ssh -o BatchMode=yes` 能过）→ 用 `ssh` / `scp`；
2. 否则用 **PuTTY 的 `plink` / `pscp`**（OpenSSH 客户端不接受命令行密码，密码那条路只能走它）。

密码与主机取自仓库根 `.env` 的 `host` / `password`，可用环境变量
`ATR_DEPLOY_HOST` / `ATR_DEPLOY_USER` / `ATR_DEPLOY_PASSWORD` / `ATR_DEPLOY_HOSTKEY` 覆盖。
主机指纹自动从 `~/.ssh/known_hosts` 推导（缺了它会表现为「密码对但连不上」）。

> 🚨 **指纹形式必须是裸 MD5 冒号**（`ab:cd:…`），**不是** `ssh-keygen -lf` 默认输出的
> `SHA256:…`。实测 PuTTY 0.72：`-hostkey SHA256:…`（含 `ssh-ed25519 255 SHA256:…` 变体）
> 一律 `not a valid format for a manual host key specification`，pscp 在**上传阶段**就失败，
> 密码那步都走不到 —— 症状是「明明 .env 里有密码，却卡在上传」。脚本已改用
> `ssh-keygen -l -E md5` 生成 MD5 形式（新旧 PuTTY 都接受）；手工传 `--hostkey` 时也请给 MD5。

前置：本机 `bun`、`node ≥ 20`、`tar`，以及 `plink`+`pscp`（或免密 ssh）。

> 建议把 `~/.ssh/id_ed25519.pub` 装到服务器 `authorized_keys`，之后就是免密路径，
> 不必再让密码出现在进程命令行里。

## 七、回滚

自动回滚发生在**远端同一个脚本内**，两种触发条件：健康检查 30 秒不过；
或**服务健康但进程跑的不是 `--runtime` 指定的那个二进制**。
产物与启动包装**一起**还原，所以本地网络中断也不会留下「切了一半」的状态。

手工回滚（用自动备份）：

```bash
TS=<时间戳>   # 见部署输出里的 .deploy-backup-<TS>
cd /data/ai-token-report
rm -rf packages/server/dist && cp -a .deploy-backup-$TS/server-dist packages/server/dist
rm -rf packages/web-portal/dist && cp -a .deploy-backup-$TS/portal-dist packages/web-portal/dist
# ★ 启动包装也在备份里：它是「线上跑哪个运行时」的唯一落点，漏掉它 = 回滚不完整
[ -f .deploy-backup-$TS/atr-server-start.sh ] && cp -a .deploy-backup-$TS/atr-server-start.sh deploy/atr-server-start.sh
export PATH=/usr/local/bin:$PATH && pm2 restart ai-token-server
```

## 十、实测记录（2026-09-30 复部署）

本次把服务端与看板重新发布到 `117.72.173.21`（`schema_version` 7 → 7，**未涉及数据库迁移**：

| 结论 | 验证方式 |

| 部署成功 | old pid `28182` → new pid `30443`，health `ok:true`，公网入口 JS `200 text/javascript`，历史 assets 清理 45 个，未触发回滚 |
| 备份位置 | `/data/ai-token-report/.deploy-backup-2026-09-30T14-46-31-740Z` |

## 十一、运行时：现在是 Node 22，可以换 Bun 吗

**可以，而且服务器上早就装了 Bun**（`/usr/local/bin/bun`，1.4.2），
但**必须同时改两处**，否则服务起不来。完整实测见
[性能：Node22 与 Bun 对比实测](性能：Node22%20与%20Bun%20对比实测.md)。

### 11.1 现在实际跑的是什么

| 项 | 值 |
|---|---|
| pm2 条目 | `ai-token-server`（id 2），**fork 模式**，`interpreter /bin/bash` |
| 被托管的脚本 | `/data/ai-token-report/deploy/atr-server-start.sh`（**不在仓库里**） |
| 该脚本 exec 的运行时 | **`/usr/local/node22/bin/node`**（v22.21.1） |
| 监听 | `127.0.0.1:8790`（`ATR_HOST` / `ATR_PORT` 来自 `/root/.atr/portal.env`） |

> ⚠️ `pm2 -v` 显示的是 node **v20.19.2** —— 那是 **pm2 自己的**解释器。
> 被托管的服务端跑的是 node22。两件事，别混。

### 11.2 换 Bun 现在是部署脚本的一个参数

```bash
bun run deploy:server:apply --runtime bun     # 缺省值就是 bun
bun run deploy:server:apply --runtime node    # 临时退回 Node22
```

`--runtime` 会渲染并安装仓库里的 `deploy/atr-server-start.sh`（只改 `ATR_RUNTIME_BIN=` 那一行），
重启后读 `/proc/<pid>/exe` 断言进程**真的** exec 在指定的二进制上。
pm2 侧**不需要任何改动**（它托管的是 bash 脚本，`interpreter` 恒为 `/bin/bash`）。

> 🚨 **顺序是有硬约束的：必须先让线上产物含 `planBunMysqlAuth()` 的 TLS 修复，才能切运行时。**
> 实测（2026-10-01）：切换前线上那份 `dist/main.mjs`（2026-09-30 构建）
> `grep -c planBunMysqlAuth` = **0** —— 直接切 Bun 会撞上 §11.4 那个 1045 认证坑。
>
> 这条现在**由代码兜住**，不再依赖人的记忆：`--runtime bun` 时
> `assertBundleSupportsRuntime()` 会在**上传之前**检查产物，
> 缺这个标识符就直接拒绝部署（`scripts/deploy-plan.mjs`，
> 由 `packages/server/test/deploy-plan.test.ts` 钉住）。
> 即使产物里有它，服务端启动横幅也应当出现 `（Bun 长口令：已自动启用 TLS）` —— 那是运行时的**事实**。

✅ **`/root/.atr/portal.env` 不用动。** 以前需要在这里给 `ATR_MYSQL_URL` 末尾加
`?tls=true`（线上 `atr_user` 口令 32 字符，Bun 1.4.2 在非 TLS 连接下对
`caching_sha2_password` + 口令 ≥ 20 字节会 `errno 1045`，oven-sh/bun#26195）——
**这个绕过已经修进代码**：`openMysqlBackend()` 现在会按需自动为这种连接启用 TLS
（`core/src/db/mysql.ts` 的 `planBunMysqlAuth()`），并在启动横幅里说明：

```
上报库    MySQL ai_token_report @ 127.0.0.1:3308（Bun 长口令：已自动启用 TLS）
```

🚨 **不要**改用「把口令缩短到 19 字符以内」来绕过这个上游缺陷。

然后 `export PATH=/usr/local/bin:$PATH && pm2 restart ai-token-server`，
按 §二 同样的口径健检（`127.0.0.1:$ATR_PORT/api/health` + 公网入口 JS 的 MIME），
并确认横幅里出现了上面那个后缀。

### 11.3 回滚

```bash
# ① 推荐：再发一次，显式指定旧运行时（产物不动，只换运行时）
bun run deploy:server:apply --runtime node
# ② 手工：改 ATR_RUNTIME_BIN 那一行 + pm2 restart（会话里最快的一招）
```

> ✅ **2026-10-01 起 `scripts/deploy-server.mjs` 也管运行时了**（`--runtime`）。
> 在此之前它只管 `dist`，运行时是**独立于部署脚本**的一次手工改动 ——
> 那时的风险是「回滚部署」并不会把运行时一起带回去。
> 现在两者在**同一个原子操作**里备份与还原，`.deploy-backup-<stamp>/` 里同时有
> `server-dist` / `portal-dist` / `atr-server-start.sh` 三样。

> ⚠️ 另外还留着一份**最初那份 Node22 启动包装**（2026-10-01 手工切换时留的）：
> `/data/ai-token-report/deploy/atr-server-start.sh.node22.bak`。它已经被自动备份取代，
> 保留只为留个原始记录，**不要**再拿它当回滚路径。

### 11.4 换之前先复核认证那条路

那个上游缺陷是**驱动的行为**，Bun 升版可能改变它。仓库里有一条活体验证：

```bash
bun run --filter '@ai-token-report/server' verify:mysql:bun-auth
```

它建三个只跑 `SELECT 1` 的临时用户（16 / 19 / 20 字节口令），断言
**19 字节必须明文能连、20 字节必须靠自动 TLS 能连**，并且**把修复关掉必须复现出 `1045`**
（否则「连上了」可能只是因为这台机器恰好不需要修）。用完自动删用户。

### 11.5 实测结论（一句话）

换 Bun 省 **约 1/6 CPU**、**约一半常驻内存**、启动快 **约 30%**，
趋势类接口快 **15~19%**，但**看板整体不会明显变快** ——
DB 边界端点差异在 ±6% 内，瓶颈是 MySQL 取数而不是运行时。
判据与数字见[实测报告](性能：Node22%20与%20Bun%20对比实测.md) §10。

## 十三、规则固化：运行时与启动包装（2026-10-01 补）

§12 那次部署暴露了一个结构性问题：**「线上跑 Bun」当时只是一台服务器磁盘上的一行字**。
仓库里既没有那个启动包装，`deploy-server.mjs` 也一个字都不提运行时。
把它变成仓库事实，是下面这四处改动共同完成的 —— 少任何一处，规则就重新退化成口头约定。

| 落点 | 负责什么 |
|---|---|
| `deploy/atr-server-start.sh`（**新增，仓库里那一份是真源**） | PM2 启动包装；`ATR_RUNTIME_BIN=` 那一行是运行时的唯一落点。项目根从脚本自身位置推导，不写死 `/data/...` |
| `scripts/deploy-plan.mjs`（新增，纯逻辑） | `RUNTIMES` / `renderStartScript()` / `assertBundleSupportsRuntime()` / `renderRemoteScript()` |
| `scripts/deploy-server.mjs` | 新增 `--runtime`（缺省 `bun`）；上传并安装启动包装（备份 + 回滚）；重启后断言实际运行时 |
| `packages/server/test/deploy-plan.test.ts`（10 项） | 把上面四条钉住，含「模板少了那行必须报错」与「生成的脚本里不许残留 `${`」 |

### 13.1 三条被钉住的规则

1. **产物配不配得上这个运行时**：`--runtime bun` 要求 `dist/main.mjs` 里含
   `planBunMysqlAuth`，否则**本地上传之前就拒绝**。这把「顺序不能错」从注意事项
   变成了不可能违反。
2. **启动包装来自仓库**：部署时渲染（只改 `ATR_RUNTIME_BIN=` 一行）→ 备份线上那份 →
   覆盖安装 → `bash -n` 语法检查。回滚时**连它一起还原**。
3. **跑的是哪个运行时是探测出来的事实**：重启后读 `/proc/<pid>/exe`，
   与 `readlink -f` 过的期望二进制比对；对不上就回滚并回 `runtime-mismatch`。
   ⚠️ 只有「两边都读到且不同」才判失败 —— 探测不到时判 unknown，
   不能因为一次 `/proc` 读取失败去回滚一个健康的部署。

```bash
bun test packages/server/test/deploy-plan.test.ts    # 10 项
node scripts/deploy-server.mjs --dry-run             # 不连服务器，只打印计划（含运行时）
```

### 13.2 为什么纯逻辑要单独一个 `.mjs`

`deploy-server.mjs` 是**用 `node` 直接跑**的（不经 bun），所以只能是 `.mjs`；
而它 import 即执行，测试没法直接引用它。于是把危险的部分抽进 `scripts/deploy-plan.mjs` ——
与 `scripts/release-plan.ts` + `release-plan.test.ts` 是同一套办法。

> 🚨 **实测踩到**：模板是 JS 模板字符串拼的，在它的注释里写了一对**反引号**
> （`` `/proc/<pid>/exe` ``）会直接把模板字符串截断，`node --check` 报
> `SyntaxError: Unexpected token '<'`。同类的还有 shell 的 `${VAR}` —— 会被 JS 抢先求值。
> 两条现在都有断言兜住（`deploy-plan.test.ts` 的最后一条）。
