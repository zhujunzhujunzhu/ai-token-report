# dsh-plugin 大数据性能分析（2026-09-26）

针对“用量面板打开、切换、刷新变慢”，先完成源码分析和隔离合成测试，再按用户确认实施了以下优化。主要压力来自调用记录数、会话/日志文件数、活动日志字节数和上报积压文件数，而不是累计 token 数字的位数。本文前半为实现结果，后半保留优化前的诊断依据；诊断中的源码行号指优化前快照。

**已实施的算法与数据通路**

- 增量解码记录完整 zstd 帧的字节位置，追加时只读取尾部；文件替换、截断及未完成帧保留重试语义。全量定位使用 Buffer.indexOf。变化文件队列缩小文件扫描和水位线读取范围，未变文件不写状态。
- 本地 SQLite 新增可重建的小时/会话/模型/cwd 压缩索引。按 rowid 增量消费，索引、事件主键映射及游标同事务提交。更新/删除/REPLACE/旧 CLI 重建/时区变化均会使索引失效，不改部门库或共享 schema 版本。
- 摘要在 SQLite 内对压缩行 SUM 四项原始 token、reasoning、calls，COUNT(DISTINCT session_id) 保证精确会话数；不把每个会话对象送入 JS。详情复用压缩行计算分组/趋势，精确日期边界只回查被切开的桶。
- DSH 查询移入独立 Worker；同库有界串行队列。启动、强制刷新及超过 30 秒后的下一次真实查询执行完整文件对账，期间消费文件通知。文件通知不是唯一正确性来源。
- 常驻面板只取摘要；详情只取当前分组 10 行及趋势。关闭详情不取明细，图表数据表展开后按 50 行翻页。响应缓存限制 64 项/8 MiB，慢探针独立防重入，旧代次响应不再反复传输。
- 上报计数直接读内存；outbox 增量维护元数据，恢复/对账与高频探针分离。发送队列不反复复制全部积压，单次 HTTP 按条数及 UTF-8 JSON 字节分块。

百万记录的同范围完整查询约快 **59 倍**。新面板的全年摘要约 23 ms、本月摘要约 9 ms，单页详情约 75 ms。完整查询计时器最大延迟由 6,874 ms 降到约 20 ms；摘要/单页约 11/15 ms。Windows 5 ms 定时器自身存在约 10–15 ms 调度误差，这不是精确 CPU 阻塞剖析。

10 万会话极端场景：旧载荷 15.18 MiB，新摘要 375 字节、会话单页及趋势约 17.3 KiB。该场景每条记录属于不同会话，无法通过桶显著压缩；精确分组仍需处理 10 万个会话，当前首个详情请求约 0.87 秒。兼容旧 API 的“所有维度所有行”并未改善，仍有约 121 ms 的主线程大对象传输延迟；现代面板不会请求这一载荷。不能把降低传输量描述为所有高基数组合都已达到常数时间。

初次创建派生索引实测百万记录约 7.8 秒（包括 Worker 启动），不会阻塞宿主事件循环；这是一次性成本，冷启动延迟没有消失。同一库由 220.1 MiB 增至 249.6 MiB，包含压缩索引与用于 REPLACE 正确失效的主键映射。第二轮 `after-summary-run.jsonl` 的 coldSummary 实际是“新 Worker 打开已建索引”，不能误当首次建索引时间。

独立扫描验证：50 MiB 历史日志只追加一帧，旧 Node 路径约 3,729 ms；新尾部读取和定向 ingest 约 8.65 ms，仅读取新帧。5,000 个文件中只变一个时，定向 ingest 约 10.79 ms；完全无变化连续三次 SQLite total_changes 增量为 0。完整目录对账依然随文件数增长。

以上是宿主查询和隔离扫描微基准，**不是实际用户日志下的浏览器端到端时延**。真实浏览器另跑了 10 项交互验收，覆盖摘要、详情、分组切换、翻页、年度趋势、表格展开/翻页及关闭详情；全部通过。

| 100 亿 | 1 万 | 100 | 15.7 ms | 45.8 ms | 41.8 KiB |
| 1 亿（数值对照） | 10 万 | 1,000 | 111.5 ms | 513.3 ms | 179.5 KiB |
| 100 亿 | 10 万 | 1,000 | 97.4 ms | 503.6 ms | 190.2 KiB |

这是**宿主查询基准，不是浏览器端到端加载时间**：测试从预填充的合成 SQLite 读取，日志目录为空，不含冷建库、真实日志扫描、outbox、HTTP 传输和浏览器绘制。JSON 大小单独测量。它隔离了现有数据库查询与数据组织的成本；真实环境还有额外开销。这些数值不能用来宣称生产环境固定需要多少秒。

百万条全年查询中，5 ms 间隔计时器最大延迟约 6,874 ms，说明同步 SQL 和 JS 聚合会长时间占用宿主事件循环。三个不同窗口同时提交时，现有按数据库串行队列合计约 8,050 ms。TTL 命中已经很快，但首次访问、手动刷新和缓存过期仍需支付上述成本。

固定 10 万记录，1 亿和 100 亿 token 的全年耗时约 513/504 ms，差异处于本轮波动范围。不能用“大整数运算”解释这一问题。

**定位到的主要原因**

1. 增量解码仍在扫描历史字节。

   `packages/core/src/scanner.ts:413` 每次文件变大都 `readFile` 整个文件；`decode.ts:235` 重新拆所有帧，`decode.ts:24` 对每个字节调用 `Buffer.compare`。现有帧数水位只跳过历史解压，没有跳过历史字节定位。

   Node 微基准每次仅解码最后一个新增帧，三次中位数如下。定位对照和尾帧对照不是完整的增量扫描实现。

   | 历史压缩文件 | 当前增量解码 | 全文件读取 | 原生 indexOf 仅定位 | 已知偏移、仅解码尾帧 |
   |---|---:|---:|---:|---:|
   | 1 MiB | 73.99 ms | 0.62 ms | 0.11 ms | 2.68 ms |
   | 10 MiB | 730.11 ms | 4.33 ms | 0.84 ms | 2.42 ms |
   | 50 MiB | 3,729.29 ms | 18.56 ms | 4.25 ms | 2.35 ms |

   `indexOf` 能显著降低常数，但仍是 O(历史字节)。保存最后完整帧的 byteOffset，并从该位置读取尾部，才把重复刷新成本变为 O(新增字节)。固定大小追加、每次都刷新的长会话，当前累计历史扫描可达到 O(最终字节数的平方)；真正续读可以使累计字节处理接近线性。

2. 没有新增数据，也遍历并更新全部历史文件状态。

   `scanner.ts:366` 列举所有会话文件，`:381` 逐个 stat；`:395` 的跳过只免除内容读取。`db/ingest.ts:428` 全量读取水位线与会话状态，`:337` 再读全部 firstSeen，`:175` 对包括未变化文件在内的全部 scan.files 执行 upsert。

   | 历史文件数，全部无变化 | Node 热态 ingest | 其中仅扫描目录/文件 | 每次仍修改的状态行 |
   |---:|---:|---:|---:|
   | 100 | 14.19 ms | 13.01 ms | 101 |
   | 1,000 | 128.03 ms | 121.03 ms | 1,001 |
   | 5,000 | 709.86 ms | 604.88 ms | 5,001 |

   修改行包括文件水位线和一行诊断；session_state 不是每次全表重写。单独减少 upsert 不能消除目录扫描成本，需变化文件队列与低频完整对账配合。

3. 每个面板查询都承担一次扫描和多轮聚合。

   `packages/dsh-plugin/src/stats.ts:149` 将同一库的查询整体串行，`:167` 每次调用 `openStats()`；`core/src/db/stats.ts:323` 在查询前 ingest。随后做会话去重、总计、模型/服务商/项目/会话四维分组和趋势。项目还需要一条独立的 cwd/session 去重查询。

   `core/src/db/query.ts:836` 为趋势取出窗口内全部原始行，再在 JS 逐条分桶。百万条全年分阶段中位数：趋势约 3,410 ms、项目约 1,307 ms、模型约 1,024 ms。单个分组索引无法消除这些全范围聚合。

4. 部分短窗口也扫描了全历史索引。

   百万条数据中，测试时“今天”只有 71 条记录，完整查询仍约 504 ms。按 `range.ts` 的真实语义，today 仅提供时间下界。EXPLAIN 显示 provider/session 分组使用 `SCAN ... idx_usage_provider/idx_usage_session`，而不是时间范围 SEARCH。单独两条查询约 163/138 ms。

   在隔离合成库强制使用现有时间索引后，两条查询各约 0.06 ms，返回结果完全一致。本次普通 ANALYZE 没有改变该执行计划。这个对照证明访问路径可以大幅减少短窗口工作量；它不代表应给所有窗口永久强制同一个索引。应按窗口选择性验证查询形状、索引及计划，保留宽窗口对照，也不能偷偷给 today 加结束时间而改变范围语义。

5. UI 一次取四维全部明细，分页发生得太晚。

   `ui-bridge.ts:215` 固定四维并设置 `top: Number.MAX_SAFE_INTEGER`。`components.tsx:253` 最后才切成 10 行；前面的分组、排序、传输、JSON 解析、协议重建和缓存已经处理全量。详情关闭时，常驻用量条仍取同一完整载荷。

   10 万会话样本返回约 15.18 MiB；仅 Node 序列化和解析/协议重建单次约 67/86 ms，尚未计网络和浏览器。独立 React SSR 对照中，1,000 到 100,000 分组行都只渲染 10 条，耗时约 3 ms。因此优先改查询和传输结构，已有前端分页应保留。

6. 高频变化探针隐藏了完整 outbox 扫描。

   `index.ts:544` 用 `backend.reporterStats.enqueued` 提供 generation，但 `reporter.ts:151` 每个 getter 都调用完整快照，`:375` 调用 `outbox.stats()`；`outbox.ts:262` 排序目录、逐文件 stat/read/JSON.parse。约为 O(积压文件数 × log 文件数 + 积压内容字节)。

   Bun 1.4.2 独立微基准，每文件 10 条、三次中位数：100/1,000/5,000 个文件时，读取 enqueued 分别约 24/318/1,398 ms。5,000 个文件仅约 13.2 MB，低于默认容量上限。它只在已启用上报并有相关积压时成立，不能据此断言当前用户一定有积压。

   同时，outbox 每写一批也重新遍历全部文件检查容量；应增量维护元数据。当前已用微任务避开 enqueue 当前调用栈，但这不等于后台线程，同步工作仍会阻塞宿主。

7. 请求与缓存还有次级放大。

   `client/store.ts:208` 的 probe 不置 loading/refreshing，`:299` 却仅用这两个状态防重入；慢探针可能被下一轮主动 abort。独立缩时复现中，10 ms 轮询、35 ms 响应，105 ms 内发出 10 个请求、取消 8 个、没有探针完成。宿主已有同 key 在途合并，不能把每次取消都当成一次重复 SQL。

   新采集代次已增而 30 秒 TTL 尚未结束时，探针还会反复返回旧完整载荷，浏览器解析后才丢弃。宿主缓存限 64 项却无限字节预算；多个重叠日期窗会复制大量会话结果。图表折叠的数据表也无条件构造所有时间点，不过正常全年 365 点是次要成本。

**建议采用的算法结构**

把链路调整为：日志变化提示 → 合并变化文件 → 完整帧尾部读取 → 幂等入库及增量聚合 → 发布查询快照 → 按需查询摘要、趋势和一页明细。

| 工作 | 当前成本 | 建议成本与适用范围 |
|---|---|---|
| 读取本进程变化计数 | 扫全部 outbox | O(1) 内存计数；恢复/对账另行调度 |
| 活动日志追加 | 处理历史文件 B 字节 | O(ΔB) 新增尾部字节 |
| 没变化的请求 | O(F) 文件检查与写状态 | 直接读快照；O(F) 检查移到启动/定期对账 |
| 一般总量、趋势 | 扫窗口内 N 条原始记录 | 查询 B 个相关小时/日桶 |
| 高基数分组首页 | 全量分组、O(G log G) 排序、返回 G 行 | 选定维度；必要时 O(G log k) 堆取 Top-k；只返回 k 行 |
| 后续分页 | 浏览器持有所有结果 | 版本一致的排行快照/游标；只传一页 |
| 同时切多个窗口 | 每个请求独立 ingest 且串行 | 一轮更新共用一个快照；有界读任务队列 |

Top-k 和分页不会自动免掉 G 个组的聚合。对于任意时间范围、任意组合过滤的精确排行，不能普遍承诺 O(k) 或 O(1)。应缓存按范围和数据版本形成的排行结果，或者对常用维度维护聚合；不建议提前构建所有维度的笛卡尔积。

增量聚合保存四项独立原始 token、reasoning 和 calls。小时/日键由现有 `toHourKey/toDayKey` 在 JS 生成；项目名复用 `projectName`。汇总后再调用 shared 公式，绝不在 SQL/浏览器另算命中率或存第二套 total 口径。

已做一个受限原型验证：复用现有 JS 分桶，将百万条记录整理成 181 个日桶，写到**临时库中的实验表**。一次构建约 3,444 ms，此后总量＋每日趋势查询约 0.64 ms。四项 token、reasoning、calls、total 及每个日期桶逐项相等。该原型不包含精确会话数、排行、组合过滤、增量维护与 UI，不能宣称完整面板已达到这个速度。

建议实现顺序：

1. 先切断额外全量工作：纯内存 generation、修正慢探针在途状态、按可用快照版本返回无载荷响应、短窗口 SQL 访问计划优化、用 indexOf 替换逐字节 compare。这阶段容易验证，暂不需要大范围改变持久化模型。
2. 改变持续增长的复杂度：完整帧 byteOffset、变化文件队列、仅提交变化的状态、更新与查询解耦、增量小时/日与常用维度聚合。此阶段决定百万级历史能否保持稳定。
3. 限制每次交互的工作量：摘要独立、只查当前明细维度、真正分页、按字节预算缓存，展开后再创建图表数据表。
4. 用独立 Worker 隔离剩余解码、聚合与 SQLite 同步调用。Worker 持有数据库，主线程传小型任务参数并接收紧凑结果；有界调度及取消过时任务。它保护 DSH 响应性，但不会减少全量算法本身的总工作量。

**实现时必须保住的边界**

- event_id 去重成功后才能增加聚合；原始事件、聚合增量和水位线必须同事务提交。尾部半帧不能推进偏移，截断/替换应回退并重试，跨文件 seq 去重和 cwd 继承不变。
- 文件通知只是提示。启动和低频完整对账仍要发现漏通知、其它 DSH 实例及 CLI 的改动；不能只信上报 enqueued。快照也应随跨午夜、解析范围和时区变化失效。
- 会话数不能把各日 COUNT(DISTINCT session_id) 相加。需维护精确 membership 或使用相关去重索引；项目合并也要对同名项目下的会话重新去重。不能为了速度替换成近似值。
- 自定义范围使用完整内部桶和两端原始记录组合；当前 UI 是完整日期，但 core/工具仍支持更细的边界。持久化时间桶需要记录时区语义并处理时区变更，不能换成 SQLite localtime 分桶。
- 一个响应及其分页使用一致数据版本；排序同值要有稳定次序。避免长读事务拖住 WAL。插件内部单写者不能替代跨进程 SQLite 协调。
- 本地库升级要兼顾 CLI 与插件共同读写，防止旧写者只写原始表不更新聚合、或旧客户端因版本不同反复重建。部门上报库不得自动重建，不能顺手把本地优化当作上报库迁移。
- 未署名不采集/上报、只读取现有本地日志的边界不变；插件公开方法继续遵守 cordis Proxy 约束。Worker、构建与双运行时解析需一并验证。

**验收方式**

后续验收同时测 1 万/10 万/100 万调用，100/1,000/10,000 及高基数会话，50 MiB 长会话追加，5,000 未变文件和积压 outbox。至少覆盖冷启动、无变化刷新、新增少量记录、今天/本月/全年/自定义、快速切换、旧快照命中和多进程补写。

同时观察响应 P50/P95、宿主事件循环延迟、每次实际读取字节/原始行/修改状态行、响应字节和峰值内存。核心要求是：固定新增量时，热态刷新处理的历史字节和文件数不随历史累积线性增长；摘要不携带全量明细；探针不读 outbox；不存在新记录却刷新旧快照不失效的情况。

可先把“百万记录下热态摘要/普通趋势 P95 < 100 ms、单页交互 P95 < 200 ms、宿主无超过 50 ms 的连续阻塞”作为同机验收目标；这是**待实施验证的目标，不是本轮已实现的承诺**。冷建库另行设进度与资源预算。

任何实现后都需原始记录/现有查询/新聚合逐项对账，覆盖重复事件、半帧、跨日跨时区、跨模型会话和自定义边界。按涉及范围运行本仓 bun test/typecheck、双驱动对照，以及插件 cordis/Node 解析/浏览器产物验证。
