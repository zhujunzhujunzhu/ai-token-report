# 本地页取数性能修复（2026-10-03）

`bun run web` 的本地页在**切换时间维度**后半天刷不出数据。本轮定位到的是
**服务端把一次瞬时冲突放大成 20~30 秒全量直扫**，以及**每个请求都在写库**。
口径、日志解析、事件去重规则一个字节都没有改动。

## 复现（真实数据，不是推测）

环境：本机真实会话日志根（6 个来源根 / 1649 个文件 / 约 2.9 GB），
把 `usage.sqlite` 复制到隔离数据目录，`bun run web --no-open --port 8899`，
按页面真实节奏发**3 个并发请求**（overview + series + breakdown）。

| 场景 | 修复前 | 修复后 |
|---|---:|---:|
| 冷启动第一轮（空库，3 并发） | **40.7 s** | **20.3 s**（只剩一份建库） |
| 稳态一轮（3 并发，热态） | 500~540 ms | 330~430 ms |
| 另一个连接持写锁 8 秒时的一轮 | **51.4 s** | **5.7 s** |
| 库被占用 + 确实需要写时（单请求） | **29.7 s**（降级直扫） | 5.5 s（读上一次入库的结果 + 说明原因） |
| 稳态一轮产生的**写事务** | 3 次（每个请求一次） | 0 次（没有新日志时） |

同一现象在用户正在运行的那个实例上也复现过：单发第一个请求 31.2 s，
3 并发时每个 28.5 s，进程持续烧掉约 60% 的一个核。

## 三条根因

1. **每个请求都在写库**（`core/src/db/schema.ts` 的 `ensureSchema`）。
   `PRAGMA user_version = N` **即使值没变也会写库头**（实测一次写产生 4152 字节 WAL 帧），
   而每次取数都会开一次库 ⇒ **每个只读请求都是一个写入者**。
   本地页一次取数发 3 个并发请求，于是三个写入者互相抢锁。
   现在只在版本真的不同时才写；`CREATE ... IF NOT EXISTS` 在表/索引都在时不写（已实测）。

2. **瞬时锁冲突被放大成全量直扫**（`core/src/db/stats.ts` 的 `openStats`）。
   `database is locked` 只是「别人正在写」，库里的数据仍然可读；
   原实现把它当成「库不可用」，于是改走直扫 —— 本机 2.9 GB 日志实测 **20~30 秒**。
   本地页每 3 秒轮询一次，几份这样的扫描同时跑就把（单线程的）服务端占满，
   后面的请求等 `busy_timeout` 超时后**也**降级 ⇒ 雪崩，页面再也刷不出来。
   现在这类失败**不降级**：本次读上一次入库的结果，并把原因带进 `degradedReason`。
   只有「库真的打不开 / 真的坏了」才直扫。

3. **并发请求各做一遍同样的工作**（没有单飞）。
   冷启动那一轮原来是**三份全量建库**（40 秒 → 20 秒）。
   现在按「库 + 这一轮要读的根 + 变更文件」做进程内单飞：
   同一份工作只跑一次，后来的并发请求共享它的结果。降级直扫同样单飞，
   避免三份 20~30 秒的扫描同时跑。

## 改了哪些文件

| 文件 | 改动 |
|---|---|
| `packages/core/src/db/schema.ts` | `ensureSchema` 先读版本再决定要不要写；导出 `schemaVersion()` |
| `packages/core/src/db/stats.ts` | `openStats`：单飞（刷新 / 直扫各一张表）+ 被占用不降级 + `isLockError` / `hasAnyEvent` |
| `packages/shared/src/protocol.ts` | `LocalOverviewResponse.degradedReason?`（可选字段） |
| `packages/server/src/local-api.ts` | overview 下发 `degradedReason` |
| `packages/cli/src/cli.ts` | SQL 路径带 `degradedReason` 时也在终端告警（原来只在直扫时告警） |
| `packages/web-local/src/composables/useUsageStats.ts` | 同一时刻只允许一轮请求在飞；切换筛选时**合并**成「这一轮回来后再跑一次」 |
| `packages/web-local/src/composables/usage-view-model.ts`、`types/usage.ts`、`views/UsageStatsView.vue` | 降级说明那一行（提示色，不是报错红） |
| `packages/core/test/db.test.ts` | 4 条回归：占用不直扫 / 两个单飞 / 版本一致时开库不写 |
| `packages/web-local/verify/verify-data.ts` | 降级说明的视图模型断言 |

前端的另一半同样重要：原来切换筛选**不看有没有在飞**，切一下就是 6 个请求、
快速切几下十几个请求同时压在服务端（每个都要 ingest 一次库）；
现在在飞时只记一个「还欠一轮」，回来立刻按**最新**筛选跑一轮。

## 「库被占用」为什么要如实说出来

这一轮的数来自上一次入库的结果（比日志旧一个轮回）。页面/CLI/插件都必须说清这一点 ——
「读了旧数据」与「日志里就是这些」在界面上长得一模一样，而差别正是使用者最需要知道的。
正常一轮不带这个字段；前端只在字段在场时显示提示，**绝不当成空**。

## 仍然存在的边界

- 冷启动第一轮仍是**一份全量建库**（本机 20 秒，2.9 GB 日志 / 4 个纯文本来源）。
  这是「先有库才能秒查」的必要成本，单飞只是把原来的三份变成一份。
- 「库被占用」时那一轮仍会等满 `busy_timeout`（5 秒，`schema.ts` 的 `openDb`）才判定占用。
  它是**有界**的：不再烧 CPU、不再触发直扫。要更快就得给交互路径单独的更短超时。
- 本章的基准都是单次记录，不是 P95 或生产延迟保证。

## 环境备注（与本次改动无关，但会挡住构建）

本机 `HTTP_PROXY` / `http_proxy` 的值带了一个**换行符**，
`bun run build:local` 会因此在 `parseProxyUrl` 抛 `ERR_PROXY_INVALID_CONFIG`。
清掉这两个变量后构建正常（本轮就是这么构建的）。
